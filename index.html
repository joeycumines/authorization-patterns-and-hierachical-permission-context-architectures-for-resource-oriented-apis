Systems Architecture Monograph & Formal Engineering Reference

General Authorization Implementation Patterns & Hierarchical Permission-Context Architectures for Resource-Oriented APIs

A formal analysis of the (Actor, Action, Resource, Context) model, a comparative taxonomy of production authorization systems, and a specification for declaring authorization on AIP/gRPC methods, deciding it with one pure function over scoped grants, and projecting it soundly to user interfaces and agent tool hosts.

Target Paradigm: Google AIP Resource-Oriented APIs (gRPC / Protobuf) Status: Canonical Technical Reference (v1.5) Date: November 2026 Source: GitHub repository ↗

Executive Summary & Key Architectural Conclusions

Core Thesis

A frontend that offers an action the server then refuses has shown a false affordance. Removing false affordances takes two inputs: static facts about each method, read from its protobuf descriptor, and evidence about what the caller holds within a named scope, sent by the server. When roles are scoped grants that select operations by resource type and access class, the server's decision and the evidence it sends are computed from the same grants and descriptors by two small pure functions, and nothing is maintained per permission. The evidence is advisory. The backend decides every request again.

Distributed APIs suffer from an authorization impedance mismatch. Backend services enforce access control pointwise, answering whether actor a may perform action k on concrete resource r under context c. User interfaces, API gateways, batch workflows and agent tool hosts need to know what an actor can do across a whole scope, such as a company or a team, without O(N) round trips and without a cache entry per leaf resource.

This report does two things. First, it formalizes the (Actor, Action, Resource, Context) model and catalogs nine production implementation patterns grounded in primary literature, including NIST RBAC [11], NIST ABAC [12], OASIS XACML [13], Google Zanzibar [10], AWS Cedar [14], Open Policy Agent [19], SpiceDB and OpenFGA [20], Kubernetes SelfSubjectRulesReview [16], Google Cloud TestIamPermissions [17], and Macaroons [15]. Second, it specifies an architecture for resource-oriented gRPC APIs that follow the Google API Improvement Proposals (AIPs), and reaches five conclusions:

  1. Declare requirements on methods and derive everything else. A permission is identified by (resource type, operation). A standard method needs one line of annotation; its operation, access class and target are derived from its AIP shape and its google.api.resource annotations. A permission exists because a method requires it, and there is no other list (§3.2, §4.1, §4.2).
  2. Treat roles as scoped grants that select by type and class. Deciding a request walks the caller's grants down the target's path. Telling a frontend what the caller holds walks the method patterns down each grant's scope. They are two walks over the same data, so the handler and the permission-context endpoint share one resolver (§3.3).
  3. Adopt the smallest profile that fits the policy. Three conformance profiles build on each other: declarations only, grant-shaped contexts, and scoped claims with holes, denials and residual conditions. A context from a simpler profile is a valid context in the next, so an implementation can start small (§3.5, §3.6).
  4. Build the AIP rules into the model. AIP-132 says a List should return the same results to every caller permitted to list. This specification requires it, and puts per-caller filtering in a Search method. The List permission is then the "read children" check that decides between NOT_FOUND and PERMISSION_DENIED, and a wildcard List needs the List permission for every parent the wildcard matches (§4.3).
  5. Make the descriptor closure the only thing a client must read. Everything a client needs to interpret a context is derivable from protobuf descriptors, by reflection or from a descriptor set. Roles, grants and handler code stay server-side policy (§3.1, §3.7).

Part I. The Problem and the Formal Model

Section Takeaway

Enforcement evaluates a pointwise decision function D(a, k, r, c). A frontend needs a statement about a whole scope, which is a universal quantification over that function. A projection is sound if every claim it makes is true at the snapshot it names. Completeness is optional, and freshness is specified separately.

1.1 What a Frontend Needs: Avoiding False Affordances

The problem this architecture solves is narrow. A frontend shows a button, a menu entry or a tool, the user or agent invokes it, and the server answers PERMISSION_DENIED. That is a false affordance. The opposite error, hiding an action the caller could have taken, is a false hide. It costs the caller a capability and is the lesser of the two errors. Failures that are not about authorization (validation, preconditions, quota) are out of scope: no permission hint predicts them. One refusal with the authorization status is out of scope for the same reason. AIP-133 requires PERMISSION_DENIED when a new resource's name collides with a resource the caller cannot see, which depends on stored state, and a hint that predicted it would disclose the hidden resource (§4.3).

A frontend already knows which operations exist, because they are in the API's descriptors. What it lacks depends on its subject, the thing the operation would act on:

  • No subject yet. A navigation bar or a tool list is drawn before any resource is chosen. The question is existential: is there anywhere this caller could do this?
  • A scope. A page for one team asks whether "New widget" should be enabled. The question is universal within that scope: may the caller do this on everything here?
  • An item. A row action asks about one resource. The question is pointwise.

The frontend also consumes two different kinds of information, and they should not be confused. Static method facts need no subject: what a method requires, which names it accepts, and whether it reads or mutates. They drive menu and tool partitioning and consent prompts. Subject-bound evidence says what the caller holds within a named scope. The table below asks, for each way a frontend could obtain that evidence, whether it removes false affordances.

1.2 The Authorization Decision Function

Authoritative enforcement is a function D(a, k, r, c) → {ALLOW, DENY} of an actor, a permission key, a concrete resource name and a context. A method does not carry one key; it carries a list of requirements, each a key paired with the request field that names its target, and every requirement must hold (§3.2). R is the set of schema-valid potential resource names, independent of stored rows: a decision about a widget that does not exist yet is still a decision.

At a fixed snapshot a policy evaluation can end in more states than two: not applicable, permit, explicit forbid, an unresolved predicate, or an evaluation error. The combining rule used throughout this report is:

  • A proven forbid denies.
  • An unresolved or possibly erroring forbid that could apply blocks an unconditional permit.
  • Otherwise a proven permit is required. An unresolved or possibly erroring permit is not sufficient.

"Proven" includes proving that the relied-on policies cannot raise an evaluation error at any point the proof covers. Cedar skips policies whose evaluation errors, including forbids, and reports them in its diagnostics [14], so a fail-closed adapter can be built on it; an adapter MUST declare and test its error policy. For authoritative decisions the recommended choice is to fail closed when an erroring forbid could apply. That is stricter than native Cedar and can reduce availability. Projection MUST use a fail-closed adapter: under native semantics an erroring forbid does not deny, so a projected denial could be unsound, and under any adapter an erroring permit does not allow, so a projected allow could be unsound. A forbid that is proven in this sense, with no unresolved predicate, is called final in the rest of this report. Forbids override permits, so nothing reverses a final forbid.

Two boundaries follow from the function's shape. First, a permission context is an advisory, snapshot-bound hint and never a credential; the server never accepts a client's projection as proof. Second, the server itself splits the work. An interceptor authenticates, binds targets from the request and evaluates everything that depends only on the request and the caller's grants. A handler or data layer makes the checks that depend on stored state and owns the check-and-commit boundary. A commit-time revision check is sufficient only if it covers every fact the decision relied on.

1.3 Pointwise Evaluation vs. Subtree Permission Projection

Pointwise evaluation answers one ground query: "Can Alice execute widgets.update on companies/A/teams/B/widgets/w1 right now?" Permission projection fixes the actor and context (a, c) and an anchor r0, which is a resource name or the service root, and summarizes D(a, k, r, c) across every key k that can bind at or below the anchor and every potential resource r ∈ Subtree(r0) = { r ∈ R | r0 ⪯ r }, where ⪯ is the canonical AIP ancestor-of order.

Each key restricts R to its binding domain, the names its requirements can target. A summary such as ALL/NONE/MIXED is lossy, because MIXED does not say where the exceptions are. Explicit regions are lossless only where every decision region can be represented and disclosed.

1.4 Soundness, Completeness and Monotonicity

Soundness is relative to a fixed actor, policy snapshot, descriptor contract and trusted context. Completeness is not required: withheld evidence stays UNLOADED and the frontend falls back to a narrower query or to the server. A time-to-live limits reuse; it does not provide causality (§3.8).

Theorem 1.1. Fix actor, context, snapshot and key. On the key's binding domain, let A(x) mean an unconditional pointwise allow, true for every assignment of unresolved facts the model admits. Let U(s) mean A(x) for every domain point x at or below s. Then A is downward-monotone if and only if A(s) = U(s) at every in-domain s. Reflexivity gives U(s) ⇒ A(s); downward monotonicity gives the converse.

Three consequences matter in practice:

  • Emitting exact universals is sound for any policy, monotone or not. It need not expose every pointwise allow, so it can be incomplete, and an empty projection is trivially sound.
  • Additive scoped grants are downward-monotone. A permit attached at a scope holds at every descendant, so the server can answer the universal question with one check at the anchor. That is why the grant-shaped profile is cheap (§3.3). Forbids and conditions on descendants break monotonicity and are what the scoped-claim profile exists for (§3.6).
  • The equivalence is trivial only where an anchor has no strict descendant in the key's binding domain. That holds for a key bound to one fixed-depth resource pattern, where the in-domain subtree of a resource is a single point. It does not hold for a parent-bound key whose resource has several parent patterns: with widgets under both companies and teams, widgets.create binds to companies and to teams. Under an arbitrary policy, being allowed to create directly under a company says nothing about its teams; the universal statement has to be proven separately.

Part II. General Authorization Implementation Patterns Taxonomy

Section Takeaway

No single authorization pattern dominates all workloads. Production architectures compose a policy representation model (RBAC, ReBAC, ABAC, Capabilities) with an evaluation topology (pointwise PEP/PDP, bulk check, subtree projection, or partial-evaluation data filtering) matched to the workload's resource graph, latency budget, and revocation strictness.

2.1 Catalog of Nine Production Implementation Patterns

1. Centralized Enforcement (PEP / PDP / PIP / PAP Architecture). Standardized by OASIS XACML 3.0 [13] and NIST SP 800-162 [12], this pattern decouples request interception (Policy Enforcement Point) from decision evaluation (Policy Decision Point) and attribute retrieval (Policy Information Point). It provides uniform auditing and language-agnostic policy governance across microservices (e.g., Envoy ext_authz [22] calling OPA or Cedar). Its primary trade-off is network-hop latency and availability coupling on the critical request path, mitigated by sidecar/in-process PDP deployment.

2. Resource-hierarchy policy inheritance with RBAC role bundles. NIST hierarchical RBAC [11] describes role hierarchies, not resource trees. Services such as Google Cloud IAM [17] and Azure RBAC [24] attach policy or role assignments to resource hierarchy nodes. Allow grants are additive under the applicable policy model; CEL conditions may vary across descendants. Google Cloud IAM policy changes typically propagate in about two minutes, but can take seven minutes or more.

3. Resource-Level ACLs & Relationship-Based Access Control (ReBAC). Pioneered at global scale by Google Zanzibar [10] and implemented in open-source engines like AuthZed SpiceDB and OpenFGA [20], ReBAC models authorization as graph reachability over stored relation tuples (object#relation@user) with userset rewrite rules (union, intersection, exclusion, tuple-to-userset). Zanzibar achieves <10 ms p95 latency across trillions of tuples and prevents the "new enemy" stale-ACL problem using opaque causal consistency tokens called zookies (called ZedToken in SpiceDB) [10] [20]. ReBAC excels at fine-grained, non-hierarchical sharing, but graph traversal makes high-fanout list filtering and coarse prefix projection computationally expensive unless backed by materialized permission views (e.g., AuthZed Materialize) [20].

4. Attribute-Based & Policy-Based Access Control (ABAC / PBAC). Formalized by NIST SP 800-162 [12] and realized in Open Policy Agent (Rego) [19], Amazon Verified Permissions (Cedar) [25] [14], and Google Cloud IAM Conditions (CEL) [17], ABAC evaluates boolean predicates over subject, resource, action, and environment attributes (e.g., time-of-day, data classification, resource ownership). Cedar specifically restricts language expressiveness (no unbounded loops, explicit permit/forbid semantics) to guarantee termination and support SMT-backed static policy analysis [14]. ABAC eliminates role explosion, but attribute volatility lowers cacheability and complicates static permission projection.

5. Scoped Permission Projection & Self-Review APIs. Used directly to drive permission-aware UIs and CLIs without O(N) pointwise checks. Real-world precedents include Kubernetes SelfSubjectRulesReview (authorization.k8s.io/v1, which enumerates a caller's effective resourceRules within a namespace and explicitly returns an incomplete boolean when an external authorizer cannot project rules) [16], Google Cloud IAMPolicy.TestIamPermissions (which intersects a caller-supplied candidate permission set against effective permissions on a resource) [17], and AWS IAM SimulatePrincipalPolicy [18]. Kubernetes warns about incomplete results and confused-deputy risks; Google Cloud warns that TestIamPermissions is for permission-aware tools and may fail open. Neither substitutes for authoritative enforcement [16] [17].

6. Batch & Bulk Authorization Evaluation. Bulk checks amortize RPC overhead. SpiceDB CheckBulkPermissions supports ZedToken consistency controls; OpenFGA BatchCheck provides correlation IDs and MINIMIZE_LATENCY / HIGHER_CONSISTENCY preferences, not a snapshot token or a shared-snapshot guarantee [20].

7. Authorization-Aware Search & Data Filtering (Partial Evaluation). AIP-132 says a standard List should return the same results to every caller permitted to list [26], so filtering results per caller belongs to a Search-style custom method (§4.3). There, authorize the invocation and the visibility of each item separately. A parent scope alone cannot exclude forbidden descendants. Use a query predicate equivalent to per-item authorization, or an authoritative bulk check of candidate rows; page sizes, counts and tokens MUST NOT expose rejected candidates. OPA’s classic /v1/compile returns Rego ASTs; /v1/compile/{path} supports target-specific SQL/UCAST filter compilation [19].

8. Delegated Capability Tokens & Attenuation. Macaroons [15] can be attenuated by appending chained HMAC caveats. Verification is O(number of caveats) plus the cost of evaluating those caveats. Short TTLs and discharge caveats can constrain offline use. Biscuit [23] offers offline attenuation with public-key signatures and Datalog-based policies.

9. Field-Level & Long-Running Operation (LRO) Authorization. AIP-161 field masks select fields [30]; a separate policy authorizes them (§3.2). AIP-151 [5] defines the operation shape, not permissions. A typical local policy binds an operation to its creator and rechecks the originating permission on GetOperation and WaitOperation, and ListOperations returns only operations the caller may get. Declare these as named handler policies for the imported Operations methods the service actually serves (§4.1).

IAM Allow inheritance is downward-monotone only where attached conditions preserve descendant truth. CEL conditions can break it even without IAM Deny.

Cedar’s guarantees concern termination and analyzability, not a latency bound.

Part III. The Architecture: Declarations, Grants, Decisions and Contexts

Section Takeaway

Methods declare what they require. Policy grants access by resource type and access class at a scope. One pure function decides a request from those two inputs, and the same data, traversed from the grant instead of from the target, produces the permission context a frontend folds. Everything else in this part is a consequence: how names form a hierarchy, which profile to adopt, how exceptions and private rules are handled, how the contract evolves, and how contexts are cached.

3.1 The Pieces and Who Owns Them

The architecture has five pieces. Each has one owner, and the design goal is that no fact is written down twice.

  1. Declarations. Each RPC states what it requires, as a protobuf method option. Combined with the resource annotations an AIP-style API already carries, this fixes for every method its resource type, operation, access class, target and effect (§3.2).
  2. Grants. Server policy records which principals hold which roles at which scopes, and what each role selects. Grants are runtime data and never appear in descriptors (§3.3).
  3. The decision. For each request the service binds the declared targets and checks the caller's grants. Checks that depend on stored state run in the handler (§4.4).
  4. The context. On request, the service tells a caller which permission keys it holds within the scopes it asks about. This is the projection (§3.5, §3.6).
  5. The fold. The client combines a context with the declarations to decide what to offer. It never enforces (§4.4).

How much should a method say about authorization? Too little, and distinct operations collapse into one check. Too much, and every RPC carries a hand-maintained string that must be kept consistent with roles, clients and other methods. The third column is the design. It separates three things that a single facet conflates.

Identity. A permission is identified by its resource type and its operation. Its display form, the permission key, is the type's plural and the operation: books.get, books.search, books.expunge. Because the key is derived, two methods that perform the same operation share it without coordination (GetBook and BatchGetBooks both require books.get), and there are no hand-spelled names whose conventions someone has to enforce.

Access class. Every requirement has exactly one class: READ, CREATE, UPDATE, DELETE, ADMIN or EXECUTE. A class is a selector over operations. A role that grants READ on Book covers books.get, books.list and books.search today and any READ operation added later. Standard methods take their class from their AIP shape. A custom method states it, because nothing else about a custom method is reliable enough to infer it from: AIP-136 lets a retrieval method use POST when its payload could exceed URL length limits [4]. EXECUTE exists so that custom mutations, such as publishing a document or running a job, are not classified as UPDATE and granted to every editor without anyone having decided so. No class implies another: ADMIN does not include DELETE, and UPDATE does not include CREATE.

Effect. Whether invoking a method changes state is a property of the method, and a frontend needs it with no subject at all: to separate read tools from mutating ones, to decide when to ask for confirmation, and to hide mutations on a read-only credential. It is derived. A method whose requirements are all READ is read-only; one with a DELETE requirement is destructive; anything else is mutating. Requirements that apply only to some requests count, because the effect describes the method and not one call. Effect and class can differ, as the access-policy row shows, and such a method overrides the derived effect with protobuf's standard idempotency_level = NO_SIDE_EFFECTS option [21].

Requirements that depend on the request. Some requirements apply only when a request field is set. AIP-134 lets an Update with allow_missing create a missing resource and says the caller must hold the update permission [26]. This specification adds a local, stricter rule that stays declarative: when a request sets allow_missing = true, create on the parent is required as well. The rule reads the request, never the stored row, so an update-only grant can never create and the client can evaluate it. A requirement that depends on stored state, such as whether a row exists or who owns it, is not declarative and belongs to the handler (§3.3).

Field-sensitive writes. AIP-134 defines the fields an Update writes from the request alone: an omitted mask means the populated fields, * means every field, and when allow_missing creates a resource every populated field is applied regardless of the mask. AIP-161 says output-only fields named in a mask are ignored [30]. A Create writes the fields its request populates. A field guard is therefore declarative too: a resource field may name an additional operation that is required whenever the fields a request writes include that field, a path inside it, or a message that contains it (§4.1, §4.2). A server that cannot tell from a request which fields it writes requires every guard. "Only fields whose values actually change" depends on stored state and is a handler concern.

Credential limits. A delegated credential, such as an OAuth grant given to an agent or a third-party client, limits what its bearer may do. Model it as a ceiling of access classes, optionally per resource type, and intersect it with the principal's grants. The ceiling applies to each key by that key's own class, so a role that names an operation is limited exactly as a role that selects the operation's class. A ceiling never adds authority, and a new READ operation falls under a read-only ceiling exactly as it falls under a READ grant. The credential issuer states the ceiling; it does not decide resource authorization, which stays with the service that owns the resource.

3.3 Scoped Grants and the Two Walks

A role, by itself, grants nothing. A grant attaches a role's selectors to a scope: "viewer at companies/A", "widget-writer at companies/A/teams/B". An actor may hold different roles at different scopes, in different tenants, with no enclosing organization assumed. A grant may also be a forbid, and may carry a condition.

Decide is the server's function. It walks the caller's grants down the path of the target. K(g) is the answer to "what should be sent for this grant": it walks the method patterns down the grant's scope and collects the keys the grant selects. Fold is the client's function over what was sent.

Proposition 3.1 (exactness). Let Π = { (g.scope, g.effect, K(g)) : g ∈ G } for unconditional grants G. Then Fold(Π, key(ρ), t) = Decide(G, ρ, t) for every requirement ρ and every target t in its binding domain, provided the type and class of a key are a function of the key. Proof. If g.scope ⪯ t and t is in the domain of ρ, then reach(ρ, g.scope) holds, so key(ρ) ∈ K(g) exactly when match(g, ρ). ∎ The regression checks in §4.5 compare the definition, the reference rule engine and the contexts of both profiles over every policy of one or two grants in the reference fixture, with permits and forbids.

How Π reaches a client. Π is a definition, not a wire format. A policy of permits only is sent as it stands: one hole-free ALLOW claim per grant scope, which is the grant-shaped profile. With forbids the two context profiles differ. The grant-shaped profile cannot send a forbid entry, so it removes from each permit entry every key that a forbid could deny somewhere within that entry's scope. What remains is true, the fold stays sound, and a narrower anchor recovers what was removed (§3.5). The scoped-claims profile sends the forbids as holes in ALLOW claims and as DENY claims, and for unconditional, disclosable grants its fold equals Decide (§3.6).

Several properties follow, and they are the practical content of this section:

  • Nothing is maintained per permission. K(g) depends only on the selector set and the shape of the scope, a company versus a team. It is computed from descriptors, it is the same for every user and every company, and it can be computed once at startup. The only per-user data is the list of scopes and selector sets.
  • The handler and the context endpoint share one resolver. Both start from the caller's effective grants. The context endpoint returns, in expanded form, what the handler already consults.
  • Scopes are discoverable. A context queried at the service root carries claims at each scope where the caller holds a grant. That answers "where can I act?" without any listing permission.
  • The no-subject question is answered from the same data. A key in an ALLOW claim means its operation is usable throughout that claim's region. In a policy of permits only the converse holds too: a key that appears in no claim of the root context is usable nowhere. With forbids or conditions, absence means only that nothing was proven at that anchor. A caller who holds only a team-level editor grant is never offered CreateTeam, which binds to the company, and no stored row is scanned to find that out.
  • The pattern walk is not needed for soundness. The ancestor test in Fold already confines a key to targets under its scope. The walk only keeps payloads minimal and makes the no-subject answer exact.

Why the class must be readable from the method. The construction works because each requirement's resource type and class can be read from the method's own declaration. If classes lived in a separate table keyed by permission name, K(g) could not be computed from descriptors, and that table would have to be shipped to every client and kept in step with every release. The same is true of a table that expands each role into a list of permissions. Both tables are the hand-maintained lists this design removes.

Counterexample 1 — One Key, Two Classes

With identities derived from (type, operation) this cannot be written down, and the build rejects two methods that give one operation different classes (§4.2).

Limits of the grant model. It is deliberately small, and five things lie outside it:

  • Exceptions. A forbid below a permit means the permit's claim is no longer universal. The grant-shaped profile omits the affected keys from the broader claim; the scoped-claim profile reports the exception as a hole (§3.5, §3.6).
  • Conditions. A conditional grant yields a CONDITIONAL claim at best. The client does not execute predicates.
  • Very many direct shares. A caller with thousands of grant scopes should not receive them all at the root. The server marks the context as having omitted descendants and the client queries narrower anchors (§4.1).
  • Relationships that are not a name hierarchy. Group membership and sharing edges are resolved by the server into effective grants before anything is decided or projected (§3.4).
  • Upward and sideways access. Nothing is implied upward: a team role does not allow reading the company. Operations bound to the service root need a grant at the root, so an administrator of one tenant never satisfies a global method.

3.4 Resource Hierarchy, Prefixes and External Identities

AIP-124 gives every resource at most one canonical parent, and AIP-121 requires the parent-child relationship to be acyclic [1]. This specification adds one synthetic node above every top-level resource, the service root, whose segment list is empty. It is written //{service_name}/ in prose only. On the wire it is a tagged value, distinct from every AIP-122 resource name and AIP-156 singleton, and it is never passed to a generated name parser. Authorization often involves relationships that are not part of this tree: a user belongs to a group, a project is linked to a billing account, a widget is shared with a collaborator in another company. Segment-Aware Matching vs. Naive String Prefixing

Counterexample 2 — Naive String Prefix Collision

If a client checks target.startsWith(scope), a grant on companies/A/teams/B also matches companies/A/teams/B2 and companies/A/teams/Billing/widgets/w9. Appending a slash fixes those sibling cases but still fails on names that are not canonical: …/teams/B/%2E%2E/C starts with …/teams/B/, yet a downstream decoder may normalize it to …/teams/C; doubled or trailing slashes create alternate spellings of one name; and the same relative path under another service is a different resource. AIP-122 says resource IDs should avoid characters that need URL-escaping [2], so a canonicalizer can reject such spellings outright.

Remedy. All matching, on server and client, parses a name into a service and a flat list of validated segments. A scope s covers a target r if and only if they belong to the same service, len(s) ≤ len(r), and every segment of s equals the segment of r at the same index. The root's empty list is a prefix of every name, and no tenant scope can be a prefix of the root. Reject empty segments, . and .., percent-encodings, and a slash or backslash inside an identifier, unless a service-defined canonicalizer resolves the spelling unambiguously before any policy is evaluated.

Two AIP allowances fall outside this segment model, and an API that uses them MUST declare the affected methods as handler policies: AIP-122 only says the terminal segment of a name should not contain a slash, and AIP-4231 allows a segment made of several variables joined by a separator [3]. Singleton and other static segments are ordinary literal segments.

Reachable Keys and the Pattern Trie

Every key is indexed under each of its binding patterns in a segment pattern trie rooted at the service root. A query walks the anchor's segments from the root. At each depth it follows the edge labeled with the anchor's segment and the * edge, whichever of the two exist. From every node it reaches at the anchor's depth it collects the keys bound at that node and at every node below it. That is the reach test of §3.3 applied to all keys at once. The walk costs O(matched nodes + keys returned), which is at most O(P·d + output) for P patterns of depth d.

A scope does not have to be a resource the service represents. A service that manages widgets under companies/{company}/teams/{team}/widgets/{widget} without implementing GetCompany can still attach grants to, and answer contexts for, companies/A: it is a local non-represented parent, a prefix of the service's own names. Resource types defined elsewhere are declared with the file-level google.api.resource_definition option documented in AIP-4231 [3].

Aliases and External Identities

AIP-122 allows programmatic aliases, such as users/me, provided responses use canonical names [2]. The server MUST resolve an alias to the immutable canonical name before policy evaluation and before any cache key is formed; otherwise a forbid on companies/A is bypassed through its alias. A name owned by another service, such as //org.example.com/companies/acme, is not a local prefix. It enters the tree only through an identity mapping that server policy declares and versions, and claims are always expressed in the queried service's own names. Where a mapping cannot preserve policy semantics, the affected methods are handler policies.

The profiles embed. A grant-shaped context is a scoped-claims context that happens to contain only hole-free ALLOW claims. In the other direction, a scoped-claims context is coarsened to a grant-shaped one by dropping every claim that is not a hole-free ALLOW, and dropping a claim is always sound. A client states the highest profile it implements, the server never sends it more, and a deployment can move between profiles without changing the meaning of anything it has already sent.

What both context profiles owe. The grant-shaped profile sends less. It does not prove less. Every ALLOW claim is a universal statement, so a server in either profile has to know whether a forbid or a condition for the key exists anywhere below the claim's scope, including one attached to a single resource; that is the descendant-rule index of §3.6. Omitting a key because of a rule also tells the caller that such a rule exists, so the disclosure rules of §3.6 bind both profiles: a key whose rules may be private is declared nonprojecting, and nothing is sent for it above its privacy boundary. A policy of unconditional permits meets both obligations trivially, which is why this profile is cheap for the policies it was designed for.

What the grant-shaped profile does with an exception. Suppose a viewer grant at companies/A and a forbid on reads at companies/A/teams/C. "Reads are allowed everywhere in A" is false, so the server omits the read keys from the claim at A. A frontend drawing the page for Team B finds no evidence for widgets.get there and queries Team B directly, where the claim is true and is returned. The exception costs one more query and never produces a wrong answer.

Item-level questions. When the anchor is a single resource, the subtree in the key's binding domain is one point, so the universal claim is the pointwise decision. A page of twenty rows with per-row actions is one query with twenty anchors. A service MAY evaluate stored attributes for such a leaf anchor and return ALLOW where a broader anchor could only say CONDITIONAL. It does so only for a resource the caller is allowed to read. An answer that depends on stored state discloses that state, so for any other name the context is computed from rules alone and is the same whether or not the resource exists.

Choosing. Implement Declarations if the only need is to partition operations and describe inputs. Implement Grant-Shaped Contexts when roles are assigned at scopes and exceptions are rare; this covers most multi-tenant applications. Move to Scoped Claims when exceptions are common enough that the extra queries are felt, or when the interface must explain a denial instead of hiding the action.

3.6 The Scoped-Claim Algebra and Disclosure

This section defines the third profile. The claim algebra is needed only for Scoped Claims. The descendant-rule index and the disclosure rules at the end of the section bind both context profiles (§3.5).

Domain. For key k and anchor s, the relevant domain is every schema-valid potential name that matches one of k's binding patterns at or below s, including names not yet allocated. For a root-bound key the domain is the root alone. A server MUST NOT enumerate stored rows to prove a universal, and emits no claim for a domain that is empty by schema, even though a universal over it is vacuously true.

Regions and kinds. A region is a scope (a resource name, a collection prefix, or the root) minus zero or more strict-descendant scopes, its holes. Collection prefixes are needed where a resource has several parent patterns: with widgets under both companies/{company} and companies/{company}/teams/{team}, a claim may cover companies/A/widgets, or cover companies/A with the hole companies/A/teams. A claim states one of three kinds about a set of keys over a region, with these proof obligations at the snapshot the view names:

  • ALLOW implies an authoritative allow at every in-domain point of the region.
  • DENY implies an authoritative denial at every in-domain point. There are two proof routes: a final forbid (§1.2), or the absence of any permit that could apply. The wire does not distinguish them.
  • CONDITIONAL means this projection did not resolve a predicate. It asserts no decision; another context may prove one for the same target.

Absent regions assert nothing either. A response's existence proves no coverage: only a DENY claim says "no".

The supported projector. Compile the rules that apply to the caller into finite, ancestor-inherited permits and forbids over canonical scopes, each with an optional predicate. In the grant model these are the caller's effective grants with their keys expanded (§3.3). Pin a single snapshot for every input the proof uses. Partition the requested subtree at the scopes of disclosable rules: each boundary owns the remainder of its region outside more specific boundaries, including the open remainder for names that do not exist yet. Intersect every cell with the key's binding domain and drop empty cells. Which rules apply is then constant within a cell; predicates may still vary from point to point. For each cell:

  1. Emit DENY if a final forbid applies throughout the cell: unconditional and provably free of evaluation errors (§1.2).
  2. Otherwise emit ALLOW only if (a) an applicable permit is unconditional on the cell, meaning it has no predicate or its predicate is proven true at every in-domain point with every fact it reads pinned to the snapshot, and is provably free of evaluation errors, and (b) every possible forbid is ruled out, including one that could apply through a predicate or an error. An owner-only permit therefore never yields ALLOW.
  3. Otherwise emit DENY if no permit can apply at any in-domain point of the cell.
  4. Otherwise emit CONDITIONAL if that is safe to disclose, and nothing if it is not.

Then merge a cell into the cell that encloses it when both have the same kind. A boundary remains a hole only where the answer changes, so nested permits yield one claim without a hole, which the grant-shaped coarsening keeps. Default denial is tested before CONDITIONAL so that a residual predicate that cannot change the outcome, such as a conditional forbid where no permit applies, does not suppress a provable denial. Budget, dependency and disclosure failures never establish DENY. If the compiler cannot establish that rule applicability is constant within a cell, as with unmodeled aliases or relationship joins, it emits no claim for the affected region. Arbitrary policy programs have no exact projection under this contract.

Proving that nothing applies below. Steps 2(b) and 3 quantify over every rule that could apply anywhere in the cell, including a rule attached to a single row, and rows may not be enumerated. Both obligations are discharged by a descendant-rule index: for each scope and key, whether any rule for that key exists strictly below the scope, with a revision that changes whenever such a rule is added or removed anywhere beneath it. The index is a normative part of both context profiles. A key whose rule sources the index does not fully cover MUST be declared nonprojecting, as defined below.

Validity inside a context. Two claims of different kinds for the same key MUST NOT overlap. Overlap and emptiness are computed on the intersection of the regions with the key's binding domain, so a remainder that contains no potential names, for example a team minus its AIP-156 singleton for a key bound only to that singleton, is empty and overlaps nothing. Claims may be merged only if their union is exactly the replacement region in the binding domain.

Counterexample 3 — The One-Bit Leak

Alice holds a viewer grant at companies/A. An administrator places a forbid on companies/A/teams/D that Alice must not learn about. If the server answers Alice's query for A with ALLOW when the forbid is absent and with nothing when it is present, Alice learns that an exception exists. If it answers ALLOW with a hole, she learns its name. If it answers CONDITIONAL only when the forbid carries a predicate, the same bit leaks through a different kind. The only answer that tells her nothing is the same answer in every case.

Private rules are declared per key. A deployment states, for each key or resource type, whether its rules may be private and at which level of the hierarchy, the privacy boundary. For a declared key the server withholds every kind of claim at every anchor strictly above the boundary, whether or not a private rule exists; such a key is nonprojecting there. At or below the boundary claims are emitted normally, because a DENY at the private scope says no more than a failed call would. This is also why the two denial routes share one wire kind: a caller cannot tell an explicit forbid from a default denial. A deployment with no private rules declares none and projects everything. A private rule found for a key that was not declared is a deployment error: the server withholds every claim for that key above the rule, raises an operational alert, and still answers the query.

The enforcement path is bound by the same principle. In three places the server itself proves a universal: a wildcard List, the single parent check of a batch, and the NOT_FOUND answer of a wildcard Get (§4.3). For a nonprojecting key above its privacy boundary each of those checks refuses in every case. Succeeding only when no private rule exists would disclose the rule as surely as a claim would.

What may be named. A claim's scope and its holes name scopes. The scope of a grant the caller holds is always disclosable to that caller: a grant cannot be used without knowing where it applies. Any other scope, typically that of a forbid, is disclosable to a caller who could see it through the API, by get on it or list on its parent. A collection prefix names no resource and is always disclosable. A rule at a scope that is not disclosable to a caller it applies to is a private rule and is handled by declaration, as above. The server never decides rule by rule whether to withdraw a claim, because that decision is the leak of Counterexample 3; policy authoring SHOULD reject such a rule for a key that is not declared private-capable. A claim is never sent without one of its holes. Coarsening may only drop claims or merge claims whose union is exact, and MUST NOT widen a region or drop a hole. The same rules govern errors and diagnostics, over the whole status payload (§4.3).

3.7 Evolution Safety: New Operations Under Existing Grants

Class selectors make policy forward-compatible, and that is also the hazard. A new RPC classified READ is granted to every role that selects READ on its resource type the moment it is deployed. Nobody edited a role, and nobody was asked. The specification keeps the convenience and adds a review step.

  1. Capability diff. The build compares the interpretation of the descriptors before and after a change and reports, for each role, the keys it gains and the keys it loses. The change is accepted only when that report has been acknowledged. This is the one place where a human reads a list of permissions, and the list is generated.
  2. Explicit-grant-only operations. An operation marked explicit_grant_only is never matched by a class selector in a permit. A role holds it only by naming it. A forbid by class still covers it, so an exception written as "no deletes here" also stops the operation that most needed stopping. AIP-164 requires an expunge permission separate from delete [28]; this marker is how that requirement is met, and it suits any operation that is irreversible or unusually sensitive.
  3. New resource types. A selector that names every type picks up a new resource type the same way, and the diff reports it the same way. Prefer selectors that name types for anything sensitive.
  4. Reclassification. Changing an operation's class changes which roles grant it. The diff shows it as a loss for some roles and a gain for others, and it is reviewed as such.
  5. Contexts across versions. Two things can differ between a client's descriptors and the server's. A key may be unknown to one side. Claims are stated per key and the server expands them, so a context issued before a change is silent about a key introduced after it, and a client skips a key it does not know. A method may also require something different: a release adds a second requirement to an existing method, and a client folding the old list would report ALLOW for a call the server refuses. Keys cannot catch that. Each view therefore carries contract_version, a hash of the interpretation the server used (§4.2), and a client folds a view only if that value equals the hash of its own interpretation. On a mismatch every fold is UNLOADED until the client has refreshed whichever is behind, its descriptors or the view. The hash covers only what authorization reads, so a release that changes nothing there invalidates nothing.
Counterexample 4 — A Class Claim Across Versions

Suppose contexts carried "READ on Widget at companies/A" instead of keys. Version 2 of the service adds ExportWidgets, classified READ, with a forbid for Alice at Team C. A client that already has the version 2 descriptors and still holds a version 1 context folds ALLOW for ExportWidgets at Team C: the claim never considered that operation. With keys, widgets.export is simply absent from the old context. This is why selectors stay on the server (§3.3).

3.8 Caching, Freshness and Cardinality

Proof cache key. Key a shared proof entry by service, contract version, revision authority, revision epoch, projection-dependency revision, effective principal, canonical claims digest, tagged canonical anchor and profile. Every component MUST be present; a missing one means the proof is not cached. Authority and epoch are part of the key because a revision counter may repeat after a failover or a reset, and a proof must never be served across that boundary. A dependency revision covers inherited changes above the anchor, changes below it that affect universal proofs, and the referenced data and disclosure rules. A service-wide monotonic revision is the conservative baseline; a tenant revision alone cannot key an anchor that spans tenants. Resolve the current revision from an authoritative view before using its cache namespace, and compute and label a new entry from that same view.

Claims digest. The digest covers every authenticated input that policy reads: the effective principal and delegation chain, tenant, credential ceiling, authentication assurance, and any stable network or device posture. Version the serialization, sort sets, preserve ordered inputs, type values, and distinguish absent from empty. An unmodeled input that can affect a claim makes the claim uncacheable or CONDITIONAL. Do not hash wall-clock time; cap reuse at the next provable time-policy boundary, or do not cache the time-dependent proof.

Session-independent entries. A shared entry MUST NOT hold a subject context identifier, a session identifier, view metadata or a session-capped lifetime. On every response, including cache hits, the server stamps the current caller's subject_context_id, the pinned view's metadata, and remaining_ttl = min(remaining proof lifetime, remaining lifetime of this caller's session or credential).

Lifetimes. Measure remaining_ttl immediately before sending, from the original expiry; receipt, persistence and replay never restart it. Each cache tier uses one expiry model. Node-local caches store a monotonic-clock deadline. Shared caches store an absolute expiry and require a documented maximum clock skew between writers and readers; a reader subtracts that bound and its read delay and treats a non-positive result as a miss. The wire carries only the relative remaining_ttl. A client converts it to a monotonic deadline measured from the start of its request, never extends it, and rejects a view whose value is zero, negative or not a number.

Ordering across replicas. A lagging replica can serve an older view after a newer one has been accepted. Serializing a client's requests prevents responses from being reordered; it does not prevent this. Wherever more than one replica can answer, one of two mechanisms is REQUIRED: the revision authority assigns a monotonic generation to every pinned view, and the client rejects a lower one, and treats an equal one as valid only if it names the same revision; or the client sends the view it last accepted as a floor, min_view, and the server answers from a view at least that new or refuses with UNAVAILABLE. A floor names its revision authority and epoch as well as the revision, and it binds only inside that namespace: after a failover or a reset the server answers from its current view, and the client, seeing a new namespace, starts again (§4.4). The revision authority orders its own revisions; clients compare them only for equality. Generations do not exceed 253−1. They are carried as int64, since AIP-141 rules out unsigned integer types, and ProtoJSON serializes them as decimal strings, so clients in every language parse them as integers and compare numerically, never as strings.

Staleness is bounded. Refresh a context when the server answers PERMISSION_DENIED, without treating the refresh as authority to retry a mutation; expiry and revalidation also discover permissions granted since the last query. After a revocation the server denies as soon as it observes the new revision. An unexpired context may still show the action until it is refreshed, and it confers nothing.

Part IV. Reference Engineering Specification & End-to-End Walkthrough

Section Takeaway

The normative content is four things: a small set of protobuf options and one context RPC (§4.1), the rules by which descriptors are interpreted (§4.2), the rules each kind of AIP method follows (§4.3), and the server and client algorithms (§4.4). An executable reference model checks them (§4.5).

4.1 Reference Protobuf Contracts & Interactive Explorer

The annotation contract extends google.protobuf.MethodOptions, ServiceOptions and FieldOptions. The numbers shown are in the range protobuf reserves for private use (50000–99999); a published API uses registered extension numbers [21].

authz/v1/annotations.proto — Method, Service and Field Options 
syntax = "proto3";

package authz.v1;

import "google/protobuf/descriptor.proto";

option java_multiple_files = true;
option java_outer_classname = "AnnotationsProto";
option java_package = "com.example.authz.v1";

extend google.protobuf.MethodOptions {
  // What this RPC requires. Omission never means public access.
  MethodAuthz method = 51001;
}

extend google.protobuf.ServiceOptions {
  // Authorization settings of the service.
  ServiceAuthz service = 51002;
}

extend google.protobuf.FieldOptions {
  // On a resource field: a request that writes the field also needs
  // this requirement, on the same target as the write. Only
  // access_class (UPDATE or ADMIN), operation and explicit_grant_only
  // are set.
  Requirement field = 51003;
}

// Authorization settings of one service.
message ServiceAuthz {
  // Every RPC of this service must carry a declaration, and every
  // served imported RPC must be listed below; a missing one fails the
  // build. When false, an RPC without a declaration is outside this
  // contract and clients defer to the server for it.
  bool required = 1;

  // Dispositions for served RPCs defined in imported protos that
  // cannot be annotated, such as google.longrunning.Operations.
  repeated ImportedMethod imported_methods = 2;
}

// The disposition of one RPC defined in an imported proto.
message ImportedMethod {
  // Full method name: "google.longrunning.Operations/GetOperation".
  string method = 1;

  // Any form except `standard`.
  MethodAuthz authz = 2;
}

// What one RPC requires. Exactly one of `standard`, `handler_policy`
// or a non-empty `requirements` is set.
message MethodAuthz {
  // The two forms that carry no requirement list of their own.
  oneof form {
    // Derive the requirement from the AIP standard or batch method shape.
    Standard standard = 1;

    // A named authoritative policy implemented by the service.
    // Clients always defer to the server for such a method.
    string handler_policy = 2;
  }

  // The independent requirements of a custom method. All must hold.
  repeated Requirement requirements = 3;

  // Search-style methods: the operation each returned item must pass,
  // on the resource type of the first requirement. Some method of the
  // service must declare that operation.
  string item_filter = 4;

  // Whether a batch-like custom method may partly succeed. Frozen.
  enum PartialSuccess {
    // Derive from the method shape.
    PARTIAL_SUCCESS_UNSPECIFIED = 0;

    // Atomic.
    NEVER = 1;

    // Operation-returning methods only.
    ALWAYS = 2;

    // Chosen by the request's return_partial_success field.
    REQUEST_SELECTED = 3;
  }

  // Custom batch-like methods only. Standard batch methods derive it.
  PartialSuccess partial_success = 5;
}

// One operation on one resource type, bound to one request field.
message Requirement {
  // A selector over operations, used by grants and by credential
  // ceilings. No class implies another. Values may be added; a method
  // with a class an interpreter does not know is not interpreted.
  enum AccessClass {
    // Invalid. Every requirement states its class.
    ACCESS_CLASS_UNSPECIFIED = 0;

    // Observes state.
    READ = 1;

    // Brings a resource into existence.
    CREATE = 2;

    // Changes an existing resource.
    UPDATE = 3;

    // Removes a resource.
    DELETE = 4;

    // Privileged administration, such as access policy.
    ADMIN = 5;

    // Any other custom mutation, such as publishing or running a job.
    EXECUTE = 6;
  }

  // The class of the operation.
  AccessClass access_class = 1;

  // The operation, in lower camel case: "count". With the resource
  // type it identifies the permission (§3.2).
  string operation = 2;

  // Request field path that names the target. `[]` expands one repeated
  // field. Derived from the request shape when omitted (§4.2).
  // Mutually exclusive with service_root.
  string target = 3;

  // The target is the service root.
  ServiceRoot service_root = 4;

  // Resource type, when the target field's google.api.resource_reference
  // cannot supply it.
  string resource_type = 5;

  // Path of a bool request field. The requirement applies only when
  // that field is true.
  string condition = 6;

  // Never matched by a class selector in a permit. Granted only by
  // naming the operation (§3.7).
  bool explicit_grant_only = 7;

  // Parent variables whose ID segment may be "-" (AIP-159).
  repeated string wildcard_variables = 8;
}

// Options of the derived form.
message Standard {
  // Parent variables whose ID segment may be "-" (AIP-159). Valid on
  // List, on Get only where IDs are unique across parents, and on the
  // top-level parent of a batch method.
  repeated string wildcard_variables = 1;
}

// The tagged service root. Distinct from every AIP-122 resource name.
message ServiceRoot {}

A method declares one of three things. standard derives the requirement from the method's AIP shape. requirements lists what a custom method needs, each entry an access class and an operation. handler_policy names a policy the service implements. A field guard is a requirement placed on a resource field.

The contracts follow the AIPs they build on, and both files pass Google's AIP linter with no findings. Integer fields are signed (AIP-141). An enum used by one message is nested in it with unprefixed values, and a shared enum sits at the end of its file with prefixed values (AIP-126, AIP-191). Request fields carry google.api.field_behavior (AIP-203). Field names are nouns, not verbs or prepositions, and avoid reserved words (AIP-140), which is why the access class is an enum value and not a field named read or delete [31]. The Java package shown is a placeholder for the publishing organization's own.

The context contract is one RPC. It is a custom method in the sense of AIP-136 [4]: it returns no resource of its own, so it does not borrow a standard method's name. It uses POST because a list of structured anchors could exceed URL length limits, the case in which AIP-136 permits POST for a retrieval method. The URI places the whole verb and noun after the colon, as AIP-136 advises for a method with no collection.

syntax = "proto3";

package authz.v1;

import "google/api/annotations.proto";
import "google/api/field_behavior.proto";
import "google/api/resource.proto";
import "google/protobuf/duration.proto";

option java_multiple_files = true;
option java_outer_classname = "PermissionContextProto";

service PermissionContextService {
  option (authz.v1.service) = {
    required: true

  // within each requested anchor. Never a credential.
  rpc QueryPermissionContexts(QueryPermissionContextsRequest)

    option (google.api.http) = {
      post: "/v1:queryPermissionContexts"
      body: "*"
    };
    option idempotency_level = NO_SIDE_EFFECTS;
    option (authz.v1.method) = {
      handler_policy: "authenticated_subject_disclosure"
    };
  }
}

// Request message for QueryPermissionContexts.
message QueryPermissionContextsRequest {
  // API service whose operations are asked about: "widgets.example.com".
  string service = 1 [(google.api.field_behavior) = REQUIRED];

  // One or more anchors: the service root or resource names.
  repeated Scope anchors = 2 [(google.api.field_behavior) = REQUIRED];

  // Highest profile the client implements. The server never sends more.
  // Unspecified means PROFILE_GRANT_SHAPED.
  Profile max_profile = 3 [(google.api.field_behavior) = OPTIONAL];

  // Answer from a view at least this new, or fail with UNAVAILABLE.
  ViewFloor min_view = 4 [(google.api.field_behavior) = OPTIONAL];
}

// Every context below shares these fields.
message QueryPermissionContextsResponse {
  // The API service the view describes.
  string service = 1;

  // Lowercase hex SHA-256 of the canonical interpretation the server
  // used (§4.2). A client folds this view only if it equals its own.
  string contract_version = 2;

  // Identifies the subject and the authenticated inputs of this view.
  string subject_context_id = 3;

  // Snapshot identifier. Clients compare it for equality only.
  string policy_revision = 4;

  // The system that issues and orders policy revisions.
  string revision_authority = 5;

  // Changes whenever the authority's revision sequence restarts.
  string revision_epoch = 6;

  // Scoped to the authority and epoch. Between 0 and 2^53-1; compare
  // numerically.
  optional int64 generation = 7;

  // Remaining, not original. Reject a value that is not positive.
  google.protobuf.Duration remaining_ttl = 8;

  // The profile actually used; never above max_profile.
  Profile profile = 9;

  // Each distinct set of permission keys, once.
  repeated KeySet key_sets = 10;

  // Sparse: an anchor that does not resolve for the caller is omitted.
  repeated PermissionContext contexts = 11;
}

// A service-relative scope (AIP-122). The service is named once, on
// the request and the response.
message Scope {
  // Exactly one arm is set.
  oneof target {
    // The tagged service root.
    ServiceRoot service_root = 1;

    // A relative resource name, such as "companies/A/teams/B".
    string resource = 2 [(google.api.resource_reference) = {
      type: "*"
    }];

    // A relative prefix ending in a collection literal, such as
    // "companies/A/teams". Claim scopes and holes only; never an anchor.
    string collection_prefix = 3;
  }
}

// The view a client last accepted. It binds only inside the authority
// and epoch it names.
message ViewFloor {
  // The revision_authority of the accepted view.
  string revision_authority = 1 [(google.api.field_behavior) = REQUIRED];

  // The revision_epoch of the accepted view.
  string revision_epoch = 2 [(google.api.field_behavior) = REQUIRED];

  // The policy_revision of the accepted view.
  string policy_revision = 3 [(google.api.field_behavior) = REQUIRED];
}

// A set of permission keys shared by the claims that reference it.
message KeySet {
  // Starts at 1. 0 is never a valid id.
  int32 id = 1;

  // Sorted, without duplicates.
  repeated string keys = 2;
}

// The claims for one anchor.
message PermissionContext {
  // Canonical. A context is identified by this anchor.
  Scope anchor = 1;

  // What the caller holds at or below the anchor.
  repeated Claim claims = 2;

  // Claims below this anchor were withheld for budget. Query narrower
  // anchors; the absence of a claim is not a denial.
  bool descendants_omitted = 3;
}

// A statement about a set of keys over a region: a scope minus holes.
message Claim {
  // At or below the context's anchor.
  Scope scope = 1;

  // KeySet.id. The claim applies to every key in that set.
  int32 key_set = 2;

  // What a claim asserts. Values may be added; a client discards a
  // context that carries a kind it does not know.
  enum Kind {
    // Invalid.
    KIND_UNSPECIFIED = 0;

    // Proven allow at every in-domain point of the region.
    ALLOW = 1;

    // Proven denial at every in-domain point of the region.
    DENY = 2;

    // An unresolved predicate. Asserts no decision.
    CONDITIONAL = 3;
  }

  // Grant-shaped profile: ALLOW only.
  Kind kind = 3;

  // Strict descendants of scope. Empty in the grant-shaped profile.
  repeated Scope holes = 4;
}

// How much a context may carry. Values may be added; a client rejects
// a view whose profile it does not know.
enum Profile {
  // Treated as PROFILE_GRANT_SHAPED in a request. Invalid in a response.
  PROFILE_UNSPECIFIED = 0;

  // Hole-free ALLOW claims only.
  PROFILE_GRANT_SHAPED = 1;

  // Adds holes, DENY and CONDITIONAL.
  PROFILE_SCOPED_CLAIMS = 2;
}

Anchors. An anchor is the service root or a resource name. A collection prefix is rejected with INVALID_ARGUMENT, and so is a root written as a string such as //svc/: the root is carried only as the service_root arm, and a resource name only as the resource arm. Exact duplicates in the request as submitted, compared by value (the same arm with the same string), are rejected with INVALID_ARGUMENT before anything else is examined, which reveals nothing. The server then resolves aliases. An alias resolves for a caller only if the caller is allowed to know what it names: it is the caller's own, such as users/me, or the caller could read the resource it names. An anchor that does not resolve is omitted, with no per-anchor error and no placeholder, so the response is the same whether an alias is unknown or names something hidden. Anchors that resolve to one canonical name yield one context. A context is identified by its canonical anchor, and a client that asked through an alias finds it by the canonical names the API returns.

A canonical name needs no visibility check. A context is computed from the rules that apply to the caller and not from stored rows, so the context for a name at which the caller holds nothing is the same whether or not anything exists there. It may have zero claims.

Claims. A claim's scope and holes are validated against the service's pattern trie, not with generated resource-name parsers, because a collection prefix is not a resource name. A scope must lie at or below the context's anchor and be a prefix of at least one binding pattern of every key in the claim's set; a hole must be a strict descendant of its claim's scope. A claim that references a key set missing from the response, an unset arm, or an unknown or unspecified kind invalidates its whole context (§4.4). A key that the client's own descriptors do not define is skipped, not treated as corruption. It can appear only when the contract versions differ, and such a view is not folded at all (§3.7). Unknown or incompatible data MUST NOT produce an allow.

The root anchor. A query at the service root returns the caller's claims at every scope where they hold a grant, which is how a client discovers where it can act (§3.3). A server MAY withhold claims below any anchor for budget and sets descendants_omitted; the client then queries narrower anchors. Kubernetes reports an incomplete rules review in the same way [16].

Wire compatibility. These messages replace the draft messages of earlier revisions of this report, whose field numbers they do not preserve. A deployment that shipped an earlier draft publishes this contract under a new package version and keeps the retired tags and names reserved in the old one; reservations alone cannot repair a repurposed tag.

4.2 Descriptor Interpretation Rules

The interpretation of a descriptor closure is normative: two conforming interpreters MUST derive the same result from the same descriptors. A service may cache that result in any form, including a JSON catalog served to browsers that cannot run gRPC reflection. Such a cache carries no authorization fact of its own, and it is valid only if it equals the interpretation. The rules are:

  1. Disposition. In a service whose option sets required, every RPC carries exactly one of the three forms of MethodAuthz, and every served RPC defined in an imported proto is listed in imported_methods. Where required is not set, an RPC without a declaration is outside this contract: the service enforces it by other means and a client defers to the server for it. A handler_policy names an authoritative implementation registered by the service, and covers intentionally public, authenticated-self and exempt methods as well as anything that cannot be decomposed into independent requirements. item_filter and partial_success accompany requirements only.
  2. Standard methods. standard is valid only on the AIP standard or batch method of a resource: the method's name is the standard verb followed by the resource's type name, or by its plural for List and batch methods, and its request has the shape AIP-131 through AIP-135 or AIP-231 through AIP-235 gives it [26] [9]. A method named GetAccessPolicy that takes a team's name is a custom method, because the name after the verb is not the resource's, and AIP-136 advises against a standard verb in a custom method's name. standard derives one requirement, as tabulated below.
  3. Target. When a requirement's target is omitted the target is the request's name field; otherwise its parent field; otherwise the name field of the first singular message field, in declaration order, whose message carries google.api.resource. Batch methods bind every item: names[], or requests[] followed by the standard path. A BatchCreate item that omits its parent takes the request's top-level parent, as AIP-233 allows, unless that parent is a wildcard. A path ends at a singular string after expanding at most one repeated field. An absent, empty, malformed or non-matching value binds no target, and a request with an unbound requirement is denied. A requirement is never satisfied by having zero targets.
  4. Resource type. The target field's google.api.resource_reference supplies it: type names the resource, and child_type names the type whose parent the field holds [3]. A resource message's own name field supplies its type. A top-level List takes the type of the response's repeated resource field, and a top-level Create the type of the resource in its request. Where none applies, resource_type is stated. A root-bound requirement with no type has the reserved service type.
  5. Binding patterns. A requirement on a resource binds to that type's patterns. A requirement on a parent binds to each pattern with its final collection and ID removed, or its final literal removed for an AIP-156 singleton [6]; the parent of a top-level pattern is the service root. A key required by several methods binds to the union of their patterns.
  6. Key. The permission key is the resource type's plural, a dot, and the operation: widgets.get. AIP-123 defines the form of plural and AIP-156 requires it for singletons [3] [6]; this specification requires it on every resource type a declaration refers to. The reserved service type has the stem service. Operation names are lower camel case. An item_filter names an operation on the resource type of the method's first requirement.
  7. Class. A standard method's class is fixed by its kind. Every other requirement states its access_class; an unspecified or unknown class is rejected. All requirements that share a key share its resource type, class and explicit_grant_only marker.
  8. Conditional requirements. A requirement with condition applies only to requests in which the named bool field is true. A standard Update whose request declares allow_missing derives one automatically: create, on the parent of the bound name, when allow_missing is true (§4.3). In a BatchUpdate the condition is read per item, so create is required only on the parents of the items that ask for it. A field hoisted to the batch level, which AIP-233 and AIP-234 allow, counts as set on every item.
  9. Effect. A method is read-only if every requirement it declares or derives is READ, conditional ones included, or if it sets idempotency_level = NO_SIDE_EFFECTS. Otherwise it is destructive if any requirement is DELETE, and mutating if none is.
  10. Partial success. A synchronous method is atomic. An Operation-returning batch method whose request declares return_partial_success is partial when that field is true; one whose metadata declares failed_requests with no request flag is always partial [9].
  11. Field guards. The fields a request writes are computed from the request. For an Update, an omitted mask is the populated fields, * is every field, an explicit mask is its paths, and with allow_missing true the populated fields are added. A mask that is present with no paths writes nothing, which AIP-134 advises (should); a service that treats it as omitted computes its guards that way. For a Create, the written fields are the populated ones. Output-only fields are removed [30]. A guard applies when a written path names the guarded field, a path inside it, or a message that contains it, and it adds the guard's operation as a requirement on the same target as the write. An implementation that cannot determine the written fields applies every guard.
  12. Contract version. contract_version is the SHA-256 digest, in lowercase hexadecimal, of the interpretation serialized as canonical JSON (RFC 8785 [32]) in the form shown below. It is not a hash of descriptor bytes, whose field order and unrelated options would change it. It covers everything a fold reads and nothing else, so two interpreters agree exactly when they would fold alike. The reference model compares the canonical form directly and leaves the digest to implementations.

Order of Checks and the Error Status

A service checks authorization before validating a request (AIP-211, must) and before learning whether the resource or its parent exists (AIP-193, must) [8] [27]. It parses only enough of the request to bind the declared targets. A requirement whose target cannot be bound has no scope to authorize, and the request is denied.

A denial returns PERMISSION_DENIED. Following AIP-211, the message reads Permission '{permission}' denied on resource '{resource}' (or it might not exist). with the permission key and the name exactly as the caller supplied it. AIP-193 requires an ErrorInfo on every error and requires every dynamic part of the message to appear in its metadata. Disclosure rules therefore cover the whole status: code, message, reason, domain, metadata and any other detail. Cases that must be indistinguishable (an absent row and a hidden row; a hidden duplicate and any other denial; an alias that is unknown and one whose target the caller may not see) MUST produce the same status in every field. Echo only values the caller supplied, never a resolved canonical name, an alias target, an owning parent or a policy identifier.

The same checks apply to a request with validate_only set: AIP-163 requires permission checks on a dry run [28]. A page token continues a query; AIP-158 forbids it from carrying any authorization, so every page is authorized again.

Missing Resources

Existence and authorization are determined in one consistent view. For a resource that does not exist:

  • If the caller's grants already decide the request for that name, the decision stands: an allow yields NOT_FOUND, a denial yields PERMISSION_DENIED.
  • If the decision cannot be made only because the row is absent, for example because it depends on the row's attributes, the service checks the List permission on the parent. This is AIP-211's "authorization to read children on the parent". If it is allowed the status is NOT_FOUND; otherwise PERMISSION_DENIED.

The List permission qualifies because a holder could list the collection and see that the child is absent. The check does not recurse: if the parent's decision is not determinable either, the status is PERMISSION_DENIED. For a top-level resource the parent is the service root. A parent allow never overrides a denial on a resource that exists, and an absent or unbindable request field is not an absent row.

List and Search

AIP-132 says a List should return the same results to any user permitted to list the collection, and that Search methods are more relaxed [26]. This specification requires it. A List is authorized by one check, the list key on the parent, and then returns the whole collection, with the same total_size and page tokens for every caller.

Two consequences should be understood before roles are designed:

  • The List permission discloses every child. AIP-132 says a List should return fully populated resources, so holding list on a parent is at least as revealing as holding get on each child. A forbid on get at one child does not hide that child from someone who can list its parent. Authoring tools SHOULD warn when such a forbid is written.
  • Existence cannot be hidden from siblings inside one List collection. A caller who must see only some children is given a Search method instead of the List permission, or the confidential children are placed under a different parent.

A Search method is a custom collection fetch method (AIP-136), for example GET /v1/{parent=companies/*/teams/*}/widgets:search. It declares its own operation and an item_filter, the operation every returned item must pass. The service applies the filter in the query or by an authoritative bulk check of candidates, and its counts, page sizes and tokens reveal nothing about rejected items. A Search with a wildcard parent applies its own key per parent as a filter; a caller who holds it nowhere receives an empty result, which is what a caller with no accessible items receives. Nothing universal is required of such a call, so a client does not fold it and leaves the answer to the server (§4.4).

Wildcards

AIP-159 lets a List accept - for a parent ID and says nothing about authorization [7]. A wildcard parent names a region, not a resource. Because this specification makes a List return the same results to every permitted caller, a wildcard List is authorized only if the list key holds for every potential parent in the region: a universal statement of exactly the kind a context makes. In the grant model that means a permit at or above the region's fixed prefix that no forbid below it interrupts. A caller who holds the key in only some parents lists those parents one at a time or uses Search.

The rule has two useful properties. No extra permission is needed to guard wildcard invocation, so there is nothing to bind when the wildcard is not the last segment or when several segments are wildcards. And a client can evaluate it locally: a wildcard List folds ALLOW when one ALLOW claim contains every name the wildcard matches, and DENY when a DENY claim contains at least one of them. For a key that may carry private rules the check is refused above the privacy boundary in every case (§3.6).

- is accepted only as the whole ID segment of a variable the declaration lists, results carry canonical names with the real parent IDs, and an item that omits its parent never inherits a wildcard top-level parent. AIP-217's unreachable field reports parents that are temporarily unavailable [29]. Under the rule above every parent in the region is one whose collection the caller may list, so naming an unreachable one discloses nothing new; this specification attaches no authorization meaning to that field.

AIP-159 permits a wildcard on Get only where IDs are unique across parents. The service resolves the name first and then applies the Get rule to the resolved resource. No match, a match the caller may not see, and a match the caller is denied all return the same PERMISSION_DENIED; NOT_FOUND is returned for no match only to a caller who holds the list key over the whole region, and never for a key that may carry private rules there.

Name Collisions

Any method that can make a name collide with an existing resource follows one rule: Create with a client-assigned ID, Move or Rename to a destination, each item of a BatchCreate, and an Update that creates. The service first authorizes the operation's own requirements. If the name is taken, it then checks, in the same consistent view, whether the caller can see the existing resource: get on it, or list on its parent. It returns ALREADY_EXISTS only if that check allows, and PERMISSION_DENIED otherwise, with the same status as any other denial of that method.

AIP-133 requires this (must). AIP-211 advises that a method should check only its own permissions when choosing an error (should not). The two conflict on exactly this case; the requirement in AIP-133 is the more specific and the stronger, so it governs, and the visibility check is confined to this one decision.

The rule leaves one inference open. A caller who is otherwise allowed to create under a parent and is refused for one particular ID can conclude that something it cannot see holds that name. The status is identical to every other denial of the method, so nothing more is disclosed, and no permission hint predicts the refusal (§1.1). A service that cannot accept the inference assigns IDs on the server for that resource.

Update, Upsert and Delete

Upsert. AIP-134 says the caller must hold the update permission to call Update even with allow_missing set, and suggests conditions to prevent creation. This specification's rule is stricter and is a local policy: a request with allow_missing = true additionally requires create on the parent. It is decided from the request alone. A caller with only the update permission sends allow_missing = false and receives NOT_FOUND for a missing resource, as AIP-134 specifies.

Delete. AIP-135's allow_missing on Delete makes a missing resource a successful no-op and needs no extra requirement. A cascading delete (force) requires at least delete on the named resource; a service that also requires delete on each child type states that as a named handler policy, since it is a universal requirement over the subtree. FAILED_PRECONDITION for children present and ABORTED for an etag mismatch are returned only to an authorized caller.

Batch Methods

A batch method's requirement is the singular method's requirement applied to each item. AIP-231 explains that the top-level parent field exists "to permit a single permissions check" [9]. In this model that check is a universal one: if the item's key holds over the whole stated parent, every item under it is authorized at once. The rules are:

  1. Bind every item that can be bound and authorize it, by the universal check on the parent or item by item. For a key that may carry private rules below the parent the universal check is refused (§3.6), and its items are authorized one by one.
  2. If any bound item is not authorized, a synchronous or atomic batch returns PERMISSION_DENIED with no detail identifying the item. No validation result is revealed first.
  3. An item that cannot be bound, and an empty batch, have no scope to authorize. INVALID_ARGUMENT is returned for them only when the universal check on the parent passes; otherwise PERMISSION_DENIED.
  4. Only then is the request validated: a mismatch between an item and the top-level parent (which AIP-231 to AIP-235 require to fail), duplicate items and malformed fields return INVALID_ARGUMENT.
  5. Atomic mutations are fully authorized before any partial commit is visible.

Partial success. Synchronous batch methods are atomic; an Operation-returning one may report partial success, and an existing API adopts it through a return_partial_success request field (AIP-233 to AIP-235). The semantics of one request are therefore read from that request. In a partial batch, a requirement that is not tied to an item is operation-level: if it fails, the request is denied and no item runs. Each item's failure is reported at its request index in failed_requests with the status the singular method would return, and if every item fails the operation's error is ABORTED.

Long-Running Operations

AIP-151 defines the shape of an operation and requires the standard Operations service; it does not define who may read an operation. A service lists each Operations method it serves in imported_methods with a handler policy, typically one that binds an operation to its creator and rechecks the originating requirement on GetOperation and WaitOperation, and one that makes ListOperations return only operations the caller may get. Methods it does not serve are not listed.

4.4 Server-Side and Client-Side Algorithms

The handler and the context endpoint are two uses of one resolver, and the client fold mirrors the handler.

Server: authorizing one request (pseudocode)
authorize(ctx, method, request):
  m = interpretation[method]                    # static, from descriptors (§4.2)
  if m is a handler policy: return policy[m.name](ctx, request)
  grants = effective_grants(ctx)                # the only step that varies by caller kind
  reqs = the requirements of m whose condition is unset or true in the request (per item in a batch)
       + the guard of every guarded field the request writes (§4.2, rule 11)
  residuals = []
  for r in reqs:
    targets = bind(r, request)                  # canonical names; aliases resolved first
    if targets is empty or one cannot be bound: return PERMISSION_DENIED   # never an empty conjunction
    for t in targets:
      if t has a wildcard:                      # "-" only for a variable the declaration lists
        if m declares item_filter: continue     # Search: the handler filters per parent
        if r targets a resource:                # wildcard Get: the handler resolves, then decides
          residuals.add((r, t, resolve)); continue
        d = ALLOW if decide() allows every name t matches, else DENY   # always DENY for a nonprojecting key
      else:
        d = decide(grants, r, t)                # ALLOW | DENY | RESIDUAL(predicates)
      if d is DENY: return PERMISSION_DENIED
      if d is RESIDUAL: residuals.add((r, t, d.predicates))
  return PROCEED(residuals)                     # the handler resolves them at its commit boundary
Server: answering QueryPermissionContexts (pseudocode)
query_permission_contexts(ctx, request):
  authenticate; pin one view v of policy and of the descriptor interpretation
  if request.min_view names v's authority and epoch and a revision newer than v: return UNAVAILABLE
  reject a collection-prefix anchor or an exact duplicate: INVALID_ARGUMENT
  grants  = effective_grants(ctx) at v          # same resolver as authorize()
  anchors = resolve aliases; drop those that do not resolve for this caller; merge equal names
  for a in anchors:
    for k in keys that can bind at or below a:  # pattern trie (§3.4)
      if k is nonprojecting at a: continue      # declared private-capable (§3.6)
      partition a at the scopes of the rules for k; classify each cell; merge equal neighbours
      emit ALLOW, DENY or CONDITIONAL per cell, or nothing
  if profile is grant-shaped: keep only ALLOW claims that have no holes
  merge claims with identical (scope, kind, holes) into one claim over a shared key set
  stamp contract_version, subject_context_id, view metadata, remaining_ttl = min(proof, session)
Client: folding a view for one operation (pseudocode)
offer(method, request):
  m = interpretation[method]
  if m is undeclared, a handler policy or cannot be interpreted: return DEFER
  if m.effect is not read-only and the credential is read-only: return HIDE   # static fact
  reqs = the requirements that apply to this request, with field guards, as on the server
  results = []
  for r in reqs:
    targets = bind(r, request)
    if invalid or empty: return DEFER
    for t in targets:
      if t has a wildcard and (m declares item_filter or r targets a resource): return DEFER
      view = newest accepted view, computed from this same interpretation,
             that has a valid context whose anchor covers t
      results.add((verdict(view, r.key, t), view.id))      # the universal verdict for a wildcard
  if any result is DENY: return DENY                       # denial always blocks
  if every result is ALLOW and all come from one view: return ALLOW
  return DEFER                                             # CONDITIONAL or UNLOADED

Accepting a view. A client keeps one namespace at a time: service, revision authority, epoch, contract version and subject context. It accepts a response only if every one of those fields and the policy revision is present, remaining_ttl is positive, and the profile is known and not above the one it requested. It folds a view only if the view's contract version equals the hash of its own interpretation; until it has refreshed its descriptors or the view, every fold is UNLOADED (§3.7). On a verified change of subject or namespace it evicts everything and ignores replies still in flight. Within a namespace it rejects a lower generation, or relies on the floor it sent (§3.8), and it does not adopt a changed subject from a delayed response. It drops the floor when the authority or the epoch changes.

Validating a context. Before matching, each context is validated as a whole, and a failing context is discarded entirely, every claim for every key: an unknown or unspecified kind, or a reference to a key set the response does not contain; an unset scope arm, or a collection prefix used as an anchor; a scope outside the anchor or outside the key's binding hierarchy; a hole that is malformed or not a strict descendant of its scope; a hole or a non-ALLOW claim in the grant-shaped profile; or an overlap between two claims of different kinds for one key. One forgotten hole shows that the producer's other claims cannot be trusted, so nothing from that context is used, including for targets outside the overlap. Overlap between claims of the same kind is redundant, not corrupt, and a key the client's descriptors do not define is skipped (§3.7).

Evaluating a target. Each target is evaluated against a single view: the most recently accepted one that has a valid context whose anchor covers the target. Claims from different views are never combined. Within that view a claim applies if its key set contains the key, its scope is a segment prefix of the target and no hole is; each hole removes its entire subtree. If ALLOW and DENY both apply the producer is in conflict: the result is UNLOADED, neither is reported as verified, and the client does not loop on refetching. Otherwise ALLOW or DENY wins over CONDITIONAL, whatever the depths of their scopes. A wildcard target is evaluated in the same way, against a context that covers the resource name above its first wildcard: ALLOW needs one ALLOW claim that contains every name the wildcard matches, and DENY needs a DENY claim that contains at least one.

Folding an operation. A denial for any required target blocks the hint, even when the targets were evaluated in different views; a conservative hint is harmless. An allow needs every requirement to bind at least one target and every target to be ALLOW in one and the same view. A batch folds as one unit when atomic. When partial, each item is folded together with the operation-level requirements, and results keep their request indices instead of collapsing to one Boolean.

Listing what is usable. A menu or a tool list asks the inverse question: which operations apply within this scope? It is the same fold run over every method. A method is listed for a scope when each of its unconditional requirements can bind at or below that scope and its key is ALLOW over the scope. Asked at the service root with no scope chosen, the answer is every method whose keys appear in some ALLOW claim, together with the scopes of those claims. In a policy of permits only, a method missing from that answer is usable nowhere. With forbids or conditions it is only unproven at that anchor (§3.3).

4.5 End-to-End Walkthrough and Executable Checks

Alice holds two grants: viewer at companies/A and widget-writer at companies/A/teams/B. Team C is confidential, so a forbid on reads is attached there. The following is what the reference model produces.

  1. Her client starts with no subject and queries the service root in the grant-shaped profile. The view contains two claims: ALLOW at companies/A for companies.get and teams.list, and ALLOW at companies/A/teams/B for widgets.create and widgets.update. The client now knows the two scopes where Alice can act. teams.create appears in no claim, so the client has no evidence for "New team" and does not offer it.
  2. The viewer's other read keys are missing from the claim at A. The forbid at Team C makes "reads are allowed everywhere in A" false, and the profile cannot express an exception, so those keys are omitted. Nothing false was said.
  3. She opens Team B. The client queries that anchor and receives one claim there carrying teams.get, settings.get, widgets.get, widgets.list, widgets.search, widgets.count, widgets.create and widgets.update. "New widget" and "Edit" are offered; "Delete" is not, because widgets.delete is absent.
  4. With the scoped-claims profile one query at A is enough. The same read keys arrive as ALLOW over companies/A with the hole companies/A/teams/C, plus DENY at C. The client folds ALLOW for Team B and DENY for Team C without a second query, and the write keys arrive as DENY over A outside Team B.
  5. A wildcard List across the teams of A is not offered. widgets.list does not hold over the whole region because of Team C, so the fold is not ALLOW, and the client offers SearchWidgets instead, which the server filters for her.
  6. The confidential team is still listed. The forbid at Team C does not reach teams.list, which binds to the company, so ListTeams on A returns C to Alice. If C's existence must be hidden from her, she is not given teams.list on A (§4.3).
  7. An upsert needs more. UpdateWidget with allow_missing = true requires widgets.update on the widget and widgets.create on Team B. Alice holds both. A caller with only UPDATE would be refused before any row is read.
  8. Her writer grant is revoked. The server denies the next update as soon as it observes the new revision. Her client may show "Edit" until its view expires or the denial triggers a refresh; the stale view confers nothing.

The executable checks exercise a finite reference model of this specification, not a production enforcement point or a proof about arbitrary policies. They run in the HTML edition on load or with the button, and the same model drives the simulator (§3.9) and the explorer (§4.1). Each check is tagged with the area it covers. Checks marked "Pinned" record behavior that was once questioned in review and found correct, so that it is not changed by mistake. The Markdown export lists every check with its result.


        


        
        

          
Part V. Limits, Objections & Verified Bibliography


          
5.1 Steel-Manned Objections & Architectural Boundaries

          
A specification should say where it stops. Seven objections mark the boundary of this one.

          
    
            
  • Objection 1 — Exclusion explosion under high-fanout denies. A hole removes a positive proof; a DENY claim proves a refusal. If a server's budget cannot represent an allow together with all the holes it needs, it omits the allow. Without other evidence the client folds UNLOADED, never a guess. The grant-shaped profile behaves this way by construction.
    • 
            
  • Objection 2 — Non-hierarchical sharing graphs. In collaboration products where access is attached to each document through sharing links instead of parent folders, almost nothing is uniform across a folder. Boundary: do not use scope-level contexts as the primary model there. Use relationship-based checks (SpiceDB, OpenFGA) with bulk checks and resource lookups [10] [20], and keep contexts for the surrounding workspace chrome.
    • 
            
  • Objection 3 — Client and server can drift. Both sides interpret the same descriptors, every view names the interpretation it was computed from, and a client does not fold a view computed from a different one. What remains is the gap between a declaration and the handler behind it. Test declarations against handler behavior with allowed and denied requests, including wildcard Lists, upserts and partial batches. Anything that depends on stored state is a handler policy, which the client always defers.
    • 
            
  • Objection 4 — Contexts go stale after a revocation. A client keeps a view for its remaining_ttl, so a freshly revoked user may see an enabled action until the server refuses it. Mitigation: treat contexts strictly as presentation hints, and on PERMISSION_DENIED from any call evict and refresh the matching anchor. The server refuses immediately, and the hint is corrected at the next refresh.
    • 
            
  • Objection 5 — Class grants expand silently when an RPC is added. They would, without the capability diff. The build reports every key each role gains or loses, and operations that should never be picked up by a class are marked explicit-grant-only (§3.7).
    • 
            
  • Objection 6 — Derived identities tie permissions to the API surface. Renaming a resource's plural or an operation changes keys, and with them any role that names the operation. That is a policy change, and the capability diff reports it as one. Roles that select by class are unaffected. An organization that must keep a legacy vocabulary of permission names maps it to derived keys in server policy, where it is not a client's concern.
    • 
            
  • Objection 7 — Why not send roles to the frontend? A role name means nothing without its definition, exceptions are not part of any role, and exposing role structure couples every client to policy internals. Keys at scopes are the effect of the policy, which is all a frontend needs and all it should be able to rely on.
    •
