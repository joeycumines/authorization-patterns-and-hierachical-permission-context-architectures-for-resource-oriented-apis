Systems Architecture Monograph & Formal Engineering Reference

General Authorization Implementation Patterns & Hierarchical Permission-Context Architectures for Resource-Oriented APIs

A formal analysis of the (Actor, Action, Resource, Context) model, a comparative taxonomy of production authorization systems, and a specification for declaring authorization on AIP/gRPC methods, deciding it with one pure function over scoped grants, and projecting it soundly to user interfaces and agent tool hosts.

Target Paradigm: Google AIP Resource-Oriented APIs (gRPC / Protobuf) Status: Canonical Technical Reference (v1.6) Date: November 2026 Source: GitHub repository ↗

Executive Summary & Key Architectural Conclusions

Core Thesis

A frontend that offers an action the server then refuses has shown a false affordance. To avoid that, the frontend needs facts about each method that do not change at run time, such as what it requires, read from the API's protobuf descriptors, and a statement from the server about what the caller may do within a scope, such as a company or a team. When a role is given to someone at a scope, as "editor of Team B", and the role picks operations by resource type and access class, as "every read and update on widgets", the server can compute both its decision on a request and that statement from the same grants and descriptors. No list of permissions has to be maintained by hand. The statement only guides what the frontend shows; the server still decides every request.

Backend services check access one request at a time: may caller a perform action k on resource r, given the request's attributes c? User interfaces, API gateways, batch workflows and agent tool hosts ask a different question: what can this caller do across a whole scope, such as a company or a team? Answering that by asking about every resource costs one round trip, and one cache entry, per resource.

This report first formalizes the usual (Actor, Action, Resource, Context) model of access control, in which the context is the request's attributes, such as time or network, and catalogs nine production implementation patterns grounded in primary literature, including NIST RBAC [11], NIST ABAC [12], OASIS XACML [13], Google Zanzibar [10], AWS Cedar [14], Open Policy Agent [19], SpiceDB and OpenFGA [20], Kubernetes SelfSubjectRulesReview [16], Google Cloud TestIamPermissions [17], and Macaroons [15]. It then specifies an architecture for resource-oriented gRPC APIs that follow the Google API Improvement Proposals (AIPs), and reaches these conclusions:

  1. Declare requirements on methods and derive everything else. A permission is identified by a resource type and an operation, such as reading widgets. A standard method, such as GetWidget, needs one line of annotation: the AIPs already fix what a Get, List, Create, Update or Delete does, so its operation, its access class and the request field naming its target follow from which standard method it is and from its google.api.resource annotations. A permission exists because a method requires it; there is no other list to maintain (§3.2, §4.1, §4.2).
  2. Treat roles as grants at a scope that pick operations by resource type and access class. To decide a request, the server looks at the caller's grants attached at or above the target. To tell a frontend what the caller can do, it takes each grant and lists the permissions it gives to the methods that can act inside the grant's scope. Both use the same grants and the same method declarations, so the request handler and the endpoint that answers frontends share one resolver (§3.3).
  3. Adopt the smallest profile that fits the policy. The conformance profiles build on each other. The first uses the declarations alone. The second adds contexts that list, for each grant's scope, the permissions held there. The third also reports exceptions inside a scope, definite denials, and permissions that depend on something the context cannot resolve, such as who owns a widget. A context from a simpler profile is a valid context in the next, so an implementation can start small (§3.5, §3.6).
  4. Build the AIP rules into the model. AIP-132 says a List should return the same results to every caller permitted to list. This specification requires it, and puts per-caller filtering in a Search method. Then anyone allowed to list a team's widgets sees every widget in the team, so telling that caller a widget does not exist reveals nothing more. That makes the List permission the check that decides between NOT_FOUND and PERMISSION_DENIED for a missing widget. A List across all teams at once needs the List permission in every team it reads (§4.3).
  5. A client needs only the API's protobuf descriptors. Everything a client needs to read a permission context can be derived from them, by reflection or from a descriptor set. Roles, grants and handler code stay on the server (§3.1, §3.7).

This specification covers how a method declares what it requires, how the server decides a request from those declarations and the caller's grants, what the server may tell a client about the caller's permissions, and what the client may conclude from that. It also specifies what each response must include so that a client can tell whether the response is current and which declarations it was computed from.

It does not specify how clients pick up new declarations after a release, how often they refresh, how caches are arranged, or how a policy change is rolled out. Those are left to the implementation. Where one of them can make a frontend show the wrong thing, the specification describes the problem but does not prescribe a fix.

Part I. The Problem and the Formal Model

Section Takeaway

Enforcement evaluates a pointwise decision function D(a, k, r, c). A frontend needs a statement about a whole scope, which is a universal quantification over that function. A projection is sound if every claim it makes is true at the snapshot it names. Completeness is optional, and freshness is specified separately.

1.1 What a Frontend Needs: Avoiding False Affordances

The problem this architecture solves is narrow. A frontend shows a button, a menu entry or a tool, the user or agent invokes it, and the server answers PERMISSION_DENIED. That is a false affordance. The opposite error, hiding an action the caller could have taken, is a false hide. It costs the caller a capability and is the lesser of the two errors. Failures that are not about authorization (validation, preconditions, quota) are out of scope: nothing a permission context says can predict them. One refusal is out of scope even though it comes back as PERMISSION_DENIED. AIP-133 requires that status when a new resource's name collides with a resource the caller cannot see. Whether that happens depends on stored data, and a context that predicted it, by saying that creating w7 in Team B will be refused, would tell the caller that w7 exists (§4.3).

A frontend already knows which operations exist, because they are in the API's descriptors. What it lacks depends on what the action would apply to:

  • Nothing chosen yet. A navigation bar or a tool list is drawn before any resource is chosen. The question is existential: is there anywhere this caller could do this?
  • A scope. A page for one team asks whether "New widget" should be enabled. The question is universal within that scope: may the caller do this on everything here?
  • An item. A row action asks about one resource. The question is pointwise.

The frontend also consumes two different kinds of information, and they should not be confused. Static method facts need nothing chosen: what a method requires, which names it accepts, and whether it reads or changes anything. They decide how menus and tool lists are grouped and when to ask for confirmation. Evidence about the caller is tied to a scope: what the caller may do there. 1.2 The Authorization Decision Function

Authoritative enforcement is a function D(a, k, r, c) → {ALLOW, DENY} of a caller a, a permission key k, a concrete resource name r and the request's attributes c, such as time or network. A method does not need just one key: it lists requirements, each a key paired with the request field that names its target, and every one must hold (§3.2). R is every name the resource patterns allow, whether or not anything is stored under it: a decision about a widget that does not exist yet is still a decision.

At a fixed snapshot, evaluating policy can end in more than two ways: no rule applies, a permit, an explicit forbid, a condition that cannot be resolved, or an evaluation error. Throughout this report they combine as follows:

  • A proven forbid denies.
  • A forbid that could apply but whose condition is unresolved, or that might raise an error, means even an unconditional permit is not enough to allow.
  • Otherwise a proven permit is required. An unresolved or possibly erroring permit is not sufficient.

"Proven" includes proving that the relied-on policies cannot raise an evaluation error at any point the proof covers; a predicate the adapter cannot prove free of errors counts as possibly erroring. Cedar skips policies whose evaluation errors, including forbids, and reports them in its diagnostics [14], so an adapter that follows the rule above can be built on it; an adapter MUST declare and test its error policy. For authoritative decisions the recommended choice is to deny when a forbid that could apply raises an error. That is stricter than native Cedar and can reduce availability. Projection MUST follow the rule above whichever choice the authority makes. A context then says DENY only for a proven forbid or where no permit could apply, and says ALLOW only for a proven permit where no forbid could apply, even through an error. An authority of either kind denies in the first two cases and allows in the last, so the context is sound against both; the authority's choice only changes how often the context has nothing to say. A forbid that is proven in this sense, with no unresolved predicate, is called final in the rest of this report. Forbids override permits, so nothing reverses a final forbid.

It follows that a permission context is advisory: it is true at the snapshot it names, and it is never a credential; the server never accepts a client's projection as proof, and an audit trail records what the server decided, never what a context said. It also follows that the server itself splits the work. An interceptor authenticates, binds targets from the request and evaluates everything that depends only on the request and the caller's grants. A handler or data layer makes the checks that depend on stored state and owns the check-and-commit boundary. A commit-time revision check is sufficient only if it covers every fact the decision relied on.

1.3 Pointwise Evaluation vs. Subtree Permission Projection

Pointwise evaluation answers one concrete question: "Can Alice execute widgets.update on companies/A/teams/B/widgets/w1 right now?" Permission projection fixes the caller and the request attributes (a, c) and an anchor r0, which is a resource name or the service root, and summarizes D(a, k, r, c) for every key k that a method can require at or below the anchor and every potential resource r ∈ Subtree(r0) = { r ∈ R | r0 ⪯ r }, where x ⪯ y means that x is y or one of its ancestors, as AIP resource names nest.

For each key only some names matter, the ones its requirements can target, called its binding domain: widgets.get targets widget names, never a team's name. A summary such as ALL, NONE or MIXED loses information, because MIXED does not say where the exceptions are. Listing the exceptions loses nothing, but only where every exception can be written as a scope and may be shown to the caller (§3.6).

1.4 Soundness, Completeness and Monotonicity

A claim is sound if it is true for the caller, the policy snapshot, the declarations and the request attributes it was computed for. A context need not be complete: what the server leaves out stays UNLOADED, and the frontend asks about a narrower scope or leaves the decision to the server. A context's time-to-live limits how long it is reused; it does not keep it current: a grant revoked a moment after the context was sent still shows until the context expires or is refreshed (§3.8).

Theorem 1.1. Fix the caller, the request attributes, the snapshot and the key, and let B be the key's binding domain (a different letter from the decision function D of §1.2). For any scope s, whether or not s is itself in B, let B(s) be the points of B at or below s. For x in B, let A(x) mean an unconditional allow at x: ALLOW in every case the evaluation could take, whatever values the unresolved facts have and whichever policies that might raise an error do so (§1.2). Let U(s) mean A(x) for every x in B(s); an ALLOW claim over s, which is sent only when B(s) is not empty, states exactly U(s). Call A downward-monotone when A(s) implies A(x) for all s ⪯ x in B. Then:

  1. A is downward-monotone if and only if A(x) = U(x) at every x in B.
  2. Suppose every rule for the key is an unconditional permit that cannot raise an error. Like every grant, each is attached to a resource name or the service root, never to a collection (§3.1), there are finitely many, and an ID segment can take unboundedly many values (§3.6). Then a permit attached at or above s proves U(s), for any scope s. Conversely, when U(s) holds and no permit is attached at or above s, every point of B(s) lies at or below a permit attached to a singleton descendant of s (AIP-156).

Read informally, part 1 says that "allowed at a point means allowed everywhere below it" and "a point's answer is also the answer for its whole subtree" are the same property. Part 2 says plain role grants have that property, and that the anchor is the only place a universal needs checking, with one exception. A grant on a singleton, such as a team's settings, makes settings.get universal under the team although nothing is granted at the team itself. That is why the grant walk of §3.3 reports such a grant at the singleton's own scope, where a client will look for it.

Proof of Theorem 1.1

Part 1. U(x) implies A(x) always, because x is in B(x). If A is downward-monotone, A(x) implies U(x), because every point of B(x) lies at or below x. Conversely, if A = U on B, then for s ⪯ x in B, A(s) gives U(s), which includes A(x).

Part 2. A permit applies at every descendant of its scope, so one at or above s allows all of B(s). For the converse, assume U(s) with no permit at or above s, and take x in B(s). If the path from s down to x crosses no ID segment, the permit that allows x extends s by literal segments alone, and as a grant's scope it is a resource name, so it is a singleton. Otherwise let i be the depth of the first ID segment crossed. The names that differ from x only at depth i are all in B(s), and finitely many permits name finitely many IDs, so one of those names is allowed only by a permit scoped above depth i. That scope extends s by literal segments alone and, being a grant's scope, is a resource name rather than a collection, so it is a singleton, and since the varied names agree with x above depth i, it is also an ancestor of x. ∎

In practice this means:

  • A claim that something is allowed everywhere in a scope is safe for any policy, monotone or not, as long as it is true: an ALLOW claim over s states exactly U(s). The server need not report every individual allow, so a context can be incomplete, and an empty one is never wrong.
  • Additive scoped grants are downward-monotone, and by part 2 checking the grants at or above the anchor decides the universal, apart from a grant attached directly to an AIP-156 singleton below it, which §3.3 reports at the singleton's own scope. That is why the grant-shaped profile is cheap (§3.3). Forbids and conditions on descendants break monotonicity and are what the scoped-claim profile exists for (§3.6).
  • The universal and the pointwise answer coincide trivially only where B(s) = {s}: the anchor is itself a domain point with nothing of the domain below it, such as a widget for a key bound only to the widget pattern. At a team, widgets.get covers unboundedly many widgets, and the universal has to be proven. A key with patterns at several depths has domain points below an in-domain anchor too: with widgets under both companies and teams, widgets.create binds to companies and to teams, and under an arbitrary policy being allowed to create directly under a company says nothing about its teams.

Part II. General Authorization Implementation Patterns Taxonomy

Section Takeaway

No single authorization pattern dominates all workloads. Production architectures compose a policy representation model (RBAC, ReBAC, ABAC, Capabilities) with an evaluation topology (pointwise PEP/PDP, bulk check, subtree projection, or partial-evaluation data filtering) matched to the workload's resource graph, latency budget, and revocation strictness.

2.1 Catalog of Nine Production Implementation Patterns

1. Centralized Enforcement (PEP / PDP / PIP / PAP Architecture). Standardized by OASIS XACML 3.0 [13] and NIST SP 800-162 [12], this pattern decouples request interception (Policy Enforcement Point) from decision evaluation (Policy Decision Point) and attribute retrieval (Policy Information Point). It provides uniform auditing and language-agnostic policy governance across microservices (e.g., Envoy ext_authz [22] calling OPA or Cedar). Its primary trade-off is network-hop latency and availability coupling on the critical request path, mitigated by sidecar/in-process PDP deployment.

2. Resource-hierarchy policy inheritance with RBAC role bundles. NIST hierarchical RBAC [11] describes role hierarchies, not resource trees. Services such as Google Cloud IAM [17] and Azure RBAC [24] attach policy or role assignments to resource hierarchy nodes. Allow grants are additive: an allow attached to a node applies to everything below it, and adding one never takes access away; in Google Cloud, only a separate deny policy does that [17]. An inherited allow holds below a node only where its conditions do: a CEL condition can be true at a folder and false for a resource inside it, with no deny policy involved. Google Cloud IAM policy changes typically propagate in about two minutes, but can take seven minutes or more.

3. Resource-Level ACLs & Relationship-Based Access Control (ReBAC). Pioneered at global scale by Google Zanzibar [10] and implemented in open-source engines like AuthZed SpiceDB and OpenFGA [20], ReBAC models authorization as graph reachability over stored relation tuples (object#relation@user) with userset rewrite rules (union, intersection, exclusion, tuple-to-userset). Zanzibar achieves <10 ms p95 latency across trillions of tuples and prevents the "new enemy" stale-ACL problem using opaque causal consistency tokens called zookies (called ZedToken in SpiceDB) [10] [20]. ReBAC excels at fine-grained, non-hierarchical sharing, but graph traversal makes high-fanout list filtering and coarse prefix projection computationally expensive unless backed by materialized permission views (e.g., AuthZed Materialize) [20].

4. Attribute-Based & Policy-Based Access Control (ABAC / PBAC). Formalized by NIST SP 800-162 [12] and realized in Open Policy Agent (Rego) [19], Amazon Verified Permissions (Cedar) [25] [14], and Google Cloud IAM Conditions (CEL) [17], ABAC evaluates boolean predicates over subject, resource, action, and environment attributes (e.g., time-of-day, data classification, resource ownership). Cedar specifically restricts language expressiveness (no unbounded loops, explicit permit/forbid semantics) to guarantee termination and support SMT-backed static policy analysis [14]; these guarantees concern termination and analysis, not a latency bound. ABAC eliminates role explosion, but attribute volatility lowers cacheability and complicates static permission projection.

5. Scoped Permission Projection & Self-Review APIs. Used directly to drive permission-aware UIs and CLIs without O(N) pointwise checks. Real-world precedents include Kubernetes SelfSubjectRulesReview (authorization.k8s.io/v1, which enumerates a caller's effective resourceRules within a namespace and explicitly returns an incomplete boolean when an external authorizer cannot project rules) [16], Google Cloud IAMPolicy.TestIamPermissions (which intersects a caller-supplied candidate permission set against effective permissions on a resource) [17], and AWS IAM SimulatePrincipalPolicy [18]. Kubernetes warns about incomplete results and confused-deputy risks; Google Cloud warns that TestIamPermissions is for permission-aware tools and may fail open. Neither substitutes for authoritative enforcement [16] [17].

6. Batch & Bulk Authorization Evaluation. Bulk checks amortize RPC overhead. SpiceDB CheckBulkPermissions supports ZedToken consistency controls; OpenFGA BatchCheck provides correlation IDs and MINIMIZE_LATENCY / HIGHER_CONSISTENCY preferences, not a snapshot token or a shared-snapshot guarantee [20].

7. Authorization-Aware Search & Data Filtering (Partial Evaluation). AIP-132 says a standard List should return the same results to every caller permitted to list [26], so filtering results per caller belongs to a Search-style custom method (§4.3). There, authorize the invocation and the visibility of each item separately. A parent scope alone cannot exclude forbidden descendants. Use a query predicate equivalent to per-item authorization, or an authoritative bulk check of candidate rows; page sizes, counts and tokens MUST NOT expose rejected candidates. OPA's /v1/compile partially evaluates a policy and returns the conditions that remain as a Rego syntax tree, and /v1/compile/{path} turns a named rule into a SQL or UCAST filter [19].

8. Delegated Capability Tokens & Attenuation. Macaroons [15] can be attenuated by appending chained HMAC caveats. Verification is O(number of caveats) plus the cost of evaluating those caveats. Short TTLs and discharge caveats can constrain offline use. Biscuit [23] offers offline attenuation with public-key signatures and Datalog-based policies.

9. Field-Level & Long-Running Operation (LRO) Authorization. AIP-161 field masks select fields [30]; a separate policy authorizes them (§3.2). AIP-151 [5] defines the operation shape, not permissions. A typical local policy binds an operation to its creator and rechecks the originating permission on GetOperation and WaitOperation, and ListOperations returns only operations the caller may get. Declare these as named handler policies for the imported Operations methods the service actually serves (§4.1).

Part III. The Architecture: Declarations, Grants, Decisions and Contexts

Section Takeaway

Methods declare what they require. Policy grants access by resource type and access class at a scope. One pure function decides a request from those two inputs, and the same data, traversed from the grant instead of from the target, produces the permission context a frontend folds. Everything else in this part is a consequence: how names form a hierarchy, which profile to adopt, how exceptions and private rules are handled, how the contract evolves, and how contexts are cached.

3.1 The Pieces and Who Owns Them

Each piece of the architecture has one owner, and the aim is that no fact is written down twice.

  1. Declarations. Each RPC states what it requires, as a protobuf method option. Combined with the resource annotations an AIP-style API already carries, this fixes for every method its resource type, operation, access class, target and effect (§3.2).
  2. Grants. Server policy records which principals hold which roles at which scopes, and what each role selects. Grants are runtime data and never appear in descriptors (§3.3).
  3. The decision. For each request the service binds the declared targets and checks the caller's grants. Checks that depend on stored state run in the handler (§4.4).
  4. The context. On request, the service tells a caller which permission keys it holds within the scopes it asks about. This is the projection (§3.5, §3.6).
  5. The fold. The client combines a context with the declarations to decide what to offer. It never enforces (§4.4).

Methods never name roles, and roles never name methods. They are related only through a small shared vocabulary: a resource type with an access class, or a resource type with one named operation. Adding an RPC changes the descriptor only. Roles that select its class cover it in the next decision and in every context issued afterwards, after one review step in which someone confirms that those roles should cover it (§3.7).

3.2 Granularity: Identity, Access Class and Effect

How much should a method say about authorization? Too little, and distinct operations collapse into one check. The third column is the design. It keeps apart what a single facet mixes up: which operation a method performs, which class of operation that is, and whether calling the method changes anything.

Identity

A permission is identified by its resource type and its operation. Its display form, the permission key, is the type's plural and the operation: books.get, books.search, books.expunge. Because the key is derived, two methods that perform the same operation share it without coordination (GetBook and BatchGetBooks both require books.get), and there are no hand-spelled names whose conventions someone has to enforce. A key is unique within one service; another service can have its own widgets.get. A client that works with several services keeps their declarations and contexts apart, which is easy because every response names its service.

Access class

Every requirement has exactly one class: READ, CREATE, UPDATE, DELETE, ADMIN or EXECUTE. A class is a selector over operations. A role that grants READ on Book covers books.get, books.list and books.search today and any READ operation added later. A standard method takes its class from which standard method it is: a Get reads, a Delete deletes. A custom method states it, because nothing else about a custom method is reliable enough to infer it from: AIP-136 lets a retrieval method use POST when its payload could exceed URL length limits [4]. EXECUTE exists so that custom mutations, such as publishing a document or running a job, are not classified as UPDATE and granted to every editor without anyone having decided so. No class implies another: ADMIN does not include DELETE, and UPDATE does not include CREATE.

Effect

Whether invoking a method changes state is a property of the method, and a frontend needs it before anything is chosen: to separate read tools from mutating ones, to decide when to ask for confirmation, and to hide mutations on a read-only credential. It is derived. A method whose requirements are all READ is read-only; one with a DELETE requirement is destructive; anything else is mutating. Requirements that apply only to some requests count, because the effect describes the method and not one call. Effect and class can differ, as the access-policy row shows, and such a method overrides the derived effect with protobuf's standard idempotency_level = NO_SIDE_EFFECTS option [21]. The override can only mark a method read-only when its requirements read or administer; the build rejects it beside a create, update, delete or execute requirement. A method decided by a named handler policy has no requirements to derive an effect from, so it is read-only only when it says so, with the same option or, for an imported method, the matching flag on its entry in imported_methods (§4.1). Otherwise its effect is unknown, and a frontend treats it as it would a destructive method: it asks before running it and keeps it from a read-only credential. A Move declared as delete at the source and create at the destination is destructive by this rule, so a frontend asks before moving anything, although nothing is lost. A service that wants a move treated as an ordinary change declares a move operation of its own, of class UPDATE, together with create at the destination; the cost is that a forbid on deletes no longer stops anyone moving resources out of a scope.

Requirements that depend on the request

Some requirements apply only when a request field is set. AIP-134 lets an Update with allow_missing create a missing resource and says the caller must hold the update permission [26]. This specification adds a local, stricter rule that stays declarative: when a request sets allow_missing = true, create on the parent is required as well. The rule reads the request, never the stored row, so an update-only grant can never create and the client can evaluate it. A requirement that depends on stored state, such as whether a row exists or who owns it, is not declarative and belongs to the handler (§3.3).

Field-sensitive writes

AIP-134 defines the fields an Update writes from the request alone: an omitted mask means the populated fields, * means every field, and when allow_missing creates a resource every populated field is applied regardless of the mask. AIP-161 says output-only fields named in a mask are ignored [30]. A Create writes the fields its request populates. A field guard is therefore declarative too: a resource field may name an additional operation that is required whenever the fields a request writes include that field, a path inside it, or a message that contains it (§4.1, §4.2). Everything this needs is on the wire, the mask and the fields the request sets, so a client and a server always compute the same set. "Only fields whose values actually change" depends on stored state and is a handler concern.

Credential limits

A delegated credential, such as an OAuth grant given to an agent or a third-party client, limits what its bearer may do. Model it as a ceiling of access classes, optionally per resource type, and intersect it with the principal's grants. The ceiling applies to each key by that key's own class, so a role that names an operation is limited exactly as a role that selects the operation's class. It narrows permits only. A forbid is never narrowed, because a narrower forbid would grant more. A ceiling never adds authority, and a new READ operation falls under a read-only ceiling exactly as it falls under a READ grant. The credential issuer states the ceiling; it does not decide resource authorization, which stays with the service that owns the resource.

3.3 Scoped Grants and the Two Walks

A role, by itself, grants nothing. A grant attaches a role's selectors to a scope: "viewer at companies/A", "widget-writer at companies/A/teams/B". A caller may hold different roles at different scopes, in different tenants, with no enclosing organization assumed. A grant may also be a forbid, and may have a condition.

Decide is the server's function. It follows the target's name down from the root and looks at the caller's grants attached at each step. K(g) answers "what should be sent for this grant": it starts at the grant's scope, follows the method patterns that can name something at or below it, and collects the keys the grant selects for those methods. These are the two walks of this section's title. Fold is the client's function over what was sent. Decide ignores conditions, so it is the whole decision only for unconditional grants; a condition can leave the server's decision unresolved, which §4.4 calls RESIDUAL.

Proposition 3.1 (exactness). Let Π = { (g.scope, ±g, K(g)) : g ∈ G } for a set G of unconditional grants, where ±g says whether g is a permit or a forbid, and K is computed from the same declarations the client folds with. Suppose each key determines the resource type, operation, access class and explicit-grant-only marker of every requirement that carries it. Then Fold(Π, key(ρ), t) = Decide(G, ρ, t) for every requirement ρ and every target t in its binding domain.

In words: send each grant's scope together with the keys it selects there, and a client that only asks "is this scope an ancestor of my target?" reaches the server's decision exactly, without ever seeing a role, a selector or an access class. The one condition is that a key always means the same kind of operation. The build enforces it (§4.2): the operation is part of the key, plurals are unique, and no key may carry two types, two classes or two markers. Counterexample 1 below shows what goes wrong without it.

Proof of Proposition 3.1

Fix ρ and t, and let k = key(ρ). A grant whose scope is not an ancestor of t counts on neither side. Take a grant with g.scope ⪯ t. Because t is in the binding domain of ρ, reach(ρ, g.scope) holds, so match(g, ρ) implies k ∈ K(g). Conversely, k ∈ K(g) means match(g, ρ′) for some requirement ρ′ with key k; match reads only the type, operation, class and marker, which k determines, so match(g, ρ) holds too. For permits and for forbids alike, then, the grants that count in Decide are exactly the entries that count in Fold, and the two definitions combine permits and forbids in the same way. ∎

The regression checks in §4.5 test the proposition over every policy of one or two grants drawn from five scopes, the fixture roles, as permits and as forbids, with contexts projected at the service root. The sent relation, the reference rule engine and the scoped-claims context match the definition exactly; the grant-shaped context is checked to be sound and to drop nothing when no forbid is present.

How Π reaches a client. Π is a definition, not a wire format. A policy of permits only is sent as it stands: one hole-free ALLOW claim per grant scope, which is the grant-shaped profile. With forbids the two context profiles differ. The grant-shaped profile cannot send a forbid entry, so it removes from each permit entry every key that a forbid could deny somewhere within that entry's scope. What remains is true and the fold stays sound. A narrower anchor usually recovers what was removed; §3.5 describes the case where none can. The scoped-claims profile sends the forbids as holes in ALLOW claims and as DENY claims, and for unconditional, disclosable grants its fold equals Decide (§3.6).

Several properties follow, and they are the practical content of this section:

  • Nothing is maintained per permission. K(g) depends only on the selector set and the shape of the scope, a company versus a team. It is computed from descriptors, it is the same for every user and every company, and it can be computed once at startup. The only per-user data is the list of scopes and selector sets.
  • The handler and the context endpoint share one resolver. Both start from the caller's effective grants. The context endpoint returns, in expanded form, what the handler already consults.
  • Scopes are discoverable. A context queried at the service root carries claims at each scope where the caller holds a grant. That answers "where can I act?" without any listing permission.
  • The question asked before anything is chosen is answered from the same data. A key in an ALLOW claim means its operation is usable throughout that claim's region. In a policy of unconditional permits that cannot raise an error, with no descendants omitted and no key nonprojecting, the converse holds too: a key that appears in no claim of the root context is usable nowhere. With forbids or conditions, absence means only that nothing was proven at that anchor. A caller who holds only a team-level editor grant is never offered CreateTeam, which binds to the company, and no stored row is scanned to find that out.
  • The pattern walk is not needed for soundness. The ancestor test in Fold already confines a key to targets under its scope. The walk only keeps payloads small and makes the answer to "where can I act?" exact for each key.

The construction works because each requirement's resource type and class can be read from the method's own declaration. If classes lived in a separate table keyed by permission name, K(g) could not be computed from descriptors, and that table would have to be shipped to every client and kept in step with every release. The same is true of a table that expands each role into a list of permissions. Both tables are the hand-maintained lists this design removes.

Limits of the grant model

The grant model covers scoped grants over a name hierarchy. These lie outside it:

  • Exceptions. A forbid below a permit means the permit no longer holds everywhere in its scope. The grant-shaped profile omits the affected keys from the broader claim; the scoped-claim profile reports the exception as a hole (§3.5, §3.6).
  • Conditions. A conditional grant yields a CONDITIONAL claim at best. The client does not evaluate conditions.
  • Requirements that depend on a request value other than true or false. A requirement can depend on a bool request field, such as allow_missing. One that depends on which value an enum field holds, such as a full view of a resource that needs an extra permission, cannot be declared: the method is a handler policy, which a frontend leaves to the server, unless the API exposes that choice as a bool field.
  • Very many direct shares. A caller with thousands of grant scopes should not receive them all at the root. The server marks the context as having omitted descendants and the client queries narrower anchors (§4.1).
  • Relationships that are not a name hierarchy. Group membership and sharing edges are resolved by the server into effective grants before anything is decided or projected (§3.4).
  • Upward and sideways access. Nothing is implied upward: a team role does not allow reading the company. Operations bound to the service root need a grant at the root, so an administrator of one tenant never satisfies a global method.

3.4 Resource Hierarchy, Prefixes and External Identities

AIP-124 gives every resource at most one canonical parent, and AIP-121 requires the parent-child relationship to be acyclic [1]. This specification adds one synthetic node above every top-level resource, the service root, whose segment list is empty. It is written //{service_name}/ in prose only. On the wire it is a tagged value, distinct from every AIP-122 resource name and AIP-156 singleton, and it is never passed to a generated name parser. Authorization often involves relationships that are not part of this tree: a user belongs to a group, a project is linked to a billing account, a widget is shared with a collaborator in another company. Counterexample 2 — Naive String Prefix Collision

If a client checks target.startsWith(scope), a grant on companies/A/teams/B also matches companies/A/teams/B2 and companies/A/teams/Billing/widgets/w9. Appending a slash fixes those sibling cases but still fails on names that are not canonical: …/teams/B/%2E%2E/C starts with …/teams/B/, yet a downstream decoder may normalize it to …/teams/C; doubled or trailing slashes create alternate spellings of one name; and the same relative path under another service is a different resource. AIP-122 says resource IDs should avoid characters that need URL-escaping [2], so a service can reject such spellings outright.

The remedy is that all matching, on server and client, parses a name into a service and a flat list of validated segments. A scope s covers a target r if and only if they belong to the same service, len(s) ≤ len(r), and every segment of s equals the segment of r at the same index. The root's empty list is a prefix of every name, and no tenant scope can be a prefix of the root. Reject empty segments, . and .., percent-encodings, a slash or backslash inside an identifier, and an ID that is just - other than as a wildcard the declaration allows, since AIP-159 reserves - for wildcards. The rule covers every name bound to a requirement and every anchor, claim scope and hole. A service may not resolve such a spelling to a canonical name instead: the client compares names segment by segment as they are written, so a name the server rewrote would fall under one scope on the client and another on the server, and the client would offer what the server refuses. A service that must accept such spellings declares the affected methods as handler policies.

AIP-122 and AIP-4231 each allow something that falls outside this segment model, and an API that uses it MUST declare the affected methods as handler policies: AIP-122 only says the terminal segment of a name should not contain a slash, and AIP-4231 allows a segment made of several variables joined by a separator [3]. Singleton and other static segments are ordinary literal segments.

Reachable Keys and the Pattern Trie

Every key is indexed under each of its binding patterns in a segment pattern trie rooted at the service root. A query walks the anchor's segments from the root. At each depth it follows the edge labeled with the anchor's segment and the * edge, whichever of the two exist. From every node it reaches at the anchor's depth it collects the keys bound at that node and at every node below it. That is the reach test of §3.3 applied to all keys at once. The walk costs O(matched nodes + keys returned), which is at most O(P·d + output) for P patterns of depth d.

A scope does not have to be a resource the service represents. A service that manages widgets under companies/{company}/teams/{team}/widgets/{widget} without implementing GetCompany can still attach grants to, and answer contexts for, companies/A: it is a local non-represented parent, a prefix of the service's own names. Resource types defined elsewhere are declared with the file-level google.api.resource_definition option documented in AIP-4231 [3].

Aliases and External Identities

AIP-122 allows programmatic aliases, such as users/me, provided responses use canonical names [2]. The server MUST resolve an alias to the immutable canonical name before policy evaluation and before any cache key is formed; otherwise a request that names companies/A through an alias would not match a forbid written on companies/A, and would get past it. An alias MUST be a value the service never uses as a canonical ID, such as me, so that whether a name is an alias never depends on data the caller cannot see. A client folds only canonical names: it compares names as written, so folding users/me against a hole on users/u_12345 would offer what the server refuses. A client that holds only an alias resolves it first, by reading the resource or from the context's requested_anchors (§4.1); until then it has no evidence for that name. A name owned by another service, such as //org.example.com/companies/acme, is not a local prefix. It enters the tree only through an identity mapping that server policy declares and versions, and claims are always expressed in the queried service's own names. Where a mapping cannot preserve policy semantics, the affected methods are handler policies.

The profiles nest: a grant-shaped context is a scoped-claims context that happens to contain only hole-free ALLOW claims. In the other direction, a scoped-claims context is coarsened to a grant-shaped one by dropping every claim that is not a hole-free ALLOW, and dropping a claim is always sound. A client states the highest profile it implements, the server never sends it more, and a deployment can move between profiles without changing the meaning of anything it has already sent.

The grant-shaped profile sends less. It does not prove less. Every ALLOW claim says that the permission holds everywhere in its scope, so a server in either profile has to know whether a forbid or a condition for the key exists anywhere below the claim's scope, including one attached to a single resource; that is the descendant-rule index of §3.6. Omitting a key because of a rule also tells the caller that such a rule exists, so the disclosure rules of §3.6 bind both profiles: a key whose rules may be private is declared nonprojecting, and nothing is sent for it above its privacy boundary. A policy of unconditional permits meets both obligations trivially, which is why this profile is cheap for the policies it was designed for.

Here is how the grant-shaped profile handles an exception. Suppose a viewer grant at companies/A and a forbid on reads at companies/A/teams/C. "Reads are allowed everywhere in A" is false, so the server omits the read keys from the claim at A. A frontend drawing the page for Team B finds no evidence for widgets.get there and queries Team B directly, where the claim is true and is returned. The exception costs one more query and never produces a wrong answer.

Recovery works because a narrower anchor can leave the exception outside it. That is not always possible. A permission can be checked at a scope and also below it: widgets.setOwner is checked on the team when a widget is created, and on the widget when it is updated. Suppose a forbid stops anyone setting the owner of companies/A/teams/B/widgets/w1. "Owners may be set anywhere in Team B" is now false, and every anchor that names Team B also covers that widget, so the grant-shaped profile can never show that creating a widget with an owner in Team B is allowed, although the server allows it. The same happens to widgets.create where widgets can sit directly under a company as well as under its teams, and one team carries a forbid on creating widgets. Nothing false is shown; the action is only hidden.

This is a known limit of the grant-shaped profile, and the architecture is built to grow past it when it starts to matter. It appears only when a policy forbids a permission below a scope where the same permission is also checked. A deployment that writes no such forbids never meets it. One that does will see frontends hide an action users can in fact perform, typically a create or an owner change in the scope around the forbid. That is the time to act: the scoped-claims profile reports the case exactly, as an ALLOW over Team B with the widget as a hole, and adopting it changes no declaration and no grant.

Questions about a single item use the same query. When the anchor is the only name in a key's binding domain at or below itself, as a widget is for widget operations and a team is not, a claim that the key holds everywhere at the anchor is simply the decision for that one resource (§1.4). A page of twenty rows with per-row actions is then one query with twenty anchors. For such a key and anchor, and only there, a service MAY also read the resource's stored fields, so that an owner-only rule gives ALLOW or DENY instead of CONDITIONAL and each row's buttons are right. It is safe only under these conditions. The caller must be allowed to read the resource and every field the rule reads, because the answer reveals their values. The answer is never reused after the row changes: it is keyed by the row's version or not cached at all. The server marks such a context row_dependent, because the client cannot tell it apart otherwise: a change of owner does not change the policy revision, so the context looks as current as any other at that revision while describing the row as it was when it was read. A client therefore uses it only for that one resource, never combines it with another anchor's answer when it decides an action, and lets a newer context for the same anchor replace it (§4.4). Moving a widget under an owner-only rule needs answers for two resources, so it is not offered from contexts; the server decides it. For any other name, including one the caller may not read and one that does not exist, the context is computed from rules alone and is the same whether or not the resource exists. This is the only place a context reads stored data.

Implement Declarations if the only need is to partition operations and describe inputs. Implement Grant-Shaped Contexts when roles are assigned at scopes and exceptions are rare; this covers most multi-tenant applications. Move to Scoped Claims when exceptions are common enough that the extra queries are felt, or when the interface must explain a denial instead of hiding the action.

3.6 The Scoped-Claim Algebra and Disclosure

This section defines the third profile. The claim algebra is needed only for Scoped Claims. The descendant-rule index and the disclosure rules at the end of the section bind both context profiles (§3.5).

The domain of key k at anchor s is every name one of k's binding patterns allows at or below s, including names under which nothing has been created yet. For a root-bound key that is the root alone. A server MUST NOT list stored rows to prove that something holds everywhere: tomorrow's widget is not among today's rows, and the claim must hold for it too. It sends no claim where the patterns allow no name at all, even though "everywhere" over nothing is trivially true.

A region is a scope (a resource name, a collection, or the root) minus zero or more scopes below it, its holes. Collections are needed where a resource has several parent patterns: with widgets under both companies/{company} and companies/{company}/teams/{team}, a claim may cover companies/A/widgets, or cover companies/A with the hole companies/A/teams. A claim says one of the following about a set of keys over a region, and the server must be able to prove it at the snapshot the response names:

  • ALLOW means the server would allow the call at every name of the region that the key can target.
  • DENY means the server would deny it at every such name. It is proven by a final forbid (§1.2) or by the absence of any permit that could apply, and the wire does not say which.
  • CONDITIONAL means the server could not resolve a condition. It says nothing about the decision; another context may prove one for the same target.

Where no claim covers a name, nothing is said about it either: only a DENY claim says no.

The projector this specification supports works as follows. Turn the rules that apply to the caller into a finite list of permits and forbids, each attached to a canonical scope, applying to everything below it, and optionally carrying a condition. In the grant model these are the caller's effective grants with their keys expanded (§3.3). Use one snapshot for every input the proof reads. Then cut the anchor's subtree into cells at the scopes of the rules the caller may be told about: each rule's scope starts a cell, which owns everything below it except the cells of deeper rules, including names under which nothing exists yet. Keep only the names the key can target, and drop cells left with none. The same rules then apply everywhere in a cell, although a condition may still come out differently from one name to the next. For each cell:

  1. Emit DENY if a final forbid applies throughout the cell: unconditional and provably free of evaluation errors (§1.2).
  2. Otherwise emit ALLOW only if (a) an applicable permit holds without condition in the cell, meaning it has no condition or its condition is proven true at every name of the cell with every fact it reads taken from the snapshot, and it provably cannot raise an evaluation error, and (b) every possible forbid is ruled out, including one that could apply through a predicate or an error. An owner-only permit therefore never yields ALLOW.
  3. Otherwise emit DENY if no permit can apply at any name of the cell.
  4. Otherwise emit CONDITIONAL if that is safe to disclose, and nothing if it is not.

Then merge a cell into the cell that encloses it when both have the same kind. A boundary remains a hole only where the answer changes, so nested permits yield one claim without a hole, which the grant-shaped coarsening keeps. Merging works one enclosing cell at a time, deepest first, and absorbs all of that cell's same-kind children together. In the grant-shaped profile it absorbs them only if the enclosing cell is left with no holes. Otherwise the coarsening would drop the merged claim, and with it an exception-free claim it had absorbed: a viewer at company A who also holds a grant at Team B, with a forbid in Team C, would lose Team B from the answer to "where can I act?". Step 3 comes before step 4 so that a condition that cannot change the outcome, such as a conditional forbid where no permit applies anyway, does not hide a denial that can be proven. Running out of budget, a missing dependency or a disclosure restriction never produces a DENY; at most it removes a claim. If the server cannot show that the same rules apply throughout a cell, as with aliases it does not model or rules that join relationships, it sends no claim there. A policy written as an arbitrary program has no exact projection under this contract.

Steps 2(b) and 3 quantify over every rule that could apply anywhere in the cell, including a rule attached to a single row, and rows may not be enumerated. Both are answered from a descendant-rule index, kept per scope and key for the rules that apply to the caller. It keeps forbids and permits apart, because they matter differently. A forbid strictly below a scope, conditional or possibly erroring ones included, stops an ALLOW over it (step 2(b)). A permit strictly below it stops a DENY that rests on the absence of permits (step 3). A second permit lower down never stops an ALLOW, and a rule that applies only to someone else stops nothing. The grant-shaped profile only needs to know whether such rules exist. The scoped-claims profile needs to know where they are, because it partitions the scope at them and turns each into a hole or a claim of its own; for it the index lists their scopes. When there are more than the server's budget allows, the server omits the claims that would need them and sets descendants_omitted (§5.1). The index carries a revision that changes whenever either answer could change, which includes a rule being added, removed or edited, and a role definition, group membership or identity mapping changing which rules apply to whom. If the index is unavailable, or older than the snapshot the view pins, the server sends no claim for that key rather than guess. The index is a normative part of both context profiles. A key whose rule sources the index does not fully cover MUST be declared nonprojecting, as defined below.

Two claims of different kinds for the same key MUST NOT overlap, since they would contradict each other. Overlap is judged only on names the key can target, so a region with no such names overlaps nothing: for a key bound only to a team's settings singleton (AIP-156), a team minus its settings is empty. Claims may be merged only if together they cover exactly the names of the merged region.

Disclosure: One Principle

A context may depend only on what the caller is allowed to know. Put precisely: compute claims from the rules the caller may be told about, and send a claim only if it stays true whatever rules the caller may not be told about exist, among those the deployment allows. The rest of this subsection follows from that.

Counterexample 3 — The One-Bit Leak

Alice holds a viewer grant at companies/A. An administrator places a forbid on companies/A/teams/D that Alice must not learn about. If the server answers Alice's query for A with ALLOW when the forbid is absent and with nothing when it is present, Alice learns that an exception exists. If it answers ALLOW with a hole, she learns its name. If it answers CONDITIONAL only when the forbid carries a predicate, the same bit leaks through a different kind. The only answer that tells her nothing is the same answer in every case.

Private rules exist for the same reason as every disclosure rule: a caller should not learn about what it cannot see, such as another company, or a team it is not allowed to list. A rule placed on such a scope is private for that caller. Take Alice, who may read widgets throughout company A but may not list its teams, and a forbid on Team D's widgets: a context that said ALLOW over company A with a hole at Team D would tell her that Team D exists. A deployment therefore states, for each key or resource type, whether its rules may be private and at which level of the hierarchy they may be placed, the privacy boundary, such as the team level. Above the boundary, for example at company A, the server sends no claim of any kind for that key, whether or not a private rule exists, so the answer is the same in both cases; such a key is nonprojecting there. At or below the boundary claims are sent normally: a DENY on Team D tells Alice no more than calling the API on Team D would, since the call would fail. That holds only if no private rule sits below the boundary, so a private rule MUST be attached at the boundary or above it: if private rules may be attached to single widgets, the boundary is the widget level.

A private rule MUST also be unconditional. A rule that depends on a widget's data, such as "no one reads Team D's widgets marked classified", changes what a context for Team D says even while no widget is marked and every call Alice makes succeeds: without the rule the context says ALLOW, and with it the server would have to say CONDITIONAL or nothing. Either way Alice learns that something is hidden there, which no call would have told her. Keeping such data from a caller is the handler's job, for example by leaving those widgets out of a Search. A deployment that needs a rule like that hidden declares its permission as never projected for that part of the tree, so contexts there carry no claims for it at any level.

This is also why both ways of denying, an explicit forbid and the absence of any permit, are sent as the same DENY: a caller who sees DENY on Team D cannot tell whether a forbid is there. A deployment with no private rules declares none and projects everything. A private rule found for a key that was not declared is a deployment error: the server withholds every claim for that key above the rule, and at and below it as well if the rule has a condition, raises an alert for whoever authors policy, and still answers the query, which here means only that the request does not fail. This fallback does not hide the rule. A caller who received ALLOW before the rule existed and receives nothing after it has learned that it exists, which is the leak of Counterexample 3, and no answer given at that point avoids it. The protection is at authoring time, below.

The same principle binds the server's own checks. In some places the server itself has to prove that a key holds everywhere in a region: a wildcard List, the single parent check of a batch, and the NOT_FOUND answer of a wildcard Get (§4.3). For a nonprojecting key above its privacy boundary each of those checks refuses in every case. Succeeding only when no private rule exists would disclose the rule as surely as a claim would. Refusing a batch's parent check does not refuse the batch: its items are then authorized one by one (§4.3). A wildcard List and a wildcard Get have no such fallback, and are refused.

A claim's scope and its holes name scopes. The scope of a permit the caller holds directly is always disclosable to that caller: a grant cannot be used without knowing where it applies. A permit that reaches the caller through a group or an identity mapping (§3.4), at a scope the caller cannot otherwise see, is a private rule. Any other scope, typically that of a forbid, is disclosable to a caller who could see it through the API, by get on it or list on its parent, or, for a parent the service does not serve (§3.4), by a visibility rule the deployment declares, such as "callers who hold a permit at or above it". A collection is disclosable exactly when the resource it sits under is, because its path names that resource: companies/A/teams/D/widgets names Team D. A rule at a scope that is not disclosable to a caller it applies to is a private rule and is handled by declaration, as above. The server never decides rule by rule whether to withdraw a claim, because that decision is the leak of Counterexample 3; policy authoring MUST reject such a rule for a key that is not declared private-capable. The same validation runs when a grant, a role, a group or a visibility rule changes: revoking someone's list permission can turn a forbid they could see into one they cannot, and a new permit above a forbid can make it apply to someone who cannot see it. Every hole of a claim is sent with it. Coarsening may only drop claims or merge claims whose union is exact, and MUST NOT widen a region or drop a hole. The same rules govern errors and diagnostics, over the whole status payload (§4.3).

The disclosure principle covers what a response says: its claims, its descendants_omitted flag and every field of an error. A server therefore decides budgets and descendants_omitted from disclosable rules only, so that neither changes when a private rule is added. It does not cover how long a response takes or how large it is. A deployment that must hide those as well does so by its own means, such as fixed work or padding per query.

3.7 Evolution Safety: New Operations Under Existing Grants

Class selectors make policy forward-compatible, and that is also the hazard. A new RPC classified READ is granted to every role that selects READ on its resource type the moment it is deployed. Nobody edited a role, and nobody was asked. The specification keeps the convenience and adds a review step.

  1. Capability diff. The build compares the interpretation of the descriptors before and after a change and reports, for each role, the keys it gains and the keys it loses. The change is accepted only when that report has been acknowledged. This is the one place where a human reads a list of permissions, and the list is generated.
  2. Explicit-grant-only operations. An operation marked explicit_grant_only is never matched by a class selector in a permit. A role holds it only by naming it. A forbid by class still covers it, so an exception written as "no deletes here" also stops the operation that most needed stopping. AIP-164 requires an expunge permission separate from delete [28]; this marker is how that requirement is met, and it suits any operation that is irreversible or unusually sensitive.
  3. New resource types. A selector that names every type picks up a new resource type the same way, and the diff reports it the same way. Prefer selectors that name types for anything sensitive.
  4. Reclassification. Changing an operation's class changes which roles grant it. The diff shows it as a loss for some roles and a gain for others, and it is reviewed as such.

  5. Contexts across versions. After a release, a client's declarations and the server's can differ for a while: the server has been deployed and the client has not yet been rebuilt or reloaded, or the other way round. Most changes do no harm in that window. A context lists keys that the server expanded with its own declarations, so a new method or a new key is simply absent from what an older client folds, a key the client does not know is skipped, and an operation moved to another access class is sent or withheld according to the classes of the server that answered. The client's own copy of the class still matters: its credential ceiling is checked against it, and it decides whether the method counts as read-only. Those follow the client's declarations, so a reclassification belongs with the changes to a method itself, described below. Methods whose declarations did not change fold as before. During a rollout, however, old and new servers can answer in turn, so a reclassified operation can be sent by one answer and refused by the server that takes the next call. The policy revision does not move, because no grant changed, so a client sees the answer flip at the same revision until every replica runs the new release and older contexts expire.

    A release that adds a resource pattern changes the names its methods accept, so it falls under the next paragraph, and it misleads in both directions. An older client cannot check claims and holes on the new pattern, so it discards the contexts that carry them (§4.4) and loses evidence for those anchors. A newer client reading an older server's answer is worse off: the older server knows nothing of the new names, ignores any rule attached to them, and can send an ALLOW or a DENY that its own rules on those names would contradict.

    Keys do not cover a change to an existing method itself: a requirement added or dropped, a requirement moved to another access class, a change to the resource names it accepts, to the fields it guards or treats as output-only, to whether it is read-only, mutating or destructive, to a Search's item filter, or to whether a batch can partly succeed. Until the client picks up the new declarations, it folds the old description of the method against the new context, and it can offer a call the server refuses, hide one the server would allow, or present a method wrongly, for example as read-only. The server still decides every call, a refusal makes the client refresh its context (§3.8), and the problem ends when the client loads the new release.

    Each view carries contract_version, a digest of the declarations the server computed it from (§4.2), so a client can tell when it is in this window. What it does then is its own choice. It can keep folding and accept that a changed method may be wrong until it updates, which is what most frontends will do. It can stop folding views whose digest differs from its own, which removes the risk but leaves it with no evidence for any method until it updates. Or it can obtain the server's declarations for that digest and fold with those. This specification does not define how a client obtains or loads newer declarations.

Counterexample 4 — A Class Claim Across Versions

Suppose contexts carried "READ on Widget at companies/A" instead of keys. Version 2 of the service adds ExportWidgets, classified READ, with a forbid for Alice at Team C. A client that already has the version 2 descriptors and still holds a version 1 context folds ALLOW for ExportWidgets at Team C: the claim never considered that operation. With keys, widgets.export is simply absent from the old context. This is why selectors stay on the server (§3.3).

3.8 Caching, Freshness and Cardinality

Proof cache key

Key a shared proof entry by everything that can change it: service, contract version, revision authority, revision epoch, projection-dependency revision, effective principal, canonical claims digest, tagged canonical anchor and profile. Every component MUST be present; a missing one means the proof is not cached. Authority and epoch are part of the key because a revision counter may repeat after a failover or a reset, and a proof must never be served across that boundary. The dependency revision changes whenever something the proof relied on changes: a grant above the anchor, a rule below it that affects whether a key holds everywhere, and the data and disclosure rules the proof read. A service-wide monotonic revision is the conservative baseline; a tenant revision alone cannot key an anchor that spans tenants. Resolve the current revision from an authoritative view before using its cache namespace, and compute and label a new entry from that same view.

Claims digest

The digest covers every authenticated input that policy reads: the effective principal and delegation chain, tenant, credential ceiling, authentication assurance, and any stable network or device posture. It also covers whatever decides which scopes the caller may be told about (§3.6), because two callers with the same grants but different visibility must not share a proof. Version the serialization, sort sets, preserve ordered inputs, type values, and distinguish absent from empty. An unmodeled input that can affect a claim makes the claim uncacheable or CONDITIONAL. Do not hash wall-clock time; cap reuse at the next provable time-policy boundary, or do not cache the time-dependent proof.

Session-independent entries

A shared entry serves many callers and sessions, so it MUST NOT hold a subject context identifier, a session identifier, view metadata or a session-capped lifetime. On every response, including cache hits, the server stamps the current caller's subject_context_id, the pinned view's metadata, and remaining_ttl = the minimum of the remaining lifetime of every proof in the response and the remaining lifetime of this caller's session or credential.

Lifetimes

Measure remaining_ttl immediately before sending, from the original expiry; receipt, persistence and replay never restart it. Each cache tier uses one expiry model. Node-local caches store a monotonic-clock deadline. Shared caches store an absolute expiry and require a documented maximum clock skew between writers and readers; a reader subtracts that bound and its read delay and treats a non-positive result as a miss. The wire carries only the relative remaining_ttl. A client converts it to a monotonic deadline measured from the start of its request, never extends it, and rejects a view whose remaining_ttl is absent, zero or negative; it is a google.protobuf.Duration, written "30s" in ProtoJSON. The client checks the deadline again every time it folds, not only when it accepts the view.

Ordering across replicas

A lagging replica can serve an older view after a newer one has been accepted. Serializing a client's requests prevents responses from being reordered; it does not prevent this. Wherever more than one replica can answer, one of two mechanisms is REQUIRED: the revision authority assigns a monotonic generation to every pinned view, and the client rejects a lower one, and treats an equal one as valid only if it names the same revision; or the client sends the view it last accepted as a floor, min_view, and the server answers from a view at least that new or refuses with UNAVAILABLE. A reply proves only that it is at least as new as the floor it was sent with, so the client accepts it only if that floor still names the view the client holds: a reply to a request sent before its last change is discarded, which stops two requests in flight from undoing each other. A server that cannot place a floor in its own order, because the revision is unknown to it or too old, refuses with UNAVAILABLE. A floor names its revision authority and epoch as well as the revision. The epochs of one authority are whole numbers from 1 to 253−1 that increase each time its revision sequence restarts, carried and compared like generations, so a client can tell a newer epoch from an older one: it starts a new namespace for a higher epoch and discards a reply from a lower one, and a server whose epoch is lower than the floor's refuses with UNAVAILABLE instead of answering from a sequence the client has already left (§4.4). A namespace that carries generations keeps them: a reply without one is rejected. The revision authority orders its own revisions; clients compare them only for equality. Generations do not exceed 253−1. They are carried as int64, since AIP-141 rules out unsigned integer types, and ProtoJSON serializes them as decimal strings, so clients in every language parse them as integers and compare numerically, never as strings.

Staleness is bounded

Refresh a context when the server answers PERMISSION_DENIED, without treating the refresh as authority to retry a mutation; expiry and revalidation also discover permissions granted since the last query. After a revocation the server denies as soon as it observes the new revision. An unexpired context may still show the action until it is refreshed, and it confers nothing.

}

extend google.protobuf.ServiceOptions {
  // Authorization settings of the service.
  ServiceAuthz service = 51002;
}

extend google.protobuf.FieldOptions {
  // A field guard on a resource field: a standard Create or Update, or
  // its batch form, that writes the field also needs this operation,
  // on the target of the write (§4.2, rule 11). A custom method that
  // can write the field lists the operation among its own requirements.
  FieldAuthz field = 51003;
}

// Authorization settings of one service.
message ServiceAuthz {
  // Every RPC of this service must carry a declaration, and every RPC
  // of an imported service the API implements must be listed below,
  // served or unimplemented; a missing one fails the build. When
  // false, an RPC without a declaration is outside this contract and
  // clients defer to the server for it.
  bool required = 1;

  // Dispositions for RPCs defined in imported protos, which cannot be
  // annotated where they are defined, such as those of
  // google.longrunning.Operations: each served one with its form, and
  // each other one as unimplemented.
  repeated ImportedMethod imported_methods = 2;
}

// The disposition of one RPC defined in an imported proto.
message ImportedMethod {
  // Full method name: "google.longrunning.Operations/GetOperation".
  string method = 1;

  // Any form except `standard`. Unset when unimplemented is true.
  MethodAuthz authz = 2;

  // The RPC changes nothing. The service cannot add an option to an RPC
  // defined in another proto, so this flag says what
  // idempotency_level = NO_SIDE_EFFECTS would say there; an RPC whose
  // own descriptor already sets that option needs no flag. It is
  // checked like the option (§4.2, rule 9): it cannot make read-only an
  // RPC whose requirements create, update, delete or execute.
  bool no_side_effects = 3;

  // The service does not serve this RPC and answers UNIMPLEMENTED.
  // Listing it lets the build confirm that every RPC of an imported
  // service the API implements was considered. Set alone: an
  // unimplemented RPC has no authz and no effect to describe.
  bool unimplemented = 4;
}

// What one RPC requires. Exactly one of `standard`, `handler_policy`
// or a non-empty `requirements` is set.
message MethodAuthz {
  // The two forms that carry no requirement list of their own.
  oneof form {
    // Derive the requirement from the AIP standard or batch method shape.
    Standard standard = 1;

    // A named authoritative policy implemented by the service.
    // Clients always defer to the server for such a method.
    string handler_policy = 2;
  }

  repeated Requirement requirements = 3;

  // Search-style methods: the operation each returned item must pass,
  // on the resource type of the first requirement. Some method of the
  // service must declare that operation.
  string item_filter = 4;

  enum PartialSuccess {
    // Derive from the method shape.
    PARTIAL_SUCCESS_UNSPECIFIED = 0;

A method declares exactly one of these: standard, which derives the requirement from which standard method it is; requirements, which lists what a custom method needs, each entry an access class and an operation; or handler_policy, which names a policy the service implements in code. A field guard is a FieldAuthz placed on a resource field: a class and an operation that writing the field also needs, checked on whatever the write targets.

The contracts follow the AIPs they build on, and both files pass Google's AIP linter with no findings. Integer fields are signed (AIP-141). An enum used by one message is nested in it with unprefixed values, and a shared enum sits at the end of its file with prefixed values (AIP-126, AIP-191). Request fields carry google.api.field_behavior (AIP-203). Field names are nouns, not verbs or prepositions, and avoid reserved words (AIP-140), which is why the access class is an enum value and not a field named read or delete [31].     KIND_UNSPECIFIED = 0;

    ALLOW = 1;

    DENY = 2;

    CONDITIONAL = 3;

  // Adds holes, DENY and CONDITIONAL.
  PROFILE_SCOPED_CLAIMS = 2;

Anchors

An anchor is the service root or a resource name, and the Anchor message has no other arm. A resource arm that holds anything but a resource name of the service, such as a collection or a root written as //svc/, is rejected with INVALID_ARGUMENT: the root is carried only as the service_root arm. An empty anchor list, and an anchor with no arm set, are rejected with INVALID_ARGUMENT. Exact duplicates in the request as submitted, compared by value (the same arm with the same string), are rejected with INVALID_ARGUMENT before anything else is examined, which reveals nothing. The server then resolves aliases. An alias resolves for a caller only if the caller is allowed to know what it names: it is the caller's own, such as users/me, or the caller could read the resource it names. An anchor that does not resolve is omitted, with no per-anchor error and no placeholder, so the response is the same whether an alias is unknown or names something hidden. Anchors that resolve to one canonical name yield one context, identified by its canonical anchor, which lists in requested_anchors every anchor of the request it answers, exactly as sent. A client that asked through an alias finds its context that way. That reveals nothing further, because an alias resolves only for a caller allowed to know what it names.

A canonical name needs no visibility check, because its context says nothing about whether the resource exists. Apart from the single-resource case of §3.5, a context is computed from the rules that apply to the caller and not from stored rows, so the context for a name at which the caller holds nothing is the same whether or not anything exists there. It may have zero claims.

Claims

A claim's scope and holes are validated against the service's pattern trie, not with generated resource-name parsers, because a collection is not a resource name. A scope must lie at or below the context's anchor and be a place where every key in the claim's set can apply, that is, the start of at least one of each key's binding patterns; a hole must be a strict descendant of its claim's scope. A claim that references a key set missing from the response, an unset arm, or an unknown or unspecified kind invalidates its whole context (§4.4). A key that the client's own descriptors do not define is skipped, not treated as corruption: it comes from a server whose declarations are newer than the client's (§3.7). Unknown or incompatible data MUST NOT produce an allow.

The root anchor

A query at the service root returns the caller's claims at every scope where they hold a grant, which is how a client discovers where it can act (§3.3). A server MAY withhold claims below any anchor for budget and sets descendants_omitted; the client then queries narrower anchors. Kubernetes reports an incomplete rules review in the same way [16].

Wire compatibility

These messages are not wire-compatible with earlier revisions of this report. A deployment that shipped an earlier revision publishes this contract under a new package version instead of changing the old one in place.

4.2 Descriptor Interpretation Rules

What an interpreter derives from the API's descriptors, the interpretation, is normative: two conforming interpreters MUST derive the same result from the same descriptors. A service may cache that result in any form, including a JSON catalog served to browsers that cannot run gRPC reflection. Such a cache carries no authorization fact of its own, and it is valid only if it equals the interpretation. The rules are:

  1. Disposition. In a service whose option sets required, every RPC carries exactly one form of MethodAuthz, and every RPC of each imported service the API implements is listed in imported_methods, with a form or as unimplemented. An API implements google.longrunning.Operations whenever one of its methods returns an Operation, because AIP-151 requires it [5]; any other imported service it implements is identified by listing one of its RPCs, after which all of them must be listed. All of this is visible in the descriptors, so an omission fails the build, typically in a lint rule run where the protos are compiled, such as a buf plugin. Server startup would be the wrong place for the check: by then the mistake has already shipped. Where required is not set, an RPC without a declaration is outside this contract: the service enforces it by other means and a client defers to the server for it. A handler_policy names an authoritative implementation registered by the service, and covers intentionally public, authenticated-self and exempt methods as well as anything that cannot be decomposed into independent requirements. item_filter and partial_success accompany requirements only.
  2. Standard methods. standard is valid only on the AIP standard or batch method of a resource: the method's name is the standard verb followed by the resource's type name, or by its plural for List and batch methods, and its request has the shape AIP-131 through AIP-135 or AIP-231 through AIP-235 gives it [26] [9]. A method named GetAccessPolicy that takes a team's name is a custom method, because the name after the verb is not the resource's, and AIP-136 advises against a standard verb in a custom method's name. standard derives one requirement, as tabulated below.
  3. Target. A standard method takes its target from the table below. When a custom method's requirement sets neither target_field nor service_root, the target is the request's name field; otherwise its parent field; otherwise the name field of the first singular message field, in declaration order, whose message carries google.api.resource. Batch methods bind every item: names[], or requests[] followed by the standard path. A BatchCreate item that omits its parent takes the request's top-level parent, as AIP-233 allows, unless that parent is a wildcard. A path ends at a singular string after expanding at most one repeated field. An absent, empty, malformed or non-matching value binds no target, and a request with an unbound requirement is denied. A requirement is never satisfied by having zero targets.
  4. Resource type. The target field's google.api.resource_reference supplies it: type names the resource, and child_type names the type whose parent the field holds [3]. A resource message's own name field supplies its type. A top-level List takes the type of the response's repeated field whose message carries google.api.resource, and a top-level Create the type of the resource in its request. Where none applies, resource_type is stated. On a requirement with a target field it says what type of resource the field names, and it must agree with any type the field's own annotation gives; on a requirement bound to the service root it gives the type the root-bound key belongs to. A field that holds a parent's name carries child_type instead, because resource_type cannot say that the name is a parent's. A root-bound requirement with no type has the reserved service type.
  5. Binding patterns. A requirement on a resource binds to that type's patterns. A requirement on a parent binds to each pattern with its final collection and ID removed, or its final literal removed for an AIP-156 singleton [6]; the parent of a top-level pattern is the service root. A key required by several methods binds to the union of their patterns.
  6. Key. The permission key is the resource type's plural, a dot, and the operation: widgets.get. AIP-123 defines the form of plural and AIP-156 requires it for singletons [3] [6]; this specification requires it on every resource type a declaration refers to. The reserved type of a requirement bound to the service root has the plural service, giving keys such as service.exportAuditLog. Operation names are lower camel case. An item_filter names an operation on the resource type of the method's first requirement.
  7. Class. A standard method's class is fixed by its kind. Every other requirement states its access_class; an unspecified or unknown class is rejected. All requirements that share a key share its resource type, class and explicit_grant_only marker.
  8. Conditional requirements. A requirement with condition applies only to requests in which the named bool field is true. A standard Update whose request declares allow_missing derives one automatically: create, on the parent of the bound name, when allow_missing is true (§4.3). In a BatchUpdate the condition is read per item, so create is required only on the parents of the items that ask for it. A field hoisted to the batch level, which AIP-233 and AIP-234 allow, counts as set on every item.
  9. Effect. A method with requirements is read-only if every requirement it declares or derives is READ, conditional ones included, or if it says it changes nothing, through idempotency_level = NO_SIDE_EFFECTS or, for an imported RPC, the no_side_effects flag of its imported_methods entry, and none of its requirements, declared or derived, is CREATE, UPDATE, DELETE or EXECUTE. Otherwise it is destructive if any requirement is DELETE, and mutating if none is. A handler-policy method is read-only if it sets that option or, when it is imported, if its own descriptor sets it or its imported_methods entry sets no_side_effects. Otherwise its effect is UNKNOWN, and a client treats it as it would a destructive method.
  10. Partial success. A synchronous method is atomic. An Operation-returning batch method whose request declares return_partial_success is partial when that field is true; one whose metadata declares failed_requests with no request flag is always partial [9].
  11. Field guards. The fields a request writes are computed from the request alone, so a client and the server always compute the same set. For an Update, an omitted mask means the populated fields, listed down to each field that is set, * means every field, and an explicit mask means its paths. A mask that is present but has no paths writes nothing: AIP-134 says should, and this specification requires it. With allow_missing true the populated fields are added, because if the resource is missing all of them are applied. For a Create, the written fields are the populated ones, listed down to each field that is set. Output-only fields are removed wherever they appear, including inside a message that is named as a whole [30]. A guard applies when a written path names the guarded field, a path inside it, or a message that contains it. Mask paths are split into segments at dots, except inside backticks, which AIP-161 uses to quote a map key that contains a dot, as in items.`a.b`.owner. A guarded field inside a map or a repeated field is written with * for the map key or for every element, as in items.*.owner, so a mask path that names one entry, such as items.foo.owner, matches it, and so does a * in a mask path, which AIP-161 lets a service accept. The guard adds its operation as a requirement on the target of the write: the parent for a Create, the resource for an Update, and the parent as well when allow_missing is true, because that Update may create the resource. In a batch, each item is guarded from its own write and on its own target, and a field the batch request sets at the top level counts for every item. If an item also sets it, the guards use both values: AIP-234 requires the two to match, but that is validation, which comes after authorization. The guard's key is the resource's plural and the guard's operation, and it binds to the patterns of the write targets like any other key, so contexts carry it. Guards are derived only for standard Create and Update methods and their batch forms; a custom method that can write a guarded field MUST list the guard's operation among its own requirements. The handler writes no field outside the computed set.
  12. Contract version. contract_version is the SHA-256 digest, in lowercase hexadecimal, of the interpretation serialized as canonical JSON (RFC 8785 [32]) in the form shown below. It is not a hash of descriptor bytes, whose field order and unrelated options would change it. Any change to the declarations that alters what some request requires, which keys some grant yields, or whether a method is read-only, mutating or destructive, changes the digest; the regression checks in §4.5 apply a range of such changes and confirm that each one does. The digest can also change when nothing a client folds on has changed, and a client that compares it then sees a mismatch it did not need to. A client that compares contract_version with its own must compute it exactly as the server does, byte for byte; the simplest way is for the client's build and the server's to take the value from the same tool. The reference model compares the canonical form directly and leaves the digest to implementations.

Order of Checks and the Error Status

A service checks authorization before validating a request (AIP-211, must) and before learning whether the resource or its parent exists (AIP-193, must) [8] [27]. It parses only enough of the request to bind the declared targets. A requirement whose target cannot be bound has no scope to authorize, and the request is denied.

A denial returns PERMISSION_DENIED. Following AIP-211, the message reads Permission '{permission}' denied on resource '{resource}' (or it might not exist). with the permission key and the name exactly as the caller supplied it. AIP-193 requires an ErrorInfo on every error and requires every dynamic part of the message to appear in its metadata. Disclosure rules therefore cover the whole status: code, message, reason, domain, metadata and any other detail. Cases that must be indistinguishable (an absent row and a hidden row; a hidden duplicate and any other denial; an alias that is unknown and one whose target the caller may not see) MUST produce the same status in every field. Echo only values the caller supplied, never a resolved canonical name, an alias target, an owning parent or a policy identifier, and bound and escape what is echoed so that a supplied name cannot forge log lines.

The same checks apply to a request with validate_only set: AIP-163 requires permission checks on a dry run [28]. A page token continues a query; AIP-158 forbids it from carrying any authorization, so every page is authorized again. A permission change between pages therefore shows in the later pages, and a token never extends what the caller may see.

Missing Resources

Existence and authorization are determined in one consistent view. For a resource that does not exist:

  • If the caller's grants already decide the request for that name, the decision stands: an allow yields NOT_FOUND, a denial yields PERMISSION_DENIED.
  • If the decision cannot be made only because the row is absent, for example because it depends on the row's attributes, the service checks the List permission on the parent. This is AIP-211's "authorization to read children on the parent". If it is allowed the status is NOT_FOUND; otherwise PERMISSION_DENIED.

The List permission qualifies because a holder could list the collection and see that the child is absent. The check does not recurse: if the parent's decision is not determinable either, the status is PERMISSION_DENIED. For a top-level resource the parent is the service root. A resource type with no List method offers no such check, so a decision that depends on its missing row is PERMISSION_DENIED. A method with several requirements returns NOT_FOUND only if every requirement that depends on the missing row passes the check. A resource is hidden from a caller who holds neither get on it nor list on its parent; a forbid on get alone does not hide it from a caller who can list the parent (List and Search, below). A parent allow never overrides a denial on a resource that exists, and an absent or unbindable request field is not an absent row.

List and Search

AIP-132 says a List should return the same results to any user permitted to list the collection, and that Search methods are more relaxed [26]. This specification requires it. An existing API whose List filters by caller changes what those callers see when it adopts this rule, so it gives them a Search first. A List is authorized by one check, the list key on the parent, and then returns the whole collection, with the same total_size and page tokens for every caller.

Before roles are designed, understand what this means:

  • The List permission discloses every child. AIP-132 says a List should return fully populated resources, so holding list on a parent is at least as revealing as holding get on each child. A forbid on get at one child does not hide that child from someone who can list its parent. Authoring tools SHOULD warn when such a forbid is written.
  • Existence cannot be hidden from siblings inside one List collection. A caller who must see only some children is given a Search method instead of the List permission, or the confidential children are placed under a different parent.

A Search method is a custom collection fetch method (AIP-136), for example GET /v1/{parent=companies/*/teams/*}/widgets:search. It declares its own operation and an item_filter, the operation every returned item must pass. The service applies the filter in the query or by an authoritative bulk check of candidates, and its counts, page sizes and tokens reveal nothing about rejected items. A Search with a wildcard parent applies its own key per parent as a filter; a caller who holds it nowhere receives an empty result, which is what a caller with no accessible items receives. Nothing has to hold everywhere for such a call, so a client does not fold it and leaves the answer to the server (§4.4). The same empty result is returned when the wildcard's fixed part names a parent that does not exist, unless the caller may see whether it exists: companies/UNKNOWN/teams/- never answers NOT_FOUND to someone who cannot see companies. A server MAY refuse such a call with PERMISSION_DENIED before validating its query, when the caller's own grants show that no parent the wildcard matches could pass, for example a credential that excludes reads or a forbid covering all of them; that reveals nothing an empty result would not, and it spares a pointless scan.

Wildcards

AIP-159 lets a List accept - for a parent ID and says nothing about authorization [7]. A wildcard parent names a set of parents, not a resource. Because this specification makes a List return the same results to every permitted caller, a wildcard List is authorized only if the list key holds for every potential parent the wildcard matches: a statement that the key holds everywhere, exactly the kind a context makes. In the grant model that means a permit at or above the part of the name before the wildcard, with no forbid below it that interrupts it. A caller who holds the key in only some parents lists those parents one at a time or uses Search.

The rule has two useful properties. No extra permission is needed to guard wildcard invocation, so there is nothing to bind when the wildcard is not the last segment or when several segments are wildcards. And a client can evaluate it locally: a wildcard List folds ALLOW when one ALLOW claim contains every name the wildcard matches, and DENY when a DENY claim contains at least one of them. When the deployment allows private rules for the list key, the check is refused above their privacy boundary in every case, since passing only when no hidden rule exists would reveal the rule (§3.6).

- is accepted only as the whole ID segment of a variable the declaration lists, results carry canonical names with the real parent IDs, and an item that omits its parent never inherits a wildcard top-level parent. AIP-217's unreachable field reports parents that are temporarily unavailable [29]. Holding the list key in every parent the wildcard matches does not mean the caller may see the parents themselves: listing widgets in every team of company A is not listing the teams. A server therefore names an unreachable parent only if the caller could see it, by get on it or list on its parent, or, for a parent the service does not serve, by the visibility rule the deployment declares (§3.6), and otherwise fails the request with UNAVAILABLE instead of returning a partial answer. This specification attaches no other authorization meaning to that field.

AIP-159 permits a wildcard on Get only where IDs are unique across parents. The service resolves the name first and then applies the Get rule to the resolved resource. No match, a match the caller may not see, and a match the caller is denied all return the same PERMISSION_DENIED; NOT_FOUND is returned for no match only to a caller who holds the list key in every parent the wildcard matches, or the get key on every name it could match, and only when the deployment allows no private rules there for the permission that proves it: a proof that passed only when no hidden rule exists would reveal the rule (§3.6). More than one match means the IDs were not unique after all: a server fault, which the server logs and answers with the same PERMISSION_DENIED.

Name Collisions

Any method that can make a name collide with an existing resource follows one rule: Create with an ID the caller chooses, Move or Rename to a destination, and each item of a BatchCreate. An Update with allow_missing is not among them: on a taken name it updates that resource (AIP-134). The difficulty is disclosure. Alice may create widgets in Team B and asks for the ID w7. A widget w7 already exists there, but Alice may not see it, and answering ALREADY_EXISTS would tell her that it exists. So the service first authorizes the operation's own requirements, as for any request. If the name is taken, it then checks, in the same consistent view, whether the caller can see the existing resource: get on it, or list on its parent. It returns ALREADY_EXISTS only if that check allows, and otherwise PERMISSION_DENIED, with the same status as any other denial of that method. That status names the method's own permission and the target the caller supplied, such as widgets.create on the parent, never the visibility check, so a hidden collision and an ordinary denial are identical in every field.

Here two AIPs pull in different directions, and the one that wins is not the one its title suggests. AIP-211, the AIP about authorization checks, says a method should check only its own permission when it chooses which error to return, and should not look at a related permission, such as whether the caller could read the existing resource; it uses exactly this case as its example. Followed alone, it would have Create answer ALREADY_EXISTS and reveal the hidden widget. AIP-133, the AIP about Create, says the opposite for this one case: a duplicate ID must get ALREADY_EXISTS, but if the caller does not have permission to see the duplicate, the service must answer PERMISSION_DENIED instead. AIP-133's rule is a must and AIP-211's a should, so AIP-133 governs: Create does look at whether the caller may see the existing resource. It does so for this one decision only, after its own permission has been checked.

The rule leaves one inference open. A caller who is otherwise allowed to create under a parent and is refused for one particular ID can conclude that something it cannot see holds that name. The status is identical to every other denial of the method, so nothing more is disclosed, and no permission context predicts the refusal (§1.1). A service that cannot accept the inference assigns IDs on the server for that resource.

Update, Upsert and Delete

For an upsert, AIP-134 says the caller must hold the update permission to call Update even with allow_missing set, and suggests conditions to prevent creation. This specification's rule is stricter and is a local policy: a request with allow_missing = true additionally requires create on the parent. It is decided from the request alone. A caller with only the update permission sends allow_missing = false and receives NOT_FOUND for a missing resource, as AIP-134 specifies.

For Delete, AIP-135's allow_missing on Delete makes a missing resource a successful no-op. It needs no extra requirement, but its answer for a missing row follows the missing-resource rule above: OK where the request would otherwise have returned NOT_FOUND, and PERMISSION_DENIED otherwise. Without that, an owner-only delete rule would answer OK for a missing widget and PERMISSION_DENIED for someone else's existing one, which reveals which widgets exist. A cascading delete (force) requires at least delete on the named resource; a service that also requires delete on each child type declares the whole method as a handler policy, since a declaration has one form and standard cannot carry that extra, subtree-wide check. FAILED_PRECONDITION for children present and ABORTED for an etag mismatch are returned only to an authorized caller.

Batch Methods

A batch method's requirement is the singular method's requirement applied to each item. AIP-231 explains that the top-level parent field exists "to permit a single permissions check" [9]. In this model that check asks whether the item's key holds everywhere under the stated parent; if it does, every item under it is authorized at once. The rules are:

  1. Bind every item that can be bound and authorize it, even if another item cannot be bound. An item whose name lies under the request's top-level parent may be authorized by one check that its key is allowed everywhere under that parent. When the parent contains a wildcard, such as companies/A/teams/-, that check covers everything under every team the wildcard matches, so a forbid on one widget in one team makes it fail. Any other item, and every item when that check fails or is refused, is authorized on its own. An item from another parent is therefore refused as unauthorized before step 4 could report that it does not belong. When the deployment allows private rules for the key below the parent, the check is refused (§3.6), because passing only when no private rule exists would reveal the rule; the items are then authorized one by one.
  2. If any bound item is not authorized, a synchronous or atomic batch returns PERMISSION_DENIED with no detail identifying the item: the message names the top-level parent if the request has one, and otherwise only the permission. No validation result is revealed first.
  3. An item that cannot be bound, and an empty batch, have no scope to authorize. INVALID_ARGUMENT is returned for them only when the check on the request's top-level parent passes for every key its items would need, including the field guards an unbindable item's write would trigger; with no top-level parent, or when the check fails, the answer is PERMISSION_DENIED.
  4. Only then is the request validated: an item whose own parent is not the top-level parent, which AIP-231 to AIP-235 require to fail (lying further below it is not enough), duplicate items and malformed fields return INVALID_ARGUMENT.
  5. Atomic mutations are fully authorized before any partial commit is visible.

Synchronous batch methods are atomic; an Operation-returning one may report partial success, and an existing API adopts it through a return_partial_success request field (AIP-233 to AIP-235). The semantics of one request are therefore read from that request. A requirement is item-level when it is checked once for each item: its target is read from the items (requests[] or names[]), each item of a top-level batch is checked on the service root, or it applies because of what one item writes, as a field guard does. Any other requirement is operation-level. In a partial batch, if an operation-level requirement fails, the request is denied and no item runs. Each item's failure is reported at its request index in failed_requests with the status the singular method would return, and if every item fails the operation's error is ABORTED.

Long-Running Operations

AIP-151 defines the shape of an operation and requires the standard Operations service; it does not define who may read an operation. A service lists each Operations method it serves in imported_methods with a handler policy, typically one that binds an operation to its creator and rechecks the originating requirement on GetOperation and WaitOperation, and one that makes ListOperations return only operations the caller may get. Methods it does not serve are listed as unimplemented, so the build can confirm that every Operations method was considered.

4.4 Server-Side and Client-Side Algorithms

The handler and the context endpoint are two uses of one resolver, and the client fold mirrors the handler.

Server: authorizing one request (pseudocode)
authorize(ctx, method, request):
  m = interpretation[method]                    # static, from descriptors (§4.2)
  if m is undeclared: the service enforces it by other means      # only where required is not set
  if m is listed as unimplemented: return UNIMPLEMENTED
  if m is a handler policy: return policy[m.name](ctx, request)
  grants = effective_grants(ctx)                # the only step that varies by caller kind
  reqs = the requirements of m whose condition is unset or true in the request (per item in a batch)
       + the guard of every guarded field the request writes (§4.2, rule 11)
  if reqs is empty: return PERMISSION_DENIED    # nothing to check is never an allow
  if m is a batch method: follow the batch steps of §4.3     # parent check, per item, partial success
  residuals = []
  for r in reqs:
    targets = bind(r, request)                  # canonical names; aliases resolved first
    if targets is empty or one cannot be bound: return PERMISSION_DENIED   # never an empty conjunction
    for t in targets:
      if t has a wildcard:                      # "-" only for a variable the declaration lists
        if m declares item_filter:              # Search: filtered, not refused (§4.3)
          if grants prove no parent t matches can pass r: return PERMISSION_DENIED   # MAY
          residuals.add((r, t, filter: r.key per parent, item_filter per item)); continue
        if r targets a resource:                # wildcard Get: the handler resolves, then decides
          residuals.add((r, t, resolve, nonprojecting at t)); continue
        d = ALLOW if decide() allows every name t matches, else DENY   # always DENY for a nonprojecting key
      else:
        d = decide(grants, r, t)                # ALLOW | DENY | RESIDUAL(predicates)
      if d is DENY: return PERMISSION_DENIED
      if d is RESIDUAL: residuals.add((r, t, d.predicates))
  return PROCEED(residuals)                     # the handler resolves them at its commit boundary
Server: answering QueryPermissionContexts (pseudocode)
query_permission_contexts(ctx, request):
  authenticate; pin one view v of policy and of the descriptor interpretation
  reject an empty anchor list, an anchor with no arm set, an anchor that is not the root or a
    resource name, an exact duplicate, or a malformed min_view: INVALID_ARGUMENT
  if request.min_view names v's authority:      # a floor binds only within one authority (§3.8)
    if its epoch is above v's: return UNAVAILABLE                  # this replica serves a sequence the client has left
    if its epoch equals v's and its revision is newer than v, or unknown or too old to place: return UNAVAILABLE
  grants  = effective_grants(ctx) at v          # same resolver as authorize()
  anchors = resolve aliases; drop those that do not resolve for this caller; merge equal names
  for a in anchors:
    for k in keys that can bind at or below a:  # pattern trie (§3.4)
      if k is nonprojecting at a: continue      # declared private-capable (§3.6)
      partition a at the scopes of the rules for k; classify each cell; merge equal neighbours
        # per enclosing cell, all same-kind children at once; grant-shaped: only if no hole is left
      emit ALLOW, DENY or CONDITIONAL per cell, or nothing
      mark the context row_dependent if it read the anchor's stored fields   # single-resource anchors only (§3.5)
  if profile is grant-shaped: keep only ALLOW claims that have no holes
  merge claims with identical (scope, kind, holes) into one claim over a shared key set
  list in each context the requested anchors it answers, exactly as sent (requested_anchors)
  stamp contract_version, subject_context_id, view metadata, and remaining_ttl = the minimum of
    the remaining lifetime of every proof in the response and of the caller's session or credential
Client: folding a view for one operation (pseudocode)
offer(method, request):
  m = interpretation[method]
  if m is undeclared or cannot be interpreted:                # its effect is unknown
    return HIDE if the credential is read-only, else DEFER
  if m is listed as unimplemented: return HIDE              # the server never serves it
  if m.effect is not read-only and the credential is read-only: return HIDE   # static fact; UNKNOWN is not read-only
  if m is a handler policy: return DEFER
  reqs = the requirements that apply to this request, with field guards, as on the server
  if any r in reqs has a (type, class) outside the credential's ceiling: return DENY   # §3.2; before binding
  if reqs is empty: return DEFER
  results = []
  for r in reqs:
    targets = bind(r, request)                  # canonical names only: an unresolved alias binds nothing (§3.4)
    if invalid or empty: return DEFER
    for t in targets:
      if t has a wildcard and (m declares item_filter or r targets a resource): return DEFER
      snap = newest accepted snapshot with a valid context whose anchor covers t   # all its covering contexts count,
             # the newest for each anchor; a row_dependent context is a snapshot of its own, for t alone
             # a view from other declarations is still used; see §3.7
      results.add((verdict(snap, r.key, t), snap))         # the universal verdict for a wildcard
  if any result is DENY: return DENY                       # denial always blocks
  if every result is ALLOW and all come from one snapshot: return ALLOW
  if any result is UNLOADED, or the allows span snapshots: return UNLOADED
  return CONDITIONAL

Accepting a view

A client keeps one namespace at a time: service, revision authority, epoch and subject context. It accepts a response only if every one of those fields, the contract version and the policy revision is present, remaining_ttl is positive, and the profile is known and not above the one it requested. A change of contract version does not start a new namespace; §3.7 explains what a difference between the server's declarations and the client's means, and what a client can do about it. The client tags each request with its own sign-in session, and discards a reply to a request sent under an earlier one. A changed subject_context_id in a reply to a current request starts a new namespace, and so do a different revision authority and a higher epoch; a lower epoch is discarded (§3.8). An epoch below 1, or a generation or epoch that is not a whole number up to 253−1, makes the response invalid. Every replica that answers a client for one service names the same revision authority; two authorities answering in turn would make the client start over each time. A response must name the service the request asked about; one that names another is discarded without touching any state. On a new namespace the client evicts everything and ignores replies still in flight. A later view in a lower profile than an earlier one is valid: it simply says less, and the client folds it as it is. Within a namespace it rejects a lower generation, and an equal one that names a different revision, or relies on the floor it sent (§3.8). It drops the floor when the authority or the epoch changes.

Validating a context

Before matching, each context is validated as a whole, and a failing context is discarded entirely, every claim for every key: an unknown or unspecified kind, or a reference to a key set the response does not contain; an unset anchor or scope arm, or an anchor that is not the root or a resource name; a scope outside the anchor or outside the key's binding hierarchy; a hole that is malformed, not a strict descendant of its scope, or outside the key's binding hierarchy; a scope arm that does not match what it holds, such as a resource arm holding a collection; a hole or a non-ALLOW claim in the grant-shaped profile; or an overlap between two claims of different kinds for one key. One forgotten hole shows that the producer's other claims cannot be trusted, so nothing from that context is used, including for targets outside the overlap. Overlap between claims of the same kind is redundant, not corrupt, and a key the client's descriptors do not define is skipped (§3.7). Some errors are in what the whole response shares, and discard the response: a key set whose id is below 1 or repeated, or whose keys are unsorted or repeated, two contexts for one anchor, and one requested anchor listed by two contexts. A requested anchor is checked like an anchor, and one listed only by a discarded context is forgotten with it.

Evaluating a target

Each target is evaluated in one snapshot: the newest one that has a valid context whose anchor covers the target, where a snapshot is everything accepted with the same service, subject context, revision authority, epoch, policy revision and contract version. Within that snapshot every valid context that covers the target counts, whichever response it came from, so refreshing a broad anchor does not hide what a narrower one proved at the same revision; for each anchor only its newest context counts, so a refresh replaces what it refreshed; and descendants_omitted in one context says nothing about another. A context marked row_dependent was computed from one resource's stored data, which the policy revision does not track (§3.5). It counts only for that resource, as a snapshot of its own, so no action is decided by combining it with another anchor's answer. Claims from different snapshots are never combined, and an older snapshot is not consulted once a newer one covers the target, so a revocation is never masked. Within the snapshot a claim applies if its key set contains the key, its scope is a segment prefix of the target and no hole is; each hole removes its entire subtree. If ALLOW and DENY both apply the producer is in conflict: the result is UNLOADED, neither is reported as verified, and the client does not loop on refetching. Otherwise ALLOW or DENY wins over CONDITIONAL, whatever the depths of their scopes. A wildcard target is evaluated in the same way, against a context that covers the resource name above its first wildcard, or the service root when the wildcard is in the first ID segment: ALLOW needs one ALLOW claim that contains every name the wildcard matches, and DENY needs a DENY claim that contains at least one.

Folding an operation

A denial for any required target stops the action from being offered, even when the targets were evaluated in different snapshots, each in its newest; holding back an action is the lesser error (§1.1). An allow needs every requirement to bind at least one target and every target to be ALLOW in one and the same snapshot. Targets queried through separate anchors, such as both teams of a Move, qualify when their answers share a snapshot. A batch folds as one unit when atomic. When partial, each item is folded together with the operation-level requirements, and results keep their request indices instead of collapsing to one Boolean.

Listing what is usable

A menu or a tool list asks the inverse question: which operations apply within this scope? It is the same fold run over every method. A method decided by its declarations is listed for a scope when each of its unconditional requirements can bind at or below that scope and its key holds over the whole scope: an ALLOW claim covers the scope and none of that claim's holes covers the scope or lies inside it. A handler-policy method is left to the server, and an unimplemented one is never listed. A claim over company A with a hole at Team C does not list the method for company A, only for its other teams. Asked at the service root with no scope chosen, the answer is every method whose unconditional requirements all have their keys in ALLOW claims, together with the regions of those claims, each a scope minus its holes. That answer is an upper bound: a listed method can still be unusable everywhere, for example when two of its requirements are held in different places, and its conditional requirements and field guards are not considered. A method missing from it is usable nowhere only when every rule is a permit with no condition that cannot raise an error, no context omitted descendants and no key is nonprojecting; otherwise it is only unproven at that anchor (§3.3). An owner-only permit, for example, makes no claim at the root, yet the owner can update their widget.

4.5 End-to-End Walkthrough and Executable Checks

Alice holds two grants: viewer at companies/A and widget-writer at companies/A/teams/B. Team C is confidential, so a forbid on reads is attached there. The following is what the reference model produces.

  1. Her client starts before anything is chosen and queries the service root in the grant-shaped profile. The view contains two claims: ALLOW at companies/A for companies.get and teams.list, and ALLOW at companies/A/teams/B for widgets.create and widgets.update. The client now knows the two scopes where Alice can act. teams.create appears in no claim, so the client has no evidence for "New team" and does not offer it.
  2. The viewer's other read keys are missing from the claim at A. The forbid at Team C makes "reads are allowed everywhere in A" false, and the profile cannot express an exception, so those keys are omitted. Nothing false was said.
  3. She opens Team B. The client queries that anchor and receives one claim there carrying teams.get, settings.get, widgets.get, widgets.list, widgets.search, widgets.count, widgets.create and widgets.update. "New widget" and "Edit" are offered; "Delete" is not, because widgets.delete is absent.
  4. With the scoped-claims profile one query at A is enough. The same read keys arrive as ALLOW over companies/A with the hole companies/A/teams/C, plus DENY at C. The client folds ALLOW for Team B and DENY for Team C without a second query, and the write keys arrive as DENY over A outside Team B.
  5. A wildcard List across the teams of A is not offered. widgets.list does not hold in every team the wildcard matches, because of Team C, so the fold is not ALLOW, and the client offers SearchWidgets instead, which the server filters for her.
  6. The confidential team is still listed. The forbid at Team C does not reach teams.list, which binds to the company, so ListTeams on A returns C to Alice. If C's existence must be hidden from her, she is not given teams.list on A (§4.3).
  7. An upsert needs more. UpdateWidget with allow_missing = true requires widgets.update on the widget and widgets.create on Team B. Alice holds both. A caller with only UPDATE would be refused before any row is read.
  8. Her writer grant is revoked. The server denies the next update as soon as it observes the new revision. Her client may show "Edit" until its view expires or the denial triggers a refresh; the stale view confers nothing.

The executable checks exercise a finite reference model of this specification, not a production enforcement point or a proof about arbitrary policies. They run in the HTML edition on load or with the button, and the same model drives the simulator (§3.9) and the explorer (§4.1). Each check is tagged with the area it covers. Checks marked "Pinned" record behavior that was once questioned in review and found correct, so that it is not changed by mistake. The Markdown export lists every check with its result.

5.1 Steel-Manned Objections & Architectural Boundaries

          
A specification should say where it stops. The objections below mark where this one does.

          
    
            
  • Objection 1 — A scope with very many exceptions. A hole removes a positive proof; a DENY claim proves a refusal. If a server's budget cannot carry a claim together with every hole it needs, it omits that claim, whatever its kind: an ALLOW sent without one of its holes would allow inside the exception, and a DENY sent without one would deny where the caller is allowed. Without other evidence the client folds UNLOADED, never a guess. The grant-shaped profile behaves this way by construction.
    • 
            
  • Objection 2 — Non-hierarchical sharing graphs. In collaboration products where access is attached to each document through sharing links instead of parent folders, almost nothing is uniform across a folder. Boundary: do not use scope-level contexts as the primary model there. Use relationship-based checks (SpiceDB, OpenFGA) with bulk checks and resource lookups [10] [20], and keep contexts for the surrounding workspace chrome.
    • 
            
  • Objection 3 — Client and server can drift. Both sides interpret the same descriptors, and every view names the interpretation it was computed from, so a client can tell when it is behind or ahead of the server. While it is, only a change to an existing method itself can mislead it. During a rollout, old and new servers can also answer in turn, so an operation moved to another access class can be offered by one answer and refused by the server that takes the call (§3.7). What remains is the gap between a declaration and the handler behind it. Test declarations against handler behavior with allowed and denied requests, including wildcard Lists, upserts and partial batches. Anything else that depends on stored state is decided by the handler, and the client cannot fold it; the one place a context reads stored data is the single-resource case of §3.5, under its conditions.
    • 
            
  • Objection 4 — Contexts go stale after a revocation. A client keeps a view for its remaining_ttl, so a freshly revoked user may see an enabled action until the server refuses it. Mitigation: use contexts only to decide what to present, and on PERMISSION_DENIED from any call evict and refresh the matching anchor. The server refuses immediately, and what the frontend shows is corrected at the next refresh.
    • 
            
  • Objection 5 — Class grants expand silently when an RPC is added. They would, without the capability diff. The build reports every key each role gains or loses, and operations that should never be picked up by a class are marked explicit-grant-only (§3.7).
    • 
            
  • Objection 6 — Derived identities tie permissions to the API surface. Renaming a resource's plural or an operation changes keys, and with them any role that names the operation. That is a policy change, and the capability diff reports it as one. Roles that select by class are unaffected. An organization that must keep a legacy vocabulary of permission names maps it to derived keys in server policy, where it is not a client's concern.
    • 
            
  • Objection 7 — Why not send roles to the frontend? A role name means nothing without its definition, exceptions are not part of any role, and exposing role structure couples every client to policy internals. Keys at scopes are what the policy amounts to for this caller, which is all a frontend needs and all it should be able to rely on.
    •
