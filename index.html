Systems Architecture Monograph & Formal Engineering Reference

General Authorization Implementation Patterns & Hierarchical Permission-Context Architectures for Resource-Oriented APIs

A formal analysis of the (Actor, Action, Resource, Context) model, a comparative taxonomy of production authorization systems, and a mathematically sound specification for introspectable AIP/gRPC permission-context projection.

Target Paradigm: Google AIP Resource-Oriented APIs (gRPC / Protobuf) Status: Canonical Technical Reference (v1.4) Date: November 2026

Executive Summary & Key Architectural Conclusions

Core Thesis

Projecting authorization from server to client is quantified partial evaluation over a typed subtree. A positive-only flat set is sound when it emits only proven universal grants, even for non-monotone policies. Downward monotonicity permits using an in-domain pointwise anchor check in place of the universal test. This equivalence is trivial for typical fixed-depth types with no same-type descendants: the in-domain subtree of such an anchor is a single point. For an out-of-domain anchor, the symbolic projector in §3.1 establishes the proof. Scoped claims preserve more useful evidence without turning omissions into denials.

Modern distributed APIs routinely suffer from an authorization impedance mismatch. Backend services enforce access control pointwise—answering whether actor a may perform action k on concrete resource r under context c—whereas user interfaces, API gateways, and batch workflows need to know what an actor can do across an entire logical scope (such as a company or team) without issuing O(N) round trips or exploding cache cardinality across millions of leaf resources.

This reference report establishes two durable foundations. First, it formalizes the general (Actor, Action, Resource, Context) model and catalogs nine production implementation patterns grounded in primary literature—including NIST RBAC [11], NIST ABAC [12], OASIS XACML [13], Google Zanzibar [10], AWS Cedar [14], Open Policy Agent (OPA) [19], SpiceDB/OpenFGA [20], Kubernetes SelfSubjectRulesReview [16], Google Cloud TestIamPermissions [17], and Macaroons [15]. Second, it rigorously stress-tests and formally completes the proposed Hierarchical Permission-Context + Introspectable AIP/gRPC Architecture, resolving its open algebraic questions and refining five key design dimensions:

  1. Resolving "The Missing Piece" (Subtree Projection Algebra): Universal allows carry authority information; existential hints are optional discovery metadata only. Scoped allows, final exclusions, residual conditions and closed coverage distinguish proof from missing evidence.
  2. Formalizing service_root as the Synthetic Internal Service Root (//{service_name}/): The empty-message arm binds global keys to the tagged synthetic root. The display string is not an AIP-122 resource name. A tenant grant cannot match the root; separately cataloged resource permissions may inherit from a service-root policy rule.
  3. Replacing Binary oneof (read | write) with Decoupled Permission Keys + Capability Classes: Classifying every method as strictly read or write conflates additive creation, standard mutation, destructive deletion, and security-plane administration—and cannot express multi-resource operations like MoveWidget. Methods should declare resource-type-qualified opaque permission keys (e.g., widgets.create, teams.update). The compiled catalog records each key’s capability class once (ACCESS_CLASS_READ, ACCESS_CLASS_CREATE, ACCESS_CLASS_UPDATE, ACCESS_CLASS_DELETE, ACCESS_CLASS_ADMIN); methods do not carry a class. This preserves coarse server-side policy authoring (including write-only grants) without privilege conflation.
  4. Fixing Create-vs-Update Collisions & String-Prefix Bugs: In AIP-133 (Create) and AIP-134 (Update), creating a child under //widgets.example.com/companies/A/teams/B and updating //widgets.example.com/companies/A/teams/B itself resolve to the identical target string. Qualifying permissions by resource type and replacing naive string prefixing with a canonical AIP-122 segment-aware pattern trie prevents both cross-method collisions and sibling prefix spoofing (teams/B matching teams/B2).
  5. Decoupling Browser Introspection from Raw gRPC Reflection: Reflection can serve extension descriptors; a build-time catalog makes their interpretation explicit and testable.

Part I. Formal Foundations of the (Actor, Action, Resource, Context) Model

Section Takeaway

Authoritative enforcement evaluates a pointwise decision function D(a, k, r, c), whereas permission-context APIs compute a set-valued abstraction Π(a, c, r0) over an entire resource subtree. Soundness is the universal projection invariant; completeness is optional and freshness is specified separately.

1.1 Formalizing the Authorization Decision Function

A permission context is an advisory snapshot-bound hint, not a credential. The interceptor authenticates, binds targets, and performs only safe preliminary checks. The handler or data layer MUST perform authoritative checks for state-dependent predicates, wildcard lists and partial batch items and own the check-and-commit consistency boundary. A commit-time revision check is sufficient only if it covers every fact on which the authorization decision depended. Never accept a client projection as proof.

Use one internal path form: a service identifier and a flat array of validated path segments. Ancestor means same service and segment-prefix, including equality; never use string-prefix matching. Relative request names MUST be validated against the declared resource pattern and paired with its declared service before evaluation. Full names MUST also match the declared service and pattern. Reject malformed, ambiguous, or alternate encodings unless a service-defined canonicalizer resolves them unambiguously before policy evaluation. Aliases and graph relationships are not prefix edges. Singleton/static segments are literal pattern components. Use a zero-segment, tagged synthetic service root internally; //svc/ is display notation only, not an AIP-122 resource name or AIP-156 singleton. Do not pass it to generated name parsers. Canonical parentage follows AIP-124.

The versioned catalog declares each permission key’s binding patterns (each canonical pattern implies its resource type) and its access class; key spelling does not imply binding. For example, widgets.update binds to the Widget pattern; widgets.create and widgets.list bind to the Widget’s parent pattern, here the Team pattern. If Widget also had a Company-level pattern, those parent-bound keys would list both parent patterns, so one key can bind to more than one resource type. Truly global keys bind only to the tagged service root, not every descendant.

At a fixed snapshot preserve NOT_APPLICABLE, permit, explicit forbid, unresolved predicates and evaluation errors. A proven forbid denies; an unresolved or possibly erroring forbid that could apply blocks an unconditional permit; otherwise a proven permit is required. An unresolved or possibly erroring permit is not sufficient. Here and in §3.1, “proven” includes proving that the relied-on policies cannot raise an evaluation error at any point the proof covers, under the adapter’s declared error policy. Cedar skips policies whose evaluation errors, including forbids, and reports the erroring policies in its diagnostics, so a fail-closed adapter can be built on it. A Cedar adapter MUST declare and test its error policy. For authoritative decisions the recommended local choice is to fail closed when an erroring forbid could apply (including when this cannot be ruled out); this is stricter than native Cedar and can reduce availability. Projection MUST use a fail-closed adapter and the no-error proof obligation: under native Cedar semantics an erroring forbid does not deny, so EXCLUDED could be unsound, and under any adapter an erroring permit does not allow, so ALLOW could be unsound.

Separate authorization target binding from caller-visible validation. Parse only enough to establish the target or authorized enclosing scope; with neither established, return PERMISSION_DENIED without target details. Do not disclose request validation errors before authorization. Determine existence and authorization in one consistent view. For a missing row, a determinable target ALLOW permits NOT_FOUND and a determinable target DENY returns PERMISSION_DENIED. Only if target authorization is indeterminate because that row is absent may a parent fallback run, and only when the resource type declares, for that pattern, a parentReadChildrenKey whose registry entry sets childExistence: UNFILTERED. Such a key must let every holder learn the existence of every child under the parent, which is the assumption behind AIP-211’s “read children” check and AIP-132’s rule that List returns the same results to everyone allowed to list the collection. A proven parent ALLOW of that key permits NOT_FOUND; otherwise return PERMISSION_DENIED. Whenever item visibility under the parent is filtered per item (an itemVisibilityKey the parent key does not imply, or row-attribute predicates), no key qualifies: absent rows and existing rows the caller may not see MUST return the same PERMISSION_DENIED. A parent allow never overrides denial on an existing target. An absent or unbindable request field is not an absent row.

In this example widgets.list does not qualify: §4.1 filters List results per item by widgets.get, so a widgets.list grant does not reveal which widget IDs exist. The fixture therefore declares no parentReadChildrenKey for Widget. A GetWidget on an absent widget whose widgets.get decision depends on row attributes returns PERMISSION_DENIED, exactly as for an existing widget the caller cannot see; following AIP-211, related permission checks do not “help out”. A service that wants NOT_FOUND there must declare and deliberately grant a key with unfiltered child-existence visibility. When a qualifying key is declared, check the schema-derived parent name, even if it has no row or is a local non-represented prefix, provided the parent decision can be proven without that row. Do not recurse: if the parent, its binding key, or a definitive parent allow cannot be established, return PERMISSION_DENIED. For top-level types the parent is the tagged service root; a fallback there requires a declared root-bound key. No such key is assumed. Ordinary NOT_FOUND does not trigger the PERMISSION_DENIED refresh path.

Name collisions. Any method that can make a name collide with an existing resource MUST apply the same rule: Create with a client-assigned ID (AIP-133), Move or rename to a destination name, each BatchCreate item, and an upsert where one is supported. First authorize the operation’s own requirements. Then, if the name is taken, check in the same consistent view whether the caller may see the existing resource under its type’s registry visibilityKey (here widgets.get). Return ALREADY_EXISTS only if that check proves ALLOW; otherwise return PERMISSION_DENIED, as AIP-133 requires, with the same status payload as any other denial on that method. In an atomic batch a hidden collision fails the whole batch with PERMISSION_DENIED; in an LRO partial batch it is that item’s PERMISSION_DENIED.

Upsert (AIP-134 allow_missing). AIP-134 lets Update create a missing resource while requiring only the update permission, and suggests IAM conditions to block creation. A protected requirement set cannot express this: whether a create check applies depends on whether the row exists at commit. For v1 the build MUST reject a protected disposition on any method whose request message has an allow_missing field. A service that supports upsert MUST bind that method to a named handler policy that requires the update key on the target and, whenever the row is absent at commit, the create key on the parent, checked in the same consistent view as the commit; the name-collision and missing-row rules above apply. The client defers named handler policies, so an update-only grant never appears to the client as a create capability, and the server cannot create through it.

Error payloads. AIP-193 requires an ErrorInfo on every error and requires every dynamic part of the message to appear in ErrorInfo metadata. Disclosure rules therefore cover the whole status: code, message, ErrorInfo reason, domain and metadata, and any other details. Cases that must be indistinguishable (an absent versus a hidden row, a hidden duplicate versus any other denial, an undisclosable versus a missing anchor) MUST produce the same code, message, reason, domain, and metadata keys and values. Echo only values the caller supplied, never a resolved canonical name, alias target, owning parent or policy identifier, and add no details (such as ResourceInfo or DebugInfo) that differ between those cases.

1.2 Pointwise Evaluation vs. Subtree Permission Projection

Pointwise evaluation answers a single ground query: "Can Alice execute widgets.update on //widgets.example.com/companies/A/teams/B/widgets/w1 right now?" By contrast, Permission Projection fixes the actor-context pair (a, c) and a resource prefix anchor r0 ∈ Rprefix (including the service root //{service_name}/), and asks for a compact summary of D(a, k, r, c) across all actions k ∈ Kreach(r0) and all descendant resources r ∈ Subtree(r0) = { r ∈ R | r0 ⪯ r }, where ⪯ denotes the canonical AIP ancestor-of partial order.

R is the set of schema-valid potential resource names, independent of stored rows. Each permission restricts it to its binding domain; root-bound keys use the tagged root separately.

ALL/NONE/MIXED is a lossy summary: MIXED does not locate exceptions. Explicit regions are lossless only where all decision regions are representable and disclosable.

1.3 Soundness, Completeness, Monotonicity, and Freshness Invariants

Soundness is relative to a fixed actor, policy snapshot, catalog and trusted context. Completeness is not required: withheld evidence remains UNLOADED. TTL limits reuse but does not provide causality.

Theorem 1.1. Fix actor, context, revision and key. On its binding domain, let A(x) mean unconditional pointwise allow (true for all unresolved fact assignments admitted by the model). Define U(s) to mean A(x) for every domain point x at or below s. A is downward-monotone iff A(s) = U(s) at every in-domain s. Reflexivity proves U(s) ⇒ A(s); downward monotonicity proves the converse. Equality implies A transfers to every in-domain descendant. This is not a theorem about arbitrary emitters or out-of-domain anchors. Exact universal emission is sound and universal-complete even for non-monotone policies; it need not expose every pointwise allow. An empty emitter is sound but generally incomplete. Child-only grants can require narrower fetches even under monotonicity.

Part II. General Authorization Implementation Patterns Taxonomy

Section Takeaway

No single authorization pattern dominates all workloads. Production architectures compose a policy representation model (RBAC, ReBAC, ABAC, Capabilities) with an evaluation topology (pointwise PEP/PDP, bulk check, subtree projection, or partial-evaluation data filtering) matched to the workload's resource graph, latency budget, and revocation strictness.

2.1 Catalog of Nine Production Implementation Patterns

1. Centralized Enforcement (PEP / PDP / PIP / PAP Architecture). Standardized by OASIS XACML 3.0 [13] and NIST SP 800-162 [12], this pattern decouples request interception (Policy Enforcement Point) from decision evaluation (Policy Decision Point) and attribute retrieval (Policy Information Point). It provides uniform auditing and language-agnostic policy governance across microservices (e.g., Envoy ext_authz [22] calling OPA or Cedar). Its primary trade-off is network-hop latency and availability coupling on the critical request path, mitigated by sidecar/in-process PDP deployment.

2. Resource-hierarchy policy inheritance with RBAC role bundles. NIST hierarchical RBAC [11] describes role hierarchies, not resource trees. Services such as Google Cloud IAM [17] and Azure RBAC [24] attach policy or role assignments to resource hierarchy nodes. Allow grants are additive under the applicable policy model; CEL conditions may vary across descendants. Google Cloud IAM policy changes typically propagate in about two minutes, but can take seven minutes or more.

3. Resource-Level ACLs & Relationship-Based Access Control (ReBAC). Pioneered at global scale by Google Zanzibar [10] and implemented in open-source engines like AuthZed SpiceDB and OpenFGA [20], ReBAC models authorization as graph reachability over stored relation tuples (object#relation@user) with userset rewrite rules (union, intersection, exclusion, tuple-to-userset). Zanzibar achieves <10 ms p95 latency across trillions of tuples and prevents the "new enemy" stale-ACL problem using opaque causal consistency tokens called zookies (called ZedToken in SpiceDB) [10] [20]. ReBAC excels at fine-grained, non-hierarchical sharing, but graph traversal makes high-fanout list filtering and coarse prefix projection computationally expensive unless backed by materialized permission views (e.g., AuthZed Materialize) [20].

4. Attribute-Based & Policy-Based Access Control (ABAC / PBAC). Formalized by NIST SP 800-162 [12] and realized in Open Policy Agent (Rego) [19], Amazon Verified Permissions (Cedar) [25] [14], and Google Cloud IAM Conditions (CEL) [17], ABAC evaluates boolean predicates over subject, resource, action, and environment attributes (e.g., time-of-day, data classification, resource ownership). Cedar specifically restricts language expressiveness (no unbounded loops, explicit permit/forbid semantics) to guarantee termination and support SMT-backed static policy analysis [14]. ABAC eliminates role explosion, but attribute volatility lowers cacheability and complicates static permission projection.

5. Scoped Permission Projection & Self-Review APIs. Used directly to drive permission-aware UIs and CLIs without O(N) pointwise checks. Real-world precedents include Kubernetes SelfSubjectRulesReview (authorization.k8s.io/v1, which enumerates a caller's effective resourceRules within a namespace and explicitly returns an incomplete boolean when an external authorizer cannot project rules) [16], Google Cloud IAMPolicy.TestIamPermissions (which intersects a caller-supplied candidate permission set against effective permissions on a resource) [17], and AWS IAM SimulatePrincipalPolicy [18]. Kubernetes warns about incomplete results and confused-deputy risks; Google Cloud warns that TestIamPermissions is for permission-aware tools and may fail open. Neither substitutes for authoritative enforcement [16] [17].

6. Batch & Bulk Authorization Evaluation. Bulk checks amortize RPC overhead. SpiceDB CheckBulkPermissions supports ZedToken consistency controls; OpenFGA BatchCheck provides correlation IDs and MINIMIZE_LATENCY / HIGHER_CONSISTENCY preferences, not a snapshot token or a shared-snapshot guarantee [20].

7. Authorization-Aware List & Data Filtering (Partial Evaluation). Authorize List invocation and visibility of each item separately. Parent scopes alone cannot exclude forbidden descendants. Use equivalent query authorization predicates or an authoritative bulk check of candidate rows; page sizes, counts and tokens MUST NOT expose rejected candidates. OPA’s classic /v1/compile returns Rego ASTs; /v1/compile/{path} supports target-specific SQL/UCAST filter compilation [19]. Wildcard targets defer local evaluation.

8. Delegated Capability Tokens & Attenuation. Macaroons [15] can be attenuated by appending chained HMAC caveats. Verification is O(number of caveats) plus the cost of evaluating those caveats. Short TTLs and discharge caveats can constrain offline use. Biscuit [23] offers offline attenuation with public-key signatures and Datalog-based policies.

9. Field-Level & Long-Running Operation (LRO) Authorization. AIP-161 field masks select fields; a separate policy authorizes them. AIP-151 [5] defines the operation shape, not permissions. For audit exports, this report’s local policy binds the operation to its creator and service and rechecks audit.export on GetOperation and WaitOperation. ListOperations returns only operations the caller may get. CancelOperation and DeleteOperation are disabled for this example. Register these as named authoritative policies if exposing the respective Operations RPCs.

IAM Allow inheritance is downward-monotone only where attached conditions preserve descendant truth. CEL conditions can break it even without IAM Deny.

Cedar’s guarantees concern termination and analyzability, not a latency bound.

Part III. Deep-Dive Analysis & Formalization of the Permission-Context + Introspectable AIP/gRPC Architecture

Section Takeaway

Typed, snapshot-bound projection can reduce repeated UI checks for reusable scopes; §3.5 states the assumptions. Backend authorization remains authoritative.

3.1 Resolving "The Missing Piece": The Scoped-Grant Algebra

For key k and anchor s, the relevant domain is all schema-valid potential names matching one of k’s declared binding patterns at or below s, including names not yet allocated. For global keys the domain is the tagged root alone. Do not enumerate existing rows to prove a universal. As a UX policy, emit no universal claim for a schema-empty domain, even though the universal is vacuously true.

Supported projector. Compile finite ancestor-inherited static permit and forbid rules over canonical prefixes, with optional target predicates. Pin a single snapshot for all inputs used by the proof. Partition a requested subtree symbolically at catalog/rule prefix boundaries: for each boundary include the remainder of its region outside more specific boundaries. Include the open remainder for future names, not merely known children. Intersect every cell with the declared binding domain; omit cells proven empty. Static rule applicability—whether a rule’s scope covers the cell—is constant within each resulting cell. Applicability ignores target predicates, which can still vary from point to point inside a cell; step 2 handles them. If the compiler cannot establish this (for example with unmodeled aliases, relationship joins or dynamic scopes), return no claim for the affected region. For each cell:

  1. Emit excluded only for a proven override-final explicit forbid throughout the cell: one that is unconditional on the cell and proven free of evaluation errors there (§1.1).
  2. Otherwise emit allow only if (a) an applicable static permit is unconditional on the cell—it has no target predicate, or its predicate is proven true at every in-domain point of the cell with every fact it reads pinned to the snapshot—and is proven free of evaluation errors there, and (b) every possible forbid is ruled out, including forbids that could apply through a predicate or an evaluation error. An owner-only permit with no forbids therefore yields conditional (step 3), never allow. This sufficient test can omit legitimate allows.
  3. If remaining modeled predicates or possible evaluation errors can affect the result, emit conditional if safe to disclose. The client does not execute policy predicates.
  4. If the full rule set proves denial by default throughout a cell (no permit can apply at any in-domain point), emit closed coverage for it. Otherwise omit the cell. Budget, dependency and disclosure failures do not establish closed coverage.

A region is a schema prefix (a resource name, a collection prefix, or the tagged root) minus zero or more strict-descendant schema prefixes, its holes (§4.1). The full subtree at an anchor is a region with no holes. Regions are typed by key. Within one context, two claims of different kinds (ALLOW, EXCLUDED, CONDITIONAL, CLOSED) for the same key MUST NOT overlap. Overlap and emptiness are computed on the intersection of the regions with the key’s binding domain, so a remainder that contains no potential names of the binding patterns—for example a Team minus its AIP-156 singleton, for a key bound only to the singleton—is empty and overlaps nothing. Coalesce cells only if their union exactly equals the replacement region in the binding domain. Within a snapshot the proof obligations are: allow ⇒ authoritative allow, excluded ⇒ final explicit denial, closed ⇒ authoritative denial. CONDITIONAL means this projection did not resolve a predicate; it asserts no decision. Another compatible context may prove a decision for the same target and key. Absent regions also assert neither. CLOSED positively proves default denial for a stated key and region; a response’s presence proves no coverage. These implications prove soundness of the client fold below; completeness is not required. Arbitrary policy programs have no exact projection guarantee under this contract.

Disclosure. Check authorization to disclose every anchor, named scope, hole and emitted fact independently of the projected permission. Coarsening may only drop claims or exact-union-merge compatible claims. It MUST NOT expand a universal or drop a hole in isolation. Build output without exposing private boundary names or whether hidden exceptions were present; omission alone is not a general noninterference proof. If C cannot be named, do not send an allow with a hidden hole at C. Withdraw the enclosing proof and affected coverage; publish independently proven, disclosable regions only under a disclosure policy that permits those facts. Where an existence-insensitive response cannot be guaranteed, use a uniform nonprojecting response for that class of queries. Apply the same disclosure rules to hints, errors (the whole status payload, §1.1) and diagnostics. For missing rows apply §1.1: only absence-caused indeterminacy invokes the parent fallback. Do not reveal existence or conflict details to unauthorized callers.

Consequence for ancestor claims. Read literally, the rules above remove ancestor proofs wherever a private override is possible. Suppose an undisclosable forbid (or any rule that would block a permit) might exist under anchor A for key k. If it exists, ALLOW(A) is unsound; hiding its existence requires the same output when it does not exist; so neither ALLOW nor CLOSED could ever be emitted over A for k. This specification resolves the conflict at authoring time. A forbid override MUST NOT be created or kept at a scope that any holder of an affected ancestor grant for the same key cannot see, and the policy store checks this whenever either the override or the ancestor grant is written. Every override inside a projected ancestor region is then disclosable as a hole, and ancestor projection keeps its value. A deployment that cannot enforce the authoring rule MUST declare the affected keys and scopes nonprojecting and withhold ancestor ALLOW and CLOSED for them uniformly, whether or not an override exists. Hiding only the override’s name while revealing that an exception exists would leak one bit per anchor and key; it is not permitted unless declared as a named disclosure exception.

3.2 Resource Hierarchy vs. Authorization Graphs, Prefixes & External Aliases

AIP-124 specifies that every resource instance has at most one canonical parent in an acyclic hierarchy (AIP-124). This specification introduces the synthetic internal service root //{service_name}/ (e.g., //library.googleapis.com/ or //widgets.example.com/), whose relative segment list is empty ([]) and which acts as the top prefix of every resource in that service. Real-world authorization, however, frequently involves non-hierarchical relationships: a user belongs to a Group, a Project is linked to a Billing Account, or a Widget is shared directly with a cross-company collaborator. Figure 2 contrasts these two topologies.

Segment-Aware Typed Pattern Matching vs. Naive String Prefixing

Counterexample 1 — Naive String Prefix Collision

If a client checks target.startsWith(anchor), a grant on //widgets.example.com/companies/A/teams/B erroneously matches //widgets.example.com/companies/A/teams/B2 and //widgets.example.com/companies/A/teams/Billing/widgets/w9. Appending a slash fixes those sibling cases but still fails against uncanonicalized names: …/teams/B/%2E%2E/C starts with …/teams/B/, yet a downstream decoder may normalize it to …/teams/C; doubled or trailing slashes create alternate spellings of one name; and the same relative path under another service (//billing.example.com/companies/A vs //widgets.example.com/companies/A) is a different resource. AIP-122 says resource IDs should avoid characters that need URL-escaping, so the canonicalizer can reject such spellings outright.

Remedy: All matching on both server and client MUST parse canonical AIP-122 full resource names into a service and flat validated segments (service_name, [segment_1, …, segment_n]) [2], where the synthetic internal service root //{service_name}/ is only display notation for the tagged (service_name, []) root. A fetched anchor s covers target r if and only if: (1) s.service_name == r.service_name, (2) len(s.segs) ≤ len(r.segs), and (3) for every index i < len(s.segs), s.segs[i] == r.segs[i] (with strict rejection of empty inner segments, ., .., or unescaped / inside IDs). Notice how cleanly this handles //{service_name}/: its empty segment list [] is a prefix of every resource in the service, while no non-root tenant scope (length ≥ 1) can ever be a prefix of [].

External / Non-Represented Anchor Resources & Aliases

The author's insight that queried anchors such as //widgets.example.com/companies/A may be non-represented local parents not directly managed by the target API (e.g., widgets.example.com manages widgets under companies/{company}/teams/{team}/widgets/{widget} without implementing GetCompany) is fully compatible with file-level resource definitions (option (google.api.resource_definition)), which are documented in AIP-4231 and checked by the AIP-123 lint rules [3]. Static reachability indexes each permission key under every declared binding pattern (e.g., companies/*/teams/*/widgets/*) under the service root node //widgets.example.com/ of a Segment Pattern Trie. A query walks the anchor’s segments, following both the literal edge and the * edge wherever a pattern has a static segment at that depth, and collects every key bound at the anchor node itself (Subtree includes equality, so teams.update is reachable from …/teams/B) and at every descendant node. Querying //widgets.example.com/companies/A walks companies → * in O(depth + traversal/output) time, while querying //widgets.example.com/ starts at the root node and reaches all indexed keys, including separately indexed root-bound keys. If an API allows aliases (e.g., companies/acme-slug aliasing companies/A), the server MUST canonicalize aliases to immutable resource IDs before both policy evaluation and cache keying; otherwise, an explicit deny on companies/A can be bypassed via its alias.

3.4 gRPC Reflection vs. Build-Time Compiled Descriptor Catalogs

Reflection can serve the descriptors defining custom option extensions. Consumers must resolve those descriptors and interpret and validate the extensions. A compiled catalog makes this interpretation explicit, deterministic and testable, and avoids requiring browser clients to implement the reflection transport and descriptor processing.

Recommended Dual-Distribution Pattern: Use the .proto options and the required versioned server registry (§4.1) as declared co-sources, and run a lightweight protoc plugin at CI/build time to emit a canonical, versioned Authorization Descriptor Catalog (normalized JSON) containing the pre-compiled Segment Pattern Trie, method permission requirements, and target field selectors. Serve this catalog from an immutable, content-hashed CDN/HTTP endpoint (e.g., GET /v1/authzCatalog?version=sha256) for web/mobile clients, while retaining standard gRPC reflection for internal CLI and service-to-service introspection.

3.5 Caching Architecture, Cardinality Math, and Mandatory Backend Enforcement

Key shared proof entries by service, catalog version, projection-dependency revision, effective principal, canonical claims digest, tagged canonical anchor, and include_ui_hints. A dependency revision covers inherited changes above the anchor and changes below it that affect universal proofs, plus referenced data and disclosure rules. A service-wide monotonic revision is the conservative baseline; a tenant revision alone cannot key a cross-tenant root. Resolve the current revision from an authoritative view before using its cache namespace; compute and label a new entry from that same view.

Catalog the policy-relevant claims: effective principal and delegation chain, tenant, session scopes, authentication assurance, and any stable network/device posture used by policy. Authenticate inputs server-side. Version the serialization, sort sets, preserve ordered claims, type values, and distinguish absent from empty. An unmodeled input that can affect a claim makes the claim uncacheable or conditional. Do not hash wall-clock time per request: cap reuse at the next provable time-policy boundary, or do not cache the time-dependent proof. Cap proof expiry by relevant policy-data deadlines; apply the session/credential cap per response, never in a shared entry.

Session-independent entries. Cache only session-independent proofs. A shared entry MUST NOT hold a subject_context_id, session identifier, pinned-view snapshot metadata or session-capped TTL. On every response, including cache hits, stamp the current caller’s subject_context_id, the pinned view’s snapshot metadata, and remaining_ttl = min(remaining proof lifetime, remaining lifetime of this caller’s session or credential), measured as below. Cache ui_existential_hints separately from proofs, under a key that also includes the data revision of the rows they summarize. A hint names a permission key k such that, in the pinned view, at least one stored row at or below the anchor is visible to the caller under its type’s visibility key and is pointwise allowed for k. Hints therefore describe only rows the caller could already list, never potential names, and disclose nothing List would hide. They are discovery metadata and never authorize.

Measure remaining_ttl immediately before sending the response, from the original expiry. Receipt, persistence and replay MUST NOT restart it. Each cache tier uses exactly one expiry model. Node-local server caches store a monotonic-clock deadline. Shared server caches store an absolute expiry computed at production and require a documented maximum clock skew between writers and readers; a reader subtracts that bound and its read delay from the remaining lifetime and treats a non-positive result as a miss. The wire carries only the relative remaining_ttl. A client converts it to a monotonic deadline measured from the start of its fetch, never extends it across persistence or replay, and rejects a context whose remaining_ttl is zero or negative. Epoch changes affect server cache lookup; they do not reach clients without push, polling, expiry or revalidation. Refresh on authoritative PERMISSION_DENIED without treating a refresh as authority to retry a mutation; expiry/revalidation also discovers newly granted permissions the UI had hidden. This is bounded staleness only given bounded publication and expiration assumptions, not causal consistency or an immediate revocation guarantee for UI hints.

Section Takeaway

A production-ready specification requires three tightly coupled artifacts: (1) Protobuf custom option extensions attached to AIP methods (with service_root {} as the tagged root), (2) a Service-Name-scoped PermissionContextService RPC contract, and (3) deterministic server projection and client matching algorithms sharing one compiled catalog.

The reference block is combined for readability. Production may split the annotation definitions into annotations.proto and the RPC/TTL messages into a service proto that imports it, so annotation consumers need not import duration.proto.

A service_root arm is the sole root encoding; reject a string such as //svc/. Validate nonempty service, catalog, snapshot and subject identifiers and the snapshot namespace. Concrete targets must match the permission’s binding domain. Claim prefixes and holes are full schema prefixes: a full resource name, or a full collection prefix ending in a collection literal of one of the key’s binding patterns (in the full_collection_prefix arm, or as a hole string); a claim prefix may also be the tagged root. Anchors are always the tagged root or a full resource name, never a collection prefix. Collection prefixes are needed for branching patterns: with companies/{company}/widgets/{widget} and companies/{company}/teams/{team}/widgets/{widget}, a claim may cover …/companies/A/widgets, or cover …/companies/A with the hole …/companies/A/teams. Strict AIP-122 parsers reject collection prefixes, so validate both forms against the catalog’s pattern trie, never with generated resource-name parsers. Enforce anchor containment and strict-descendant holes. A Widget key may therefore have a Company prefix. A root-only key has no nonempty descendant region. A prefix or hole is valid only if it is a prefix of at least one of the key’s binding patterns (or the tagged root, for a claim prefix). Evaluate emptiness and overlap on the intersection with the binding domain (§3.1). All claim scopes belong to the explicitly requested service. An external name such as //org.example.com/companies/A is not a local prefix: declare a local anchor and a trusted mapping where available; defer if it cannot preserve policy semantics. Reject empty relative paths or leading, inner, or trailing empty segments, dot segments, percent encodings, and slash or backslash inside identifiers; use only the declared canonical identifier grammar. The service separator and tagged root are not path segments. Unknown or incompatible data MUST NOT produce an allow. If an earlier wire contract shipped, reserve retired tags and names in the applicable schema and use a new version or new tags where meaning changed; reservations alone cannot repair repurposed tags. Prior deployment status is not established by this report.

For v1 every RPC MUST declare a nonempty protected AND set or a named authoritative handler policy (including intentionally public, authenticated-self and exempt methods). Omission fails the build and is never an allow. Protected requirements are only for policy proven decomposable into the declared independent checks; methods with joint predicates MUST instead use a named authoritative handler policy. The client defers named handler policies. The build rejects a protected disposition whose request message has an allow_missing field (§1.1). Both permission-context RPCs require authentication and apply disclosure to the authenticated subject. OR-groups are future work requiring defined unknown/error semantics. Rule attachment, key binding, and method disposition are independent: a root-attached rule reaches descendants only for descendant-bound keys; audit.export binds only to the root.

The Authorization Descriptor Catalog is a versioned normalized JSON format, not ProtoJSON. Its top-level fields are schemaVersion, catalogVersion, service, keys, expansionTable, resourceTypes and methods. Each key maps to a binding and an accessClass (ACCESS_CLASS_READ, ACCESS_CLASS_CREATE, ACCESS_CLASS_UPDATE, ACCESS_CLASS_DELETE or ACCESS_CLASS_ADMIN); access classes live only here, never on method records. A binding is either serviceRoot (root-only keys) or patterns: a nonempty list of canonical patterns, each of which implies its resource type. A resource-bound key lists its type’s patterns; a parent-bound key such as widgets.create or widgets.list lists the parent patterns of every Widget pattern, which may span several types. Reject conflicting definitions. Resource types declare all canonical patterns, their non-represented local parents, a visibilityKey (used for name-collision checks), and, per pattern where supported, a parentReadChildrenKey that the registry marks childExistence: UNFILTERED. REJECT ambiguous canonical matches with inconsistent parents or fallback keys. The tagged root is the structural parent of top-level resource types. Method records are keyed by fully qualified RPC name and contain disposition plus requirements or handlerPolicy; List records also declare itemVisibilityKey. A requirement has permission and exactly one binding: serviceRoot or path (selector, targetKind, wildcardParentVariables). A protected method record carries batchSemantics. Optional method-level metadata compiled from the registry—effectiveParent, itemCorrelation, emptyInputAuthorization, wildcardInvocationAuthorization and wildcardGet—describes fallback, item identity and wildcard policy, not selector syntax. effectiveParent declares the top-level selector, optional item selector (or the parent derived from the bound resource name), and whether fallback is permitted. itemCorrelation declares either repeatedMessageAncestor or stable item ID selectors for every participating repeated source. Reject duplicate or unmatched IDs. The per-method records in the explorer include their fully qualified method name. Compile against descriptors and the declared server registry, normalize and sort map keys deterministically, and preserve declared requirement order. The explorer shows individual method records.

The versioned server registry is a JSON co-source: schemaVersion; keys (binding and accessClass by key); resourceTypes (canonical patterns, nonRepresentedLocalParents, visibilityKey, and per-pattern parentReadChildrenKey with its childExistence declaration); expansionTable (grant name to key array); methodMetadata by fully qualified RPC (effectiveParent, itemCorrelation, emptyInputAuthorization, wildcardInvocationAuthorization and wildcardGet); handlerPolicies (registered implementation identifiers); importedMethodBindings (fully qualified imported RPC to a disposition record); and externalIdentityMappings (local prefix to external service/pattern plus registered mapping implementation, when supported). Bind the registry version to the compiled catalog and include mapping changes in proof dependencies. Fail on unknown policy identifiers, ambiguous or conflicting declarations, unresolved referenced keys and unbound RPCs. Registry-side disposition bindings are for imported RPCs (e.g. Operations, reflection and health); do not copy upstream protos. Bind only served methods, and require an explicit named policy for infrastructure RPCs not handled declaratively.

Selectors use protobuf descriptor field identifiers, dot traversal through messages and [] on repeated fields to expand elements. The terminal value MUST be a string resource name. Absent values fail binding unless explicit effectiveParent metadata supplies a fallback; do not conflate an empty result with permission. Correlate via one shared repeated-message ancestor or explicit stable item ID, never by zipping arrays. Resolve each item’s parent from its own field, or from the top-level parent when the item omits it and the AIP permits omission (AIP-233). A top-level parent containing - is never inherited: an item that omits its parent under a wildcard top-level parent is rejected. When items carry full names (AIP-231 BatchGet, AIP-234 BatchUpdate, AIP-235 BatchDelete), effectiveParent.itemParentFrom derives each item’s parent from its bound name, and that derived parent is compared with a concrete top-level parent. Accept - only as the ID segment of a template variable named in wildcard_parent_variables. The build validates every named variable against each binding pattern of the requirement’s key: it must occur in at least one pattern, and wherever it occurs it must name an ID segment of the bound parent, never a collection literal or static segment; a pattern in which it does not occur accepts no wildcard. Wildcard variables are accepted only on List methods, unless registry methodMetadata.wildcardGet declares both that the method documents - and that IDs are unique across parents, as AIP-159 requires for Get. Reject PARTIAL_BEST_EFFORT for every AIP-231 BatchGet and for synchronous AIP-233 BatchCreate, AIP-234 BatchUpdate and AIP-235 BatchDelete. The operation has one batch_semantics setting; UNSPECIFIED means atomic conjunction. Atomic mutations MUST be fully authorized before any partial commit is visible.

Batch status order. Authorize before validating, scope by scope: first the concrete top-level parent when any requirement or the effectiveParent comparison uses it, then each item’s bound targets. If any check the operation needs fails, a synchronous batch returns PERMISSION_DENIED with no detail identifying the failing item. Only when every bound target is authorized does the server validate and return INVALID_ARGUMENT for a parent/item mismatch (which AIP-233 and AIP-234 require to fail), duplicate or unmatched item IDs, or other malformed items. An item whose target cannot be bound at all has no authorizable scope: return PERMISSION_DENIED unless the concrete top-level parent is authorized, in which case return INVALID_ARGUMENT. In PARTIAL_BEST_EFFORT (LRO) batches, requirements not correlated to an item—such as a top-level parent check—are operation-level: if one fails, the whole request returns PERMISSION_DENIED and no item runs. Item-correlated requirements are then folded per item, and each item’s failures are reported only in that item’s result.

Do not allow an empty target set by vacuous conjunction. For AIP-231 BatchGet, if requests=[] (or the batch’s repeated names input is empty), and likewise for empty AIP-233 BatchCreate, AIP-234 BatchUpdate and AIP-235 BatchDelete inputs (AIP-233 and AIP-234 say requests should be required), first authorize the declared enclosing parent or scope, then return INVALID_ARGUMENT to the authorized caller. If that scope or its authorization cannot be established, fail closed; do not infer a parent permission key from the item key. The binding for the enclosing check is method-specific and MUST be declared in registry methodMetadata as emptyInputAuthorization (permission plus parent/scope binding). No such key is assumed for undeclared methods.

The versioned expansionTable maps coarse grant names to concrete keys. In this example, write-only expands to widgets.create and widgets.update, not read, delete or admin keys. Expand at compilation and check concrete keys only at the PEP. For Lists, authorize invocation separately from item visibility. Use a query predicate equivalent to per-item authorization or authoritative bulk checks on candidates. Parent authorization alone is insufficient; counts, tokens and page sizes MUST NOT disclose rejected candidates.

4.2 Server-Side Projection & Client-Side Evaluation Algorithms

Select contexts from the current service, subject/session, catalog and one compatible snapshot; exclude expired contexts. For multi-anchor operations request all needed anchors with BatchGetPermissionContexts; use the batch only if every returned context matches the response’s top-level pinned-view fields (revision, authority, epoch, generation, subject context, catalog and service), and reject the whole batch otherwise. A missing anchor is missing evidence, not denial. Snapshot identifiers must identify the same authoritative view, not merely equal tenant counters. Apply region prefix and hole matching to the validated binding target. A loaded ancestor with no applicable claim is not exhaustive. Evaluate in this order:

Keep one active subject_context_id and snapshot namespace (service, revision authority, epoch, catalog, subject-context). On a verified subject/session or namespace change, evict that view and reject in-flight replies from it. When generations are used, the revision authority MUST assign them monotonically to pinned views within the namespace and MUST NOT exceed 253−1; compare them only for replacement, never for proof compatibility. ProtoJSON serializes uint64 as a decimal string, so clients parse it as an integer (BigInt, or Number after the bound check), reject a value outside the bound, and compare numerically, never as strings (as strings, “10” sorts before “9”). Use the last accepted coherent fetch for the required anchors. Within the same namespace reject a lower generation. When generation is unavailable, allow at most one permission-context fetch in flight per namespace; start the next only after the previous one settles or is abandoned, and ignore replies to abandoned fetches. Otherwise a lagging replica serving a later request could install an older view. Equal ordered generations must identify the same pinned view or be treated as incompatible. Never fill gaps from a different snapshot; fetch a coherent batch or defer. Do not adopt a changed subject_context_id merely from an unsolicited or delayed response; re-establish the view through a current authenticated fetch.

Before matching, validate each context as a whole. Discard the entire context—every claim for every key—and defer if needed when it contains KIND_UNSPECIFIED or unknown claim kinds; unset Scope arms, or a collection prefix used as an anchor; a malformed hole, or a hole that is not a strict descendant of its claim prefix; a prefix or hole outside the requested service, outside the context’s anchor, or outside the key’s binding-pattern hierarchy; or any overlap between two claims of different kinds for the same key. Compute overlap and emptiness on the intersection of the regions with the key’s binding domain; a remainder that holds no potential names of the binding patterns (for example after an AIP-156 singleton hole) is empty and overlaps nothing. A discarded context contributes nothing, including to targets outside the overlap, because one forgotten hole shows that the producer’s other claims cannot be trusted. Same-kind overlap is redundant, not corrupt. Cross-context residuals follow the precedence below. Membership requires the key and typed target to match, the claim prefix to segment-prefix the target, and no hole to segment-prefix the target. Each hole cuts its entire subtree.

  1. Gather every claim matching the target and key from compatible contexts at the selected snapshot.
  2. If ALLOW overlaps CLOSED or EXCLUDED, record a producer conflict, discard the conflicting claims for this evaluation, and return UNLOADED. Do not report either decision as verified; do not loop on automatic refetch. Backend enforcement remains fail-closed.
  3. Otherwise a matching ALLOW returns ALLOW; a matching CLOSED or EXCLUDED returns DENY. A definitive proof supersedes CONDITIONAL regardless of anchor depth.
  4. Otherwise return CONDITIONAL if present, or UNLOADED if not.

UNLOADED and CONDITIONAL defer to the authoritative endpoint or a newly acquired compatible context. ALLOW governs presentation only. Independent per-item hints may carry different snapshots; never fold them into an atomic ALLOW.

Resolve each requirement before folding. For an atomic operation, a definitive DENY for any required target blocks the allow hint, whether or not its snapshot matches the others in the current namespace; a conservative hint is harmless. An allow hint requires every requirement to bind at least one target and every target to be ALLOW under one compatible snapshot; a requirement whose repeated selector expands to zero targets defers the whole operation. Otherwise defer. Move applies this to each independently bindable check (for example source and destination). Policies that relate resources jointly are named handler policies (§4.1) and are deferred before any folding. For partial batches, fold per item and preserve stable item identifiers or request indices; do not reduce the results to one Boolean. AIP-234 BatchUpdate is atomic when synchronous; use the LRO form for supported partial success and communicate per-item failures there. The server rechecks against the actual operation and its consistency boundary regardless of client results.

4.3 End-to-End Walkthrough: Company A, Team B, and Team C

With a Team B-only grant, a service-root response that omits the grant and makes no closed claim yields UNLOADED on B. With an unconditional grant on B and an owner-only grant on C, the Company context can report ALLOW on B and CONDITIONAL on C. An owner-only grant at Company A with no forbids yields CONDITIONAL throughout the Company, never ALLOW (§3.1 step 2). An empty Team does not gain an update permission: potential widget names exist independently of row count. Under §3.1’s authoring rule an exception at C must be disclosable to holders of the Company grant, so it appears as a hole in the Company-wide allow; a deployment without that rule withholds the Company-wide allow for the affected keys whether or not an exception exists. After revocation, the PEP denies immediately once it observes the new authoritative revision; an unexpired old UI context may lag, but cannot confer access.

The executable checks exercise a finite reference model, not a production PEP or a proof of arbitrary policy semantics. They live in the HTML edition’s regression script (the same model drives the §3.6 simulator) and run on load or with the button. Each v1.4 soundness or security fix (items 1–9) has a tagged case that fails against the v1.3 rules and passes against v1.4. The markdown export lists every check with its result.


          


        
        

          
Part V. Peer-Review Critique, Operational Limits & Verified Bibliography


          
5.1 Steel-Manned Objections & Architectural Boundaries

          
A rigorous architecture specification must explicitly state where it breaks down. Four steel-manned objections define the boundary of this pattern:

          
    
            
  • Objection 1 — Exclusion Explosion Under High-Fanout Denies: A ScopedClaim hole only removes a positive proof; an EXCLUDED claim independently proves a final explicit denial. If the budget cannot represent the allow and all required holes, omit the affected allow and any unsupported coverage. Without other evidence the result is UNLOADED, not CONDITIONAL.
    • 
            
  • Objection 2 — Non-Hierarchical / Fine-Grained ReBAC Graphs: In consumer collaboration platforms (e.g., Google Drive, Figma) where permissions are attached per-document via arbitrary sharing links rather than parent folders, almost no permission is universally valid across a folder prefix. Boundary: Do not use hierarchical Permission Contexts as the primary model for per-document sharing graphs; use Zanzibar-style ReBAC (SpiceDB/OpenFGA) with CheckBulkPermissions and LookupResources [10] [20].
    • 
            
  • Objection 3 — Client/Server Policy Drift: The interceptor authenticates, binds and safely prechecks; the handler or data layer owns state-dependent checks and consistency through use or commit. A commit-time revision check must cover every relied-on fact. Test the catalog against authoritative handler behavior, including wildcard lists and partial batches. For the same reason upsert-capable Updates are named handler policies, so an update-only grant cannot silently create (§1.1).
    • 
            
  • Objection 4 — Stale Contexts After Immediate Revocation: Because clients cache permission contexts for remaining_ttl (e.g., 60–300 s), a freshly revoked user may briefly see an enabled button before receiving PERMISSION_DENIED from the backend PEP. Mitigation: Treat client contexts strictly as UX hints; on receiving PERMISSION_DENIED from any RPC, the client SDK must automatically evict and refresh the matching anchor context.
    •
