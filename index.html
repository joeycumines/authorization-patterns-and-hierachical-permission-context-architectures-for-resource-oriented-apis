Systems Architecture Monograph & Formal Engineering Reference

General Authorization Implementation Patterns & Hierarchical Permission-Context Architectures for Resource-Oriented APIs

A formal analysis of the (Actor, Action, Resource, Context) model, a comparative taxonomy of production authorization systems, and a specification for declaring authorization on AIP/gRPC methods, deciding it with one pure function over scoped grants, and projecting it soundly to user interfaces and agent tool hosts.

Target Paradigm: Google AIP Resource-Oriented APIs (gRPC / Protobuf) Status: Canonical Technical Reference (v1.7) Date: November 2026 Source: GitHub repository ↗

Executive Summary & Key Architectural Conclusions

Core Thesis

A frontend that offers an action the server then refuses has shown a false affordance. Avoiding that without per-resource round trips or duplicated role logic requires keeping static facts about each RPC separate from runtime evidence about the caller. Static method facts come straight from the API's protobuf descriptors, with no generated glue code required. Runtime evidence comes from a permission context summarizing what the caller may do within a scope such as a company or team. When roles are granted at scopes and select operations by resource type and access class, the server computes both request enforcement and permission contexts from the same grants and descriptors. No permission list is maintained by hand, and the server remains the sole enforcement authority.

Backend services check access one request at a time: may caller a perform action k on resource r, given request attributes c? User interfaces, API gateways, batch workflows, and agent tool hosts (such as MCP servers) ask a broader question: what can this caller do across a whole scope, or across whichever scopes their credential grants access to? Answering that by querying every individual resource costs one round trip and one cache entry per resource.

This report starts by formalizing the standard (Actor, Action, Resource, Context) model of access control (where the formal context is request attributes such as time or network) and cataloging production implementation patterns grounded in primary literature, including NIST RBAC [11], NIST ABAC [12], OASIS XACML [13], Google Zanzibar [10], AWS Cedar [14], Open Policy Agent [19], SpiceDB and OpenFGA [20], Kubernetes SelfSubjectRulesReview [16], Google Cloud TestIamPermissions [17], and Macaroons [15]. It then specifies a modular architecture for resource-oriented gRPC APIs that follow Google's API Improvement Proposals (AIPs):

  1. Declare requirements once on methods; derive everything else from descriptors. A permission is identified by a resource type and an operation, such as widgets.get. Standard AIP methods need a single annotation line: the AIPs fix what Get, List, Create, Update, and Delete do, so the operation, access class, and target field follow from the method shape and its google.api.resource annotations. Clients read protobuf descriptors directly (via gRPC Server Reflection or an HTTP descriptor set) without generated code or hand-maintained permission lists (§3.2, §4.1, §4.2).
  2. Express roles as scoped grants selecting resource types and access classes. To authorize a request, the server checks the caller's grants attached at or above the target. To build a permission context, it walks the method patterns reachable at or below each grant's scope and emits the selected keys. Both paths share one grant resolver and the same descriptors (§3.3).
  3. Adopt the smallest conformance profile your policy needs, and keep contexts pure functions of rules. The profiles build in order: annotated declarations alone, hole-free grant-shaped contexts, and scoped claims with holes, definite denials, and conditionals. Contexts in Core never read stored resource rows; specialized field-level write guards live in a separate optional extension (§3.5, §3.6, §4.5).
  4. Align with AIP semantics and isolate server status rules. Uniform List vs. per-caller Search, wildcard reads, upsert allow_missing, explicit-grant-only Expunge, batch checks, and imported Operations RPCs shape declarations and folding directly (§4.2). Server-only status and existence-oracle rules (AIP-133, AIP-193, AIP-211, AIP-217) sit in a dedicated server enforcement reference so UI and agent-host implementers do not need to wade through them (§4.3).
  5. Separate static availability from request folding, and keep freshness opaque on the wire. Static availability uses descriptors and any known credential ceiling before any snapshot is loaded; the fold evaluates concrete requests against snapshots carrying an opaque snapshot_token, an AIP-214 expire_time, and an opaque descriptor_etag that tells dynamic clients when to refresh descriptors (§3.7, §3.8, §4.4).

This specification defines how a method declares what it requires, how the server decides a request from declarations and grants, what the server may report in a permission context, what a client may conclude statically and at request time, and which standard AIP freshness signals cross the wire.

It leaves deployment choices to the operator: how descriptor sets are distributed to browsers, how often caches revalidate, how replicas implement the opaque snapshot token internally, and how policy-administration tooling validates policy writes. Where a deployment choice can make a frontend show the wrong action, this document describes the failure mode without prescribing one infrastructure.

Part I. The Problem and the Formal Model

Section Takeaway

Enforcement evaluates a pointwise decision function D(a, k, r, c). A frontend needs a statement about a whole scope, which is a universal quantification over that function. A projection is sound if every claim it makes is true at the snapshot it names. Completeness is optional, and freshness is specified separately.

1.1 What a Frontend Needs: Avoiding False Affordances

The problem this architecture solves is narrow. A frontend shows a button, a menu entry or a tool, the user or agent invokes it, and the server answers PERMISSION_DENIED. That is a false affordance. The opposite error, hiding an action the caller could have taken, is a false hide. It costs the caller a capability and is the lesser of the two errors. Failures that are not about authorization (validation, preconditions, quota) are out of scope: nothing a permission context says can predict them. One refusal is out of scope even though it comes back as PERMISSION_DENIED. AIP-133 requires that status when a new resource's name collides with a resource the caller cannot see. Whether that happens depends on stored data, and a context that predicted it, by saying that creating w7 in Team B will be refused, would tell the caller that w7 exists (§4.3).

A frontend already knows which operations exist, because they are in the API's descriptors. What it lacks depends on what the action would apply to:

  • Nothing chosen yet. A navigation bar or a tool list is drawn before any resource is chosen. The question is existential: is there anywhere this caller could do this?
  • A scope. A page for one team asks whether "New widget" should be enabled. The question is universal within that scope: may the caller do this on everything here?
  • An item. A row action asks about one resource. The question is pointwise.

The frontend also consumes two different kinds of information, and they should not be confused. Static method facts need nothing chosen: what a method requires, which names it accepts, and whether it reads or changes anything. They decide how menus and tool lists are grouped and when to ask for confirmation. Evidence about the caller is tied to a scope: what the caller may do there. 1.2 The Authorization Decision Function

Authoritative enforcement is a function D(a, k, r, c) → {ALLOW, DENY} of a caller a, a permission key k, a concrete resource name r and the request's attributes c, such as time or network. A method does not need just one key: it lists requirements, each a key paired with the request field that names its target, and every one must hold (§3.2). R is every name the resource patterns allow, whether or not anything is stored under it: a decision about a widget that does not exist yet is still a decision.

At a fixed snapshot, evaluating policy can end in more than two ways: no rule applies, a permit, an explicit forbid, a condition that cannot be resolved, or an evaluation error. Throughout this report they combine as follows:

  • A proven forbid denies.
  • A forbid that could apply but whose condition is unresolved, or that might raise an error, means even an unconditional permit is not enough to allow.
  • Otherwise a proven permit is required. An unresolved or possibly erroring permit is not sufficient.

"Proven" includes proving that the relied-on policies cannot raise an evaluation error anywhere the proof covers; a predicate the adapter cannot prove error-free counts as possibly erroring. Authoritative policy engines differ in how they handle evaluation errors (some fail closed, while others skip erroring policies and report diagnostics; see Part II, Pattern 4 for Cedar). Every backend adapter MUST declare and test its error policy, and denying whenever an applicable forbid errors is the safer authoritative default. Projection MUST follow the combining rules above regardless of which error policy the backend chooses: a context emits DENY only for a proven forbid or where no permit can apply, and emits ALLOW only for a proven permit where no forbid can apply even through an error. Because both fail-closed and error-skipping authorities deny in the first two cases and allow in the last, projection stays sound against either; the authority's error policy only affects how often a context omits a claim. A proven forbid with no unresolved predicate is called final throughout this report. Forbids override permits, so nothing reverses a final forbid.

It follows that a permission context is advisory: it is true at the snapshot it names, and it is never a credential; the server never accepts a client's projection as proof, and an audit trail records what the server decided, never what a context said. It also follows that the server itself splits the work. An interceptor authenticates, binds targets from the request and evaluates everything that depends only on the request and the caller's grants. A handler or data layer makes the checks that depend on stored state and owns the check-and-commit boundary. A commit-time revision check is sufficient only if it covers every fact the decision relied on.

1.3 Pointwise Evaluation vs. Subtree Permission Projection

Pointwise evaluation answers one concrete question: "Can Alice execute widgets.update on companies/A/teams/B/widgets/w1 right now?" Permission projection fixes the caller and the request attributes (a, c) and an anchor r0, which is a resource name or the service root, and summarizes D(a, k, r, c) for every key k that a method can require at or below the anchor and every potential resource r ∈ Subtree(r0) = { r ∈ R | r0 ⪯ r }, where x ⪯ y means that x is y or one of its ancestors, as AIP resource names nest.

For each key only some names matter, the ones its requirements can target, called its binding domain: widgets.get targets widget names, never a team's name. A summary such as ALL, NONE or MIXED loses information, because MIXED does not say where the exceptions are. Listing the exceptions loses nothing, but only where every exception can be written as a scope and may be shown to the caller (§3.6).

1.4 Soundness, Completeness and Monotonicity

A claim is sound if it is true for the caller, the policy snapshot, the declarations and the request attributes it was computed for. A context need not be complete: what the server leaves out stays UNLOADED, and the frontend asks about a narrower scope or leaves the decision to the server. A snapshot's expire_time limits how long it is reused; it does not keep it current: a grant revoked a moment after the snapshot was sent still shows until the snapshot expires or is refreshed (§3.8).

Theorem 1.1. Fix the caller, the request attributes, the snapshot and the key, and let B be the key's binding domain (a different letter from the decision function D of §1.2). For any scope s, whether or not s is itself in B, let B(s) be the points of B at or below s. For x in B, let A(x) mean an unconditional allow at x: ALLOW in every case the evaluation could take, whatever values the unresolved facts have and whichever policies that might raise an error do so (§1.2). Let U(s) mean A(x) for every x in B(s); an ALLOW claim over s, which is sent only when B(s) is not empty, states exactly U(s). Call A downward-monotone when A(s) implies A(x) for all s ⪯ x in B. Then:

  1. A is downward-monotone if and only if A(x) = U(x) at every x in B.
  2. Suppose every rule for the key is an unconditional permit that cannot raise an error. Like every grant, each is attached to a resource name or the service root, never to a collection (§3.1), there are finitely many, and an ID segment can take unboundedly many values (§3.6). Then a permit attached at or above s proves U(s), for any scope s. Conversely, when U(s) holds and no permit is attached at or above s, every point of B(s) lies at or below a permit attached to a singleton descendant of s (AIP-156).

Read informally, part 1 says that "allowed at a point means allowed everywhere below it" and "a point's answer is also the answer for its whole subtree" are the same property. Part 2 says plain role grants have that property, and that the anchor is the only place a universal needs checking, with one exception. A grant on a singleton, such as a team's settings, makes settings.get universal under the team although nothing is granted at the team itself. That is why the grant walk of §3.3 reports such a grant at the singleton's own scope, where a client will look for it.

Proof of Theorem 1.1

Part 1. U(x) implies A(x) always, because x is in B(x). If A is downward-monotone, A(x) implies U(x), because every point of B(x) lies at or below x. Conversely, if A = U on B, then for s ⪯ x in B, A(s) gives U(s), which includes A(x).

Part 2. A permit applies at every descendant of its scope, so one at or above s allows all of B(s). For the converse, assume U(s) with no permit at or above s, and take x in B(s). If the path from s down to x crosses no ID segment, the permit that allows x extends s by literal segments alone, and as a grant's scope it is a resource name, so it is a singleton. Otherwise let i be the depth of the first ID segment crossed. The names that differ from x only at depth i are all in B(s), and finitely many permits name finitely many IDs, so one of those names is allowed only by a permit scoped above depth i. That scope extends s by literal segments alone and, being a grant's scope, is a resource name rather than a collection, so it is a singleton, and since the varied names agree with x above depth i, it is also an ancestor of x. ∎

In practice this means:

  • A claim that something is allowed everywhere in a scope is safe for any policy, monotone or not, as long as it is true: an ALLOW claim over s states exactly U(s). The server need not report every individual allow, so a context can be incomplete, and an empty one is never wrong.
  • Additive scoped grants are downward-monotone, and by part 2 checking the grants at or above the anchor decides the universal, apart from a grant attached directly to an AIP-156 singleton below it, which §3.3 reports at the singleton's own scope. That is why the grant-shaped profile is cheap (§3.3). Forbids and conditions on descendants break monotonicity and are what the scoped-claim profile exists for (§3.6).
  • The universal and the pointwise answer coincide trivially only where B(s) = {s}: the anchor is itself a domain point with nothing of the domain below it, such as a widget for a key bound only to the widget pattern. At a team, widgets.get covers unboundedly many widgets, and the universal has to be proven. A key with patterns at several depths has domain points below an in-domain anchor too: with widgets under both companies and teams, widgets.create binds to companies and to teams, and under an arbitrary policy being allowed to create directly under a company says nothing about its teams.

Part II. General Authorization Implementation Patterns Taxonomy

Section Takeaway

No single authorization pattern dominates all workloads. Production architectures compose a policy representation model (RBAC, ReBAC, ABAC, Capabilities) with an evaluation topology (pointwise PEP/PDP, bulk check, subtree projection, or partial-evaluation data filtering) matched to the workload's resource graph, latency budget, and revocation strictness.

2.1 Production Implementation Patterns

1. Centralized Enforcement (PEP / PDP / PIP / PAP Architecture). Standardized by OASIS XACML 3.0 [13] and NIST SP 800-162 [12], this pattern decouples request interception (Policy Enforcement Point) from decision evaluation (Policy Decision Point) and attribute retrieval (Policy Information Point). It provides uniform auditing and language-agnostic policy governance across microservices (e.g., Envoy ext_authz [22] calling OPA or Cedar). Its primary trade-off is network-hop latency and availability coupling on the critical request path, mitigated by sidecar/in-process PDP deployment.

2. Resource-hierarchy policy inheritance with RBAC role bundles. NIST hierarchical RBAC [11] describes role hierarchies, not resource trees. Services such as Google Cloud IAM [17] and Azure RBAC [24] attach policy or role assignments to resource hierarchy nodes. Allow grants are additive: an allow attached to a node applies to everything below it, and adding one never takes access away; in Google Cloud, only a separate deny policy does that [17]. An inherited allow holds below a node only where its conditions do: a CEL condition can be true at a folder and false for a resource inside it, with no deny policy involved. Google Cloud IAM policy changes typically propagate in about two minutes, but can take seven minutes or more.

3. Resource-Level ACLs & Relationship-Based Access Control (ReBAC). Pioneered at global scale by Google Zanzibar [10] and implemented in open-source engines like AuthZed SpiceDB and OpenFGA [20], ReBAC models authorization as graph reachability over stored relation tuples (object#relation@user) with userset rewrite rules (union, intersection, exclusion, tuple-to-userset). Zanzibar achieves <10 ms p95 latency across trillions of tuples and prevents the "new enemy" stale-ACL problem using opaque causal consistency tokens called zookies (called ZedToken in SpiceDB) [10] [20]. ReBAC excels at fine-grained, non-hierarchical sharing, but graph traversal makes high-fanout list filtering and coarse prefix projection computationally expensive unless backed by materialized permission views (e.g., AuthZed Materialize) [20].

4. Attribute-Based & Policy-Based Access Control (ABAC / PBAC). Formalized by NIST SP 800-162 [12] and realized in Open Policy Agent (Rego) [19], Amazon Verified Permissions (Cedar) [25] [14], and Google Cloud IAM Conditions (CEL) [17], ABAC evaluates boolean predicates over subject, resource, action, and environment attributes (e.g., time-of-day, data classification, resource ownership). Cedar restricts language expressiveness (no unbounded loops, explicit permit/forbid semantics) to guarantee termination and support SMT-backed static policy analysis [14]; these guarantees concern termination and analysis, not a latency bound. Native Cedar skips policies whose evaluation raises an error (including forbids) and reports them in diagnostics [14], so an adapter enforcing fail-closed forbid errors checks diagnostics directly (§1.2). ABAC eliminates role explosion, but attribute volatility lowers cacheability and complicates static permission projection.

5. Scoped Permission Projection & Self-Review APIs. Used directly to drive permission-aware UIs and CLIs without O(N) pointwise checks. Real-world precedents include Kubernetes SelfSubjectRulesReview (authorization.k8s.io/v1, which enumerates a caller's effective resourceRules within a namespace and explicitly returns an incomplete boolean when an external authorizer cannot project rules) [16], Google Cloud IAMPolicy.TestIamPermissions (which intersects a caller-supplied candidate permission set against effective permissions on a resource) [17], and AWS IAM SimulatePrincipalPolicy [18]. Kubernetes warns about incomplete results and confused-deputy risks; Google Cloud warns that TestIamPermissions is for permission-aware tools and may fail open. Neither substitutes for authoritative enforcement [16] [17].

6. Batch & Bulk Authorization Evaluation. Bulk checks amortize RPC overhead. SpiceDB CheckBulkPermissions supports ZedToken consistency controls; OpenFGA BatchCheck provides correlation IDs and MINIMIZE_LATENCY / HIGHER_CONSISTENCY preferences, not a snapshot token or a shared-snapshot guarantee [20].

7. Authorization-Aware Search & Data Filtering (Partial Evaluation). AIP-132 says a standard List should return the same results to every caller permitted to list [26], so filtering results per caller belongs to a Search-style custom method (§4.2, §4.3). There, authorize the invocation and the visibility of each item separately. A parent scope alone cannot exclude forbidden descendants. Use a query predicate equivalent to per-item authorization, or an authoritative bulk check of candidate rows; page sizes, counts and tokens MUST NOT expose rejected candidates. OPA's /v1/compile partially evaluates a policy and returns the conditions that remain as a Rego syntax tree, and /v1/compile/{path} turns a named rule into a SQL or UCAST filter [19].

8. Delegated Capability Tokens & Attenuation. Macaroons [15] can be attenuated by appending chained HMAC caveats. Verification is O(number of caveats) plus the cost of evaluating those caveats. Short TTLs and discharge caveats can constrain offline use. Biscuit [23] offers offline attenuation with public-key signatures and Datalog-based policies.

9. Field-Level & Long-Running Operation (LRO) Authorization. AIP-161 field masks select fields [30]; an optional field-guard extension authorizes privileged field writes (§4.5). AIP-151 [5] defines the operation shape, not permissions. A typical local policy binds an operation to its creator and rechecks the originating permission on GetOperation and WaitOperation, and ListOperations returns only operations the caller may get. Declare these as named handler policies in imported_methods for the Operations methods the service serves (§4.1, §4.2).

Part III. The Architecture: Declarations, Grants, Decisions and Contexts

Section Takeaway

Methods declare what they require. Policy grants access by resource type and access class at a scope. One pure function decides a request from those two inputs, and the same data, traversed from the grant instead of from the target, produces the permission context a frontend folds. Everything else in this part is a consequence: how names form a hierarchy, which profile to adopt, how exceptions and private rules are handled, how the contract evolves, and how contexts are cached.

3.1 The Pieces and Who Owns Them

Each piece of the architecture has one owner, so no authorization fact has to be written down twice.

  1. Declarations. Each RPC states what it requires as a protobuf method option. Combined with standard AIP resource annotations, this fixes the method's resource type, operation, access class, target, and effect directly in the protobuf descriptors, with no generated code required (§3.2, §4.2).
  2. Grants. Server policy records which principals hold which roles at which scopes, and what each role selects. Grants are runtime data and never appear in descriptors (§3.3).
  3. The decision. For each request the service binds declared targets and evaluates the caller's grants. Checks that depend on stored state run in the handler (§4.3, §4.4).
  4. The context. On request, the service returns a snapshot telling the caller which permission keys it holds within the requested anchors (§3.5, §3.6).
  5. Static method availability and the fold. Before fetching any snapshot, the client uses descriptors (plus any known credential ceiling) to determine whether a method is usable on the current connection. For available methods and concrete requests, the client folds accepted snapshots to decide what to offer. The client never enforces (§4.4).

The Join Key

Methods never name roles, and roles never name methods. They meet only through a small shared vocabulary: a resource type with an access class, or a resource type with one named operation. Adding an RPC changes the descriptor only. Roles that select its class cover it in the next decision and in every context issued afterwards, after one review step in which someone confirms that those roles should cover it (§3.7).

How much should a method say about authorization? Too little, and distinct operations collapse into one check. Too much, and every RPC carries a hand-maintained string that must be kept consistent with roles, clients and other methods. The third column is the design. It keeps apart what a single facet mixes up: which operation a method performs, which class of operation that is, and whether calling the method changes anything.

Identity

A permission is identified by its resource type and its operation. Its display form, the permission key, is the type's plural and the operation: books.get, books.search, books.expunge. Because the key is derived, two methods that perform the same operation share it without coordination (GetBook and BatchGetBooks both require books.get), and there are no hand-spelled names whose conventions someone has to enforce. A key is unique within one service; another service can have its own widgets.get. A client that works with several services keeps their declarations and contexts apart, which is easy because every response names its service.

Access class

Every requirement has exactly one class: READ, CREATE, UPDATE, DELETE, ADMIN or EXECUTE. A class is a selector over operations. A role that grants READ on Book covers books.get, books.list and books.search today and any READ operation added later. A standard method takes its class from which standard method it is: a Get reads, a Delete deletes. A custom method states it, because nothing else about a custom method is reliable enough to infer it from: AIP-136 lets a retrieval method use POST when its payload could exceed URL length limits [4]. EXECUTE exists so that custom mutations, such as publishing a document or running a job, are not classified as UPDATE and granted to every editor without anyone having decided so. No class implies another: ADMIN does not include DELETE, and UPDATE does not include CREATE.

Effect

Whether invoking a method changes state is a property of the method, and a frontend needs it before anything is chosen: to separate read tools from mutating ones, to decide when to ask for confirmation, and to hide mutations on a read-only credential. It is derived. A method whose requirements are all READ is read-only; one with a DELETE requirement is destructive; anything else is mutating. Requirements that apply only to some requests count, because the effect describes the method and not one call. Effect and class can differ, as the access-policy row shows, and such a method overrides the derived effect with protobuf's standard idempotency_level = NO_SIDE_EFFECTS option [21]. The override can only mark a method read-only when its requirements read or administer; the build rejects it beside a create, update, delete or execute requirement. A method decided by a named handler policy has no requirements to derive an effect from, so it is read-only only when it says so, with the same option or, for an imported method, the matching flag on its entry in imported_methods (§4.1). Otherwise its effect is unknown, and a frontend treats it as it would a destructive method: it asks before running it and keeps it from a read-only credential. A Move declared as delete at the source and create at the destination is destructive by this rule, so a frontend asks before moving anything, although nothing is lost. A service that wants a move treated as an ordinary change declares a move operation of its own, of class UPDATE, together with create at the destination; the cost is that a forbid on deletes no longer stops anyone moving resources out of a scope.

Requirements that depend on the request

Some requirements apply only when a request field is set. AIP-134 lets an Update with allow_missing create a missing resource and says the caller must hold the update permission [26]. This specification adds a local, stricter rule that stays declarative: when a request sets allow_missing = true, create on the parent is required as well. The rule reads the request, never the stored row, so an update-only grant can never create and the client can evaluate it. A requirement that depends on stored state, such as whether a row exists or who owns it, is not declarative and belongs to the handler (§3.3).

Field-sensitive writes (optional extension)

Core declarations authorize at the RPC level (plus boolean request flags such as allow_missing). Most services handle privileged field updates either with a dedicated custom RPC (such as SetWidgetOwner) or a named handler policy, keeping core descriptor interpretation free of field-mask parsing and message traversal. Services that do want declarative per-field checks on standard Create and Update requests can opt into the standalone Field Guards extension in §4.5 (authz/v1/field_guards.proto). Note that AIP-161 classifies map-key traversal and mid-path collection wildcards as non-standard extensions unsupported by standard protobuf runtime libraries [30], which is a primary reason field guards stay outside Core. Checks that depend on whether a field's stored value actually changed always remain handler logic.

Credential limits

A delegated credential, such as an OAuth grant given to an agent or a third-party client, limits what its bearer may do. Model it as a ceiling of access classes, optionally per resource type, and intersect it with the principal's grants. The ceiling applies to each key by that key's own class, so a role that names an operation is limited exactly as a role that selects the operation's class. It narrows permits only. A forbid is never narrowed, because a narrower forbid would grant more. A ceiling never adds authority, and a new READ operation falls under a read-only ceiling exactly as it falls under a READ grant. The credential issuer states the ceiling; it does not decide resource authorization, which stays with the service that owns the resource.

3.3 Scoped Grants

A role, by itself, grants nothing. A grant attaches a role's selectors to a scope: "viewer at companies/A", "widget-writer at companies/A/teams/B". A caller may hold different roles at different scopes, in different tenants, with no enclosing organization assumed. A grant may also be a forbid, and may have a condition.

Decide is the server's function. It follows the target's name down from the root and looks at the caller's grants attached at each step. K(g) answers "what should be sent for this grant": it starts at the grant's scope, follows the method patterns that can name something at or below it, and collects the keys the grant selects for those methods. Fold is the client's function over what was sent. Decide ignores conditions, so it is the whole decision only for unconditional grants; a condition can leave the server's decision unresolved, which §4.4 calls RESIDUAL.

Proposition 3.1 (exactness). Let Π = { (g.scope, ±g, K(g)) : g ∈ G } for a set G of unconditional grants, where ±g says whether g is a permit or a forbid, and K is computed from the same declarations the client folds with. Suppose each key determines the resource type, operation, access class and explicit-grant-only marker of every requirement that carries it. Then Fold(Π, key(ρ), t) = Decide(G, ρ, t) for every requirement ρ and every target t in its binding domain.

In words: send each grant's scope together with the keys it selects there, and a client that only asks "is this scope an ancestor of my target?" reaches the server's decision exactly, without ever seeing a role, a selector or an access class. The one condition is that a key always means the same kind of operation. The build enforces it (§4.2): the operation is part of the key, plurals are unique, and no key may carry two types, two classes or two markers. Counterexample 1 below shows what goes wrong without it.

Proof of Proposition 3.1

Fix ρ and t, and let k = key(ρ). A grant whose scope is not an ancestor of t counts on neither side. Take a grant with g.scope ⪯ t. Because t is in the binding domain of ρ, reach(ρ, g.scope) holds, so match(g, ρ) implies k ∈ K(g). Conversely, k ∈ K(g) means match(g, ρ′) for some requirement ρ′ with key k; match reads only the type, operation, class and marker, which k determines, so match(g, ρ) holds too. For permits and for forbids alike, then, the grants that count in Decide are exactly the entries that count in Fold, and the two definitions combine permits and forbids in the same way. ∎

The regression checks in §4.6 test the proposition over every policy of one or two grants drawn from five scopes, the fixture roles, as permits and as forbids, with contexts projected at the service root. The sent relation, the reference rule engine and the scoped-claims context match the definition exactly; the grant-shaped context is checked to be sound and to drop nothing when no forbid is present.

How Π reaches a client. Π is a definition, not a wire format. A policy of permits only is sent as it stands: one hole-free ALLOW claim per grant scope, which is the grant-shaped profile. With forbids the two context profiles differ. The grant-shaped profile cannot send a forbid entry, so it removes from each permit entry every key that a forbid could deny somewhere within that entry's scope. What remains is true and the fold stays sound. A narrower anchor usually recovers what was removed; §3.5 describes the case where none can. The scoped-claims profile sends the forbids as holes in ALLOW claims and as DENY claims, and for unconditional, disclosable grants its fold equals Decide (§3.6).

Several practical properties follow from this construction:

  • Nothing is maintained per permission. K(g) depends only on the selector set and the shape of the scope, a company versus a team. It is computed from descriptors, is identical for every user and company, and can be cached once at startup. The only per-user data is the list of scopes and selector sets.
  • The handler and the context endpoint share one resolver. Both start from the caller's effective grants. The context endpoint returns, in expanded form, what the handler already consults.
  • Scopes are discoverable without knowing them beforehand. A client holding a user credential or an exchanged downstream token (such as an MCP server integrating with an identity provider like Keycloak) does not need to know which companies or teams the caller belongs to. Querying the tagged service_root anchor returns claims at each scope where the caller holds a grant, answering "where can I act?" without requiring a root listing permission.
  • Startup discovery stays strictly about proven access. A key in an ALLOW claim proves its operation holds throughout that claim's region. In a policy of unconditional, error-free permits with no descendants omitted and no key nonprojecting, the converse holds too: a key missing from the root snapshot is usable nowhere (so a caller with only a team-level editor grant is never offered CreateTeam, which binds to the company). Under forbids in Grant-Shaped, conditional permits (such as owner-only rules), private-rule privacy boundaries, or budget truncation (descendants_omitted), absence from a root snapshot means unproven rather than denied. An MCP server or UI keeps unproven tools available to attempt (or queries narrower anchors once a scope is known) rather than falsely hiding them.
  • The pattern walk is not needed for soundness. The ancestor test in Fold already confines a key to targets under its scope. The walk keeps payloads small and makes the answer to "where can I act?" exact for each key.

The construction works because each requirement's resource type and class can be read from the method's own declaration. If classes lived in a separate table keyed by permission name, K(g) could not be computed from descriptors, and that table would have to be shipped to every client and kept in step with every release. The same is true of a table that expands each role into a list of permissions. Both tables are the hand-maintained lists this design removes.

Limits of the grant model

The grant model covers scoped grants over a name hierarchy. These lie outside it:

  • Exceptions. A forbid below a permit means the permit no longer holds everywhere in its scope. The grant-shaped profile omits the affected keys from the broader claim; the scoped-claim profile reports the exception as a hole (§3.5, §3.6).
  • Conditions. A conditional grant yields a CONDITIONAL claim at best. The client does not evaluate conditions.
  • Requirements that depend on a request value other than true or false. A requirement can depend on a bool request field, such as allow_missing. One that depends on which value an enum field holds, such as a full view of a resource that needs an extra permission, cannot be declared: the method is a handler policy, which a frontend leaves to the server, unless the API exposes that choice as a bool field.
  • Very many direct shares. A caller with thousands of grant scopes should not receive them all at the root. The server marks the context as having omitted descendants and the client queries narrower anchors (§4.1).
  • Relationships that are not a name hierarchy. Group membership and sharing edges are resolved by the server into effective grants before anything is decided or projected (§3.4).
  • Upward and sideways access. Nothing is implied upward: a team role does not allow reading the company. Operations bound to the service root need a grant at the root, so an administrator of one tenant never satisfies a global method.

3.4 Resource Hierarchy, Prefixes and External Identities

AIP-124 gives every resource at most one canonical parent, and AIP-121 requires the parent-child relationship to be acyclic [1]. This specification adds one synthetic node above every top-level resource, the service root, whose segment list is empty. It is written //{service_name}/ in prose only. On the wire it is a tagged value, distinct from every AIP-122 resource name and AIP-156 singleton, and it is never passed to a generated name parser. Authorization often involves relationships that are not part of this tree: a user belongs to a group, a project is linked to a billing account, a widget is shared with a collaborator in another company. Segment-Aware Matching vs. Naive String Prefixing

Counterexample 2 — Naive String Prefix Collision

If a client checks target.startsWith(scope), a grant on companies/A/teams/B also matches companies/A/teams/B2 and companies/A/teams/Billing/widgets/w9. Appending a slash fixes those sibling cases but still fails on names that are not canonical: …/teams/B/%2E%2E/C starts with …/teams/B/, yet a downstream decoder may normalize it to …/teams/C; doubled or trailing slashes create alternate spellings of one name; and the same relative path under another service is a different resource. AIP-122 says resource IDs should avoid characters that need URL-escaping [2], so a service can reject such spellings outright.

The remedy is that all matching, on server and client, parses a name into a service and a flat list of validated segments. A scope s covers a target r if and only if they belong to the same service, len(s) ≤ len(r), and every segment of s equals the segment of r at the same index. The root's empty list is a prefix of every name, and no tenant scope can be a prefix of the root. Reject empty segments, . and .., percent-encodings, a slash or backslash inside an identifier, and an ID that is just - other than as a wildcard the declaration allows, since AIP-159 reserves - for wildcards. The rule covers every name bound to a requirement and every anchor, claim scope and hole. A service may not resolve such a spelling to a canonical name instead: the client compares names segment by segment as they are written, so a name the server rewrote would fall under one scope on the client and another on the server, and the client would offer what the server refuses. A service that must accept such spellings declares the affected methods as handler policies.

AIP-122 and AIP-4231 each allow something that falls outside this segment model, and an API that uses it MUST declare the affected methods as handler policies: AIP-122 only says the terminal segment of a name should not contain a slash, and AIP-4231 allows a segment made of several variables joined by a separator [3]. Singleton and other static segments are ordinary literal segments.

Reachable Keys and the Pattern Trie

Every key is indexed under each of its binding patterns in a segment pattern trie rooted at the service root. A query walks the anchor's segments from the root. At each depth it follows the edge labeled with the anchor's segment and the * edge, whichever of the two exist. From every node it reaches at the anchor's depth it collects the keys bound at that node and at every node below it. That is the reach test of §3.3 applied to all keys at once. The walk costs O(matched nodes + keys returned), which is at most O(P·d + output) for P patterns of depth d.

A scope does not have to be a resource the service represents. A service that manages widgets under companies/{company}/teams/{team}/widgets/{widget} without implementing GetCompany can still attach grants to, and answer contexts for, companies/A: it is a local non-represented parent, a prefix of the service's own names. Resource types defined elsewhere are declared with the file-level google.api.resource_definition option documented in AIP-4231 [3].

Aliases and Cross-Service Name Isolation

AIP-122 allows programmatic aliases, such as users/me, provided responses use canonical names [2]. The server MUST resolve an alias to its immutable canonical name before policy evaluation and before any cache key is formed; otherwise a request naming companies/A through an alias would miss a forbid attached to companies/A. An alias MUST use a value the service never assigns as a canonical ID (such as me), so whether a name is an alias never depends on data the caller cannot see. A client folds canonical names only: it compares names segment by segment as written, so folding users/me against a hole on users/u_12345 would offer what the server refuses. A client holding only an alias resolves it first, by reading the resource or from the context's requested_anchors (§4.1); until then it has no evidence for that name.

Resource names owned by another service (such as //org.example.com/companies/acme) are never prefixes in this service's resource tree, and claims are always expressed in the queried service's own relative resource names. Translating external organization or identity-provider claims (such as Keycloak group or organization attributes) into local scopes is server-side grant-resolver logic alongside group and role resolution; any change to those mappings advances the server's internal policy revision and invalidates cached proofs just like a group membership change (§3.8).

The profiles nest: a grant-shaped context is a scoped-claims context that happens to contain only hole-free ALLOW claims. A client states the highest profile it implements (max_profile), the server never sends more, and a deployment can move between profiles without changing the meaning of anything it has already sent.

The grant-shaped profile sends less, yet it proves the same universal guarantee. Every ALLOW claim states that the permission holds everywhere in its scope, so a server in either context profile must know whether a forbid or a condition for the key exists anywhere below the claim's scope, including one attached to a single resource; that is the descendant-rule index of §3.6. A policy of unconditional permits meets both obligations trivially, which is why Grant-Shaped is inexpensive for the multi-tenant RBAC workloads it was designed for.

Here is how the grant-shaped profile handles an exception. Suppose Alice holds a viewer grant at companies/A and a forbid on reads at companies/A/teams/C. "Reads are allowed everywhere in A" is false, so the server omits the read keys from the claim at A. A frontend drawing the page for Team B finds no evidence for widgets.get there and queries Team B directly, where the claim is true and is returned. The exception costs one extra query and never produces a false allow.

Recovery works because a narrower anchor can leave the exception outside it. That is not always possible when one permission key can bind both at a scope and strictly below it. For example, if widgets can sit directly under a company as well as under its teams, widgets.create binds to companies/A and to every team under it; a forbid on creating widgets in Team C makes "create widgets anywhere under A" false, and every anchor covering companies/A also covers Team C. The same occurs when the optional Field Guards extension (§4.5) checks widgets.setOwner on the team during Create and on the widget during Update, and a forbid blocks widgets.setOwner on one widget w1 inside Team B. Nothing false is shown; the action is simply left UNLOADED. A deployment that hits this limit in practice moves to Scoped Claims, which reports the region accurately as ALLOW over the parent with the exception as a hole, without changing any declaration or grant.

Single-item queries and pure rule-based contexts

Questions about a single resource use the same QueryPermissionContexts RPC with the resource as the anchor. When the anchor is the only name in a key's binding domain at or below itself (a widget for widgets.update, unlike a team), a universal claim over that anchor is simply the decision for that resource (§1.4), so a list view with per-resource policy rules can query twenty widget anchors in one batched call.

In Core, a permission context is always a pure function of policy rules and never reads stored resource rows. That invariant keeps QueryPermissionContexts decoupled from the application database, guarantees that ordinary row edits never stale a policy snapshot, and allows contexts for separate anchors to combine cleanly inside multi-target folds such as MoveWidget. Where access depends on stored row attributes (such as an owner-only rule widget.owner == alice), Scoped Claims honestly reports CONDITIONAL (and Grant-Shaped omits the claim). Frontends resolve row-dependent actions by inspecting fields of the resource they already fetched, calling a separate pointwise authorization check or validate_only dry run (AIP-163), or letting the server decide the call. Because contexts never consult stored data, the context for a canonical name is identical whether or not a resource exists there.

Implement Declarations if the only need is to partition operations, describe inputs, and apply credential ceilings. Implement Grant-Shaped Contexts when roles are assigned at scopes and exceptions are rare; this covers most multi-tenant applications. Move to Scoped Claims when exceptions are common enough that narrower follow-up queries are felt, or when the interface needs to explain a denial instead of hiding the action.

3.6 Scoped Claims and Disclosure

The claim representation and partitioning rules below are needed only for Scoped Claims. The descendant-rule index and the disclosure rules bind both context profiles (§3.5).

Binding domains, regions, and claim kinds

The binding domain of key k at anchor s is every name one of k's binding patterns allows at or below s, including names under which nothing has been created yet. For a root-bound key that is the service root alone. A server MUST NOT enumerate stored rows to prove that a permission holds everywhere: tomorrow's widget is not among today's rows, and the claim must hold for it too. It emits no claim where the patterns allow no name at all, even though universal quantification over an empty set is vacuously true.

A region is a scope (a resource name, a collection, or the service root) minus zero or more strict descendant scopes, its holes. Collections are needed where a resource has multiple parent patterns: if widgets sit under both companies/{company} and companies/{company}/teams/{team}, a claim may cover companies/A/widgets, or cover companies/A with the hole companies/A/teams. A claim states one of the following about a set of keys over a region, proven at the snapshot the response names:

  • ALLOW means the server would allow the call at every name in the region that the key can target.
  • DENY means the server would deny it at every such name. It is proven either by a final forbid (§1.2) or by the absence of any permit that could apply; the wire format does not distinguish which.
  • CONDITIONAL means the server could not resolve a condition. It asserts no decision; another context at the same snapshot may still prove one for the same target.

Where no claim covers a name, nothing is asserted about it: only a DENY claim says no. Claims of different kinds for the same key MUST NOT overlap on any name the key can target (a region with no targetable names, such as a team minus its settings singleton for settings.get, overlaps nothing).

Cell partitioning and merging

The projector turns the rules applying to the caller at one pinned policy snapshot into a finite list of permits and forbids, each attached to a canonical scope, applying to everything below it, and optionally carrying a condition. In the grant model these are the caller's effective grants with their keys expanded (§3.3). It then partitions the anchor's subtree into cells at the scopes of the disclosable rules for key k: each rule's scope starts a cell owning everything below it except the cells of deeper rules, including names that do not exist yet. Drop cells that contain no name in k's binding domain. Within each remaining cell the same rules apply everywhere, though a condition may still evaluate differently from one name to the next. Classify each cell in order:

  1. Emit DENY if a final forbid applies throughout the cell (unconditional and provably free of evaluation errors, §1.2).
  2. Otherwise emit ALLOW only if (a) an applicable permit holds unconditionally throughout the cell using facts pinned at the snapshot and provably cannot raise an evaluation error, and (b) every possible forbid is ruled out, including any conditional or possibly erroring forbid. An owner-only permit therefore never yields ALLOW.
  3. Otherwise emit DENY if no permit can apply at any name of the cell.
  4. Otherwise emit CONDITIONAL if that is safe to disclose, and nothing if it is not.

After classification, merge adjacent cells of the same kind from deepest enclosing cell upward, absorbing all of an enclosing cell's same-kind direct children together. A boundary remains a hole only where the verdict actually changes, so nested permits collapse into one hole-free claim. In the Grant-Shaped profile, an enclosing cell absorbs its same-kind children only if the merged result has zero holes; otherwise the subsequent coarsening step would drop the merged claim and erase an exception-free child grant (for example, a viewer at company A with an extra grant on Team B and a forbid on Team C would lose Team B from root discovery). Step 3 runs before step 4 so a condition that cannot affect the outcome (such as a conditional forbid where no permit exists) does not obscure a provable denial. Exhausting budget, missing a dependency, or hitting a disclosure restriction never produces DENY; it only omits claims. Claims may be merged only when their union covers the exact same binding-domain names as the merged region.

Descendant-rule index

Steps 2(b) and 3 quantify over every rule that could apply anywhere in a cell, including a rule attached to a single row, without enumerating stored rows. Both are answered from a descendant-rule index maintained per scope and key for the rules applying to the caller. It tracks forbids and permits separately because they block different proofs: a forbid strictly below a scope (including conditional or possibly erroring forbids) blocks an ALLOW over that scope, whereas a permit strictly below it blocks a DENY resting on the absence of permits. A deeper permit never blocks an ALLOW, and rules for other callers block nothing.

In Grant-Shaped, the index only needs to answer whether any blocking descendant rule exists. In Scoped Claims, it lists their scopes so the projector can split cells and emit holes. When more descendant scopes exist than the server's budget permits, the server omits claims that depend on them and sets descendants_omitted (§5.1). The index carries an internal revision that advances whenever any answer can change, including rule edits, role changes, group membership changes, and external-identifier mapping changes (§3.4). If the index is unavailable or older than the pinned snapshot, the server omits claims for that key rather than guessing. Any key whose rule sources the index does not fully cover MUST be declared nonprojecting.

Counterexample 3 — The One-Bit Leak

Alice holds a viewer grant at companies/A. An administrator places a forbid on companies/A/teams/D that Alice must not learn about. If the server answers Alice's query for A with ALLOW when the forbid is absent and with nothing when it is present, Alice learns that an exception exists. If it answers ALLOW with a hole, she learns Team D's name. If it answers CONDITIONAL only when the forbid carries a predicate, the same bit leaks through a different kind. The only answer that reveals nothing is the identical answer in both cases.

Private rules arise whenever a caller must not learn about scopes it cannot see, such as another company or a team it may not list. Take Alice, who may read widgets across company A but may not list its teams, and a forbid on Team D's widgets: a context saying ALLOW over company A with a hole at Team D would reveal that Team D exists. A deployment therefore declares, per key or resource type, whether private rules are allowed and at which hierarchy level they may sit (the privacy boundary, for example the team level). Above that boundary (such as at company A), the server emits no claim of any kind for that key whether or not a private rule exists; the key is nonprojecting there. At or below the boundary, claims project normally: a DENY at Team D tells Alice no more than calling the API on Team D would. Because that holds only if no private rule sits deeper than the boundary, every private rule MUST sit at or above its key's privacy boundary (if private rules may attach to single widgets, the boundary is the widget level).

A private rule MUST also be unconditional. A conditional private rule (such as "forbid reading Team D widgets marked classified") changes a Team D context from ALLOW to CONDITIONAL or empty even while no widget is marked and every call succeeds, revealing the rule's existence. Hiding sensitive rows belongs in the handler (for example, filtering them out of Search), or the deployment declares the key nonprojecting throughout that subtree.

This is also why an explicit forbid and the absence of any permit are both encoded as the same DENY kind: seeing DENY on Team D does not reveal whether a forbid exists there. Deployments without private rules declare none and project everything. The same disclosure rule binds the server's universal checks (wildcard List, batch top-level parent check, and wildcard Get NOT_FOUND proofs, §4.3): for a nonprojecting key above its privacy boundary, each universal check refuses unconditionally so succeeding does not leak the absence of a private rule. Refusing a batch's parent shortcut falls back to per-item checks; wildcard List and wildcard Get have no such fallback and refuse.

Policy-plane authoring invariant

Which scopes are disclosable to a caller? The scope of a permit the caller holds directly is always disclosable to that caller (a grant cannot be used without knowing where it applies). A permit reaching the caller indirectly through a group or external-identifier mapping at a scope the caller cannot otherwise see is a private rule. Any other scope (typically a forbid) is disclosable if the caller can observe it through the API (by get on the scope or list on its parent) or, for a local non-represented parent (§3.4), by a visibility rule declared by the deployment (such as holding a permit at or above it). A collection is disclosable exactly when the resource it sits under is, because companies/A/teams/D/widgets names Team D.

Runtime withholding cannot prevent the one-bit leak of Counterexample 3. If an undeclared private rule appears on a key that previously projected ALLOW, withholding claims at runtime still tells a caller who saw ALLOW yesterday and nothing today that a rule was added. When an undeclared private rule is encountered at runtime, withholding claims for that key above the rule (and at and below it if conditional), raising an operator alert, and still returning the response serves only as a last-resort safety net.

Preventing the leak is therefore a normative invariant on policy state: policy writes MUST NOT leave an unnameable rule on any key that is not declared private-capable at or below that rule's level, and MUST reject conditional private rules. That invariant applies whenever grants, forbids, role definitions, group memberships, or visibility permissions (such as revoking list) change. The policy-administration plane enforces this check when policy writes are validated and committed, rather than deferring it to QueryPermissionContexts at read time. Coarsening in projection may only drop claims or merge claims whose union is exact, and MUST NOT widen a region or drop a hole. The disclosure principle covers everything in response payloads and errors, including budgets and descendants_omitted (computed from disclosable rules only); it does not cover response timing or byte length, which deployments with side-channel requirements mitigate separately.

3.7 Evolution Safety: New Operations Under Existing Grants

Class selectors make policy forward-compatible, and that convenience carries a risk: a new RPC classified READ is immediately granted to every role selecting READ on its resource type. Nobody edited a role, and nobody was asked. The specification pairs class selectors with built-in safeguards:

  1. Capability diff. The build compares the descriptor interpretation before and after a change and reports, for each role, every key gained and lost. The change is accepted only after that generated diff is reviewed and acknowledged.
  2. Explicit-grant-only operations. An operation marked explicit_grant_only is never matched by a class selector in a permit; a role holds it only by naming the operation explicitly. A forbid by class still matches it, so "forbid DELETE here" still blocks the most sensitive deletes. AIP-164 requires an expunge permission separate from delete [28]; this marker enforces that rule and suits any irreversible or high-risk operation.
  3. New resource types. A wildcard type selector (*) picks up a new resource type the same way, and the capability diff surfaces it. Prefer explicit resource-type selectors on sensitive roles.
  4. Reclassification. Changing an operation's access class moves it between roles; the capability diff reports the exact losses and gains for review.

  5. Descriptor refresh and descriptor_etag. Because clients derive static method facts directly from protobuf descriptors without generated glue code (§4.2), a client's cached descriptors can temporarily lag behind a newly deployed server during a rollout. Every QueryPermissionContextsResponse carries an opaque server-computed descriptor_etag (formatted as an RFC 7232 ETag per AIP-154 [32]) identifying the server's active descriptors, with no client-side canonical hashing required:

    • A browser client fetching a FileDescriptorSet (or optional cached interpretation) over HTTP compares descriptor_etag with the HTTP ETag of its cached descriptors and re-fetches on mismatch.
    • A gRPC Server Reflection client (such as an MCP server, since gRPC reflection itself carries no ETag) records the descriptor_etag returned on its initial QueryPermissionContexts call and refreshes its descriptors via reflection whenever a later response returns a different descriptor_etag.

    Before a client finishes refreshing, expanded permission keys keep additive releases and access-class reclassifications sound: an unknown key from a newer server is simply skipped, and a newly added operation is absent from an older server's context. Only an in-place change to an existing method's requirements, accepted resource patterns, or effect can mislead a stale client until it refreshes descriptors (and the server still enforces authoritatively, triggering a refresh on PERMISSION_DENIED). Breaking changes to existing RPCs follow AIP-180 and AIP-185 versioning [33].

Counterexample 4 — A Class Claim Across Versions

Suppose contexts carried "READ on Widget at companies/A" instead of keys. Version 2 of the service adds ExportWidgets, classified READ, with a forbid for Alice at Team C. A client that already has the version 2 descriptors and still holds a version 1 context folds ALLOW for ExportWidgets at Team C: the claim never considered that operation. With keys, widgets.export is simply absent from the old context. This is why selectors stay on the server (§3.3).

3.8 Caching, Freshness and Cardinality

Freshness and multi-replica ordering are real distributed-systems problems, and clients should not have to implement a distributed state machine to fold permission contexts. The specification therefore keeps the wire freshness contract tiny and opaque, while keeping multi-replica ordering and proof-cache keying on the server.

Snapshot freshness on the wire

  • Opaque snapshot_token. Every QueryPermissionContextsResponse carries a non-empty opaque snapshot_token identifying the coherent policy snapshot from which its contexts were computed. Clients never parse it; they compare snapshot_token for string equality only (to confirm that targets in a multi-target fold such as MoveWidget come from one coherent snapshot).
  • Monotonicity via min_snapshot_token. A client sends its latest accepted snapshot_token back as min_snapshot_token on subsequent queries. Inside the opaque token, the server encodes whatever revision authority, epoch, and monotonic counter its policy store uses. A replica whose policy state is behind min_snapshot_token, or that serves a superseded epoch after failover, refuses with UNAVAILABLE (and a malformed token returns INVALID_ARGUMENT). A replica at or ahead of the floor, or on a newer epoch or authority after failover, answers with its current snapshot_token.
  • Safe concurrent requests without client-parsed generations. A client may have multiple QueryPermissionContexts calls in flight at once. When a reply arrives for the current sign-in session and subject_context_id: if its snapshot_token equals the client's current token, merge its contexts into that snapshot; if its snapshot_token differs, accept and advance to it only if the min_snapshot_token sent with that request still equals the client's current token. Otherwise another request already advanced the client while this call was in flight, so the late reply is discarded. That prevents lagging replies from ever regressing client state without exposing numeric generations or epochs on the wire.
  • Expiration via AIP-214 expire_time. Every response carries a google.protobuf.Timestamp expire_time (AIP-214, AIP-148 [34]), set to the earlier of the proof expiry and the caller's session or credential expiry. Clients reject responses with an absent or already-elapsed expire_time, and re-check now < expire_time on every fold. Because contexts are strictly advisory and real clients already rely on wall-clock timestamps for TLS certificates and OAuth/JWT exp claims, clock skew creates no security hazard: a client clock running ahead of the server fails safe into cache misses, and a slow clock only widens an advisory cache window while backend enforcement revokes immediately.

Server-side shared proof cache

Inside the server, a shared proof cache keys entries by every input that can change a proof: service, descriptor_etag, internal revision authority, internal revision epoch, projection-dependency revision, effective principal, canonical claims digest, tagged canonical anchor, and profile. Every component MUST be present; any missing component fails closed (bypass cache). Internal authority and epoch stay in the server cache key so a counter reset after failover never serves a stale proof.

The canonical claims digest covers every authenticated input policy reads: effective principal and delegation chain, tenant, credential ceiling, authentication assurance, stable network or device posture, and whatever determines scope visibility (§3.6), since callers with identical grants but different visibility must not share proofs. Version the serialization, sort sets, preserve ordered lists, type values, and distinguish absent from empty. Do not hash wall-clock time; cap proof expiry at the next provable time-policy boundary or skip caching.

Shared proof entries are session-independent: they MUST NOT store a subject_context_id, session ID, or session-capped expiry. On every response (including cache hits), the server stamps the caller's subject_context_id, the pinned snapshot's snapshot_token and descriptor_etag, and expire_time = min(proof_expire_time, session_expire_time).

Staleness and cardinality

Refresh the affected anchor whenever the server returns PERMISSION_DENIED on an RPC, without retrying mutations automatically; expiry and periodic revalidation also pick up newly granted permissions. After a revocation, the server denies immediately once it observes the new policy revision. An unexpired snapshot may still show the control until it expires or refreshes, and confers no authority.

  // clients defer to the server for it.

  // annotated where they are defined, such as those of
  // google.longrunning.Operations: each served one with its form, and
  // each other one as unimplemented.
  repeated ImportedMethod imported_methods = 3;
}

// The disposition of one RPC defined in an imported proto.
message ImportedMethod {
  // Full method name: "google.longrunning.Operations/GetOperation".
  string method = 1;

  // Any form except `standard`. Unset when unimplemented is true.
  MethodAuthz authz = 2;

  // The RPC changes nothing. The service cannot add an option to an RPC
  // defined in another proto, so this flag says what
  // idempotency_level = NO_SIDE_EFFECTS would say there; an RPC whose
  // own descriptor already sets that option needs no flag. Checked
  // like the option (§4.2): it cannot label as read-only an RPC whose
  // requirements create, update, delete, or execute.
  bool no_side_effects = 3;

  // Listing it lets the build confirm that every RPC of an imported
  // service the API implements was considered. Set alone: an
  // unimplemented RPC has no authz and no effect to describe.
  bool unimplemented = 4;

  // on the resource type of the first requirement. Some method of the
  // service must declare that operation.
  string item_filter = 4;

    CREATE = 2;

    // Removes a resource.
    DELETE = 4;

    ADMIN = 5;

    EXECUTE = 6;

  string operation = 2;

  // service_root, the type the key belongs to. A field that holds a
  // parent's name carries child_type instead.
  string resource_type = 5;

  // that field is true.
  string condition = 6;

  // naming the operation (§3.7).
  bool explicit_grant_only = 7;

  repeated string wildcard_variables = 8;

A method declares exactly one form: standard derives the requirement from the AIP standard or batch method shape; requirements lists what a custom method needs, each entry carrying an access class and an operation; and handler_policy names a policy the service enforces in code.

The contracts follow the AIPs they build on, and every published proto file in this specification passes Google's AIP linter with no findings. Integer fields are signed (AIP-141). An enum used by one message is nested in it with unprefixed values, and a shared enum sits at the end of its file with prefixed values (AIP-126, AIP-191). syntax = "proto3";

package authz.v1;

import "google/api/annotations.proto";
import "google/api/field_behavior.proto";
import "google/api/resource.proto";
import "google/protobuf/timestamp.proto";

option java_outer_classname = "PermissionContextProto";
option java_package = "com.example.authz.v1";

// Advisory permission contexts for the authenticated caller.
service PermissionContextService {
  option (authz.v1.service) = {
    api_service: "authz.example.com"
    required: true
  };

  // Returns advisory claims about what the authenticated caller holds
  // within each requested anchor. Never a credential.
  rpc QueryPermissionContexts(QueryPermissionContextsRequest)
      returns (QueryPermissionContextsResponse) {
    option (google.api.http) = {
      post: "/v1:queryPermissionContexts"
      body: "*"
    };
    option idempotency_level = NO_SIDE_EFFECTS;
    option (authz.v1.method) = {
      handler_policy: "authenticated_subject_disclosure"
    };
  }
}

// Request message for QueryPermissionContexts.
message QueryPermissionContextsRequest {
  // Logical API service whose operations are queried: "widgets.example.com".
  string service = 1 [(google.api.field_behavior) = REQUIRED];

  // One or more anchors: the service root or resource names.
  repeated Anchor anchors = 2 [(google.api.field_behavior) = REQUIRED];

  // Highest profile the client implements. The server never sends more.
  // Unspecified means PROFILE_GRANT_SHAPED.
  Profile max_profile = 3 [(google.api.field_behavior) = OPTIONAL];

  // Opaque snapshot_token from a previously accepted snapshot (§3.8).
  // The server answers from a snapshot at least as new, fails with
  // UNAVAILABLE if lagging or on a superseded epoch, or fails with
  // INVALID_ARGUMENT if the token is malformed.
  string min_snapshot_token = 4 [(google.api.field_behavior) = OPTIONAL];
}

// Response message for QueryPermissionContexts: one coherent snapshot.
// Every context below shares these fields.
message QueryPermissionContextsResponse {
  // The logical API service this snapshot describes.
  string service = 1;

  // Opaque RFC 7232 ETag (AIP-154) over the active descriptors used to
  // compute this snapshot (§3.7, §4.2). Clients compare it for equality
  // to detect when their local descriptors need a refresh.
  string descriptor_etag = 2;

  // Identifies the subject and the authenticated inputs of this snapshot.
  string subject_context_id = 3;

  // Opaque non-empty identifier of the policy snapshot. Clients compare
  // it for equality only and pass it back as min_snapshot_token (§3.8).
  string snapshot_token = 4;

  // Absolute expiration time of this snapshot (AIP-214, AIP-148): the
  // earliest expiry across every underlying proof and the caller's
  // session or credential.
  google.protobuf.Timestamp expire_time = 5;

  // The profile actually used; never above max_profile.
  Profile profile = 6;

  // Each distinct set of permission keys, once.
  repeated KeySet key_sets = 7;

  // Sparse: an anchor that does not resolve for the caller is omitted.
  repeated PermissionContext contexts = 8;
}

// The service is named once, on the request and the response.

  oneof target {
    // The tagged service root.
    ServiceRoot service_root = 1;

    // A relative resource name, such as "companies/A/teams/B".
    string resource = 2 [(google.api.resource_reference) = {
      type: "*"
    }];
  }
}

// The scope of a claim, or one of its holes (AIP-122).
message Scope {
  // Exactly one arm is set.
  oneof target {
    // The tagged service root.
    ServiceRoot service_root = 1;

    // A relative resource name, such as "companies/A/teams/B".
    string resource = 2 [(google.api.resource_reference) = {
      type: "*"
    }];

    // A collection, written as its relative path, such as
    // "companies/A/teams": every resource in it.
    string collection = 3;
  }
}

// A set of permission keys shared by the claims that reference it.
message KeySet {
  // Starts at 1. 0 is never a valid id.
  int32 id = 1;

  // Sorted, without duplicates.
  repeated string keys = 2;
}

// The claims for one anchor.
message PermissionContext {
  // Canonical. A context is identified by this anchor.
  Anchor anchor = 1;

  // What the caller holds at or below the anchor.
  repeated Claim claims = 2;

  // Claims below this anchor were withheld for budget. Query narrower
  // anchors; the absence of a claim is not a denial.
  bool descendants_omitted = 3;

  // The anchors of the request this context answers, exactly as sent:
  // the canonical name itself, or an alias that resolved to it.
  repeated Anchor requested_anchors = 4;
}

// A statement about a set of keys over a scope, except its holes.
message Claim {
  // At or below the context's anchor.
  Scope scope = 1;

  // KeySet.id. The claim applies to every key in that set.
  int32 key_set = 2;

  // What a claim asserts. Values may be added; a client discards a
  // context that carries a kind it does not know.
  enum Kind {
    // Invalid.
    KIND_UNSPECIFIED = 0;

    // Proven allow at every in-domain point of the region.
    ALLOW = 1;

    // Proven denial at every in-domain point of the region.
    DENY = 2;

    // An unresolved predicate. Asserts no decision.
    CONDITIONAL = 3;
  }

  // Grant-shaped profile: ALLOW only.
  Kind kind = 3;

  // Strict descendants of scope. Empty in the grant-shaped profile.
  repeated Scope holes = 4;
}

// How much a context may carry. Values may be added; a client rejects
// a snapshot whose profile it does not know.
enum Profile {
  // Treated as PROFILE_GRANT_SHAPED in a request. Invalid in a response.
  PROFILE_UNSPECIFIED = 0;

  // Hole-free ALLOW claims only.
  PROFILE_GRANT_SHAPED = 1;

  // Adds holes, DENY, and CONDITIONAL.
  PROFILE_SCOPED_CLAIMS = 2;
}

Anchors

An anchor is the service root or a resource name, and the Anchor message has no other arm. A resource arm holding anything other than a resource name of the service, such as a collection or a root written as //svc/, is rejected with INVALID_ARGUMENT: the root is carried only as the service_root arm. An empty anchor list, and an anchor with no arm set, are rejected with INVALID_ARGUMENT. Exact duplicates in the request as submitted, compared by value (the same arm with the same string), are rejected with INVALID_ARGUMENT before anything else is examined, which reveals nothing. The server then resolves aliases. An alias resolves for a caller only if the caller is allowed to know what it names: it is the caller's own, such as users/me, or the caller could read the resource it names. An anchor that does not resolve is omitted, with no per-anchor error and no placeholder, so the response is identical whether an alias is unknown or names something hidden. Anchors that resolve to one canonical name yield one context, identified by its canonical anchor, which lists in requested_anchors every anchor of the request it answers, exactly as sent. A client that asked through an alias finds its context that way without disclosing anything further.

A canonical name needs no visibility check, because its context says nothing about whether the resource exists. Contexts are pure functions of the policy rules that apply to the caller and never read stored resource rows, so the context for a name where the caller holds nothing is the same whether or not a resource exists there. It may have zero claims.

Claims

A claim's scope and holes are validated against the service's pattern trie, not with generated resource-name parsers, because a collection is not a resource name. A scope must lie at or below the context's anchor and be a place where every key in the claim's set can apply (the start of at least one of each key's binding patterns); a hole must be a strict descendant of its claim's scope. A claim referencing a missing key set, an unset arm, or an unknown or unspecified kind invalidates its whole context (§4.4). A key that the client's own descriptors do not define is skipped rather than treated as corruption: it comes from a server whose declarations are newer than the client's (§3.7). Unknown or incompatible data MUST NOT produce an allow.

The root anchor

Querying the service root (Anchor { service_root {} }) returns claims at every scope where the caller holds a grant, letting a UI or MCP host discover usable scopes before any resource has been chosen (§3.3). A key missing from a root response is unproven rather than denied, because Grant-Shaped forbids, conditional permits, nonprojecting privacy boundaries, or descendants_omitted can withhold it. A server MAY withhold claims below any anchor for budget and sets descendants_omitted; the client then queries narrower anchors. Kubernetes reports an incomplete rules review in the same way [16].

Wire compatibility

These messages are not wire-compatible with earlier revisions of this report. A deployment that shipped an earlier revision publishes this contract under a new package version instead of changing the old one in place [33].

4.2 Descriptor Interpretation & Method Declarations

Direct interpretation of protobuf descriptors (a FileDescriptorSet) is the core norm: nothing in this architecture requires generated code or a build-time JSON compiler. Server-side clients such as MCP tool hosts read descriptors through gRPC Server Reflection; browser clients fetch a FileDescriptorSet (or an optional server-cached equivalent carrying the same HTTP ETag) over HTTP. Any cached representation carries no authorization fact of its own and is valid only if it equals the interpretation.

What an interpreter derives from an API's descriptors (the interpretation) is normative: conforming interpreters MUST derive the same result from the same descriptors. Conforming interpreters apply the following rules:

  1. API service name. Every interpreted service has one logical AIP-122 API service name (such as widgets.example.com), which clients send in QueryPermissionContextsRequest.service and use to isolate permission keys across services (§3.4). An interpreter derives it from the shared {Service Name} prefix of every message-level google.api.resource option defined in the service's own protobuf package (excluding file-level google.api.resource_definition references to external services); for example, widgets.example.com/Widget and widgets.example.com/Team share widgets.example.com. When a service defines no resource types of its own, or defines resources under multiple service names, ServiceAuthz.api_service MUST be set explicitly; when set alongside resource definitions that all share one prefix, it must match that prefix or the build rejects it. Never derive the API service name from google.api.default_host: AIP-122 permits one logical service to expose multiple regional, mTLS, or private endpoints while keeping a single resource-type service name [2].
  2. Disposition and imported methods. In a service whose option sets required, every RPC carries exactly one form of MethodAuthz, and every RPC of each imported service the API implements is listed in imported_methods, either with a form or marked unimplemented. An API implements google.longrunning.Operations whenever any of its methods returns an Operation, because AIP-151 requires it without copying the Operations proto [5]; any other imported service is identified by listing one of its RPCs, after which every RPC of that imported service must be listed. Because all of this is visible in the descriptors, an omission fails the build (for example, in a buf lint plugin) rather than surfacing after deployment. Where required is false, an undeclared RPC is outside this contract: the service enforces it by other means and clients defer to the server. A handler_policy names an authoritative policy registered in code, covering intentionally public, authenticated-self, and exempt methods as well as rules that cannot be decomposed into independent requirements. item_filter and partial_success accompany requirements only.
  3. Standard methods. standard is valid only on an AIP standard or batch method of a resource: the RPC name is the standard verb followed by the resource's type name (or plural for List and batch methods), and its request matches the shape in AIP-131 through AIP-135 or AIP-231 through AIP-235 [26] [9]. A method named GetAccessPolicy taking a team name is a custom method because the noun is not the resource's type, and AIP-136 advises against standard verbs on custom RPCs. standard derives one requirement from the table below.
  4. Target binding. Standard methods take their target from the table below. When a custom requirement sets neither target_field nor service_root, the target defaults to the request's name field, then parent, then the name field of the first singular message field (in declaration order) whose message carries google.api.resource. Batch methods bind every item: names[], or requests[] followed by the standard path. A BatchCreate item omitting its parent inherits the request's top-level parent (AIP-233), unless that top-level parent is a wildcard. A path expands at most one repeated field and ends at a singular string. An absent, empty, malformed, or non-matching value binds no target; a requirement is never satisfied by zero targets.
  5. Resource type. The target field's google.api.resource_reference supplies the resource type: type names the resource itself, and child_type names the resource type whose parent the field holds [3]. A resource message's own name field supplies its type; a top-level List uses the response's repeated resource field, and a top-level Create uses the resource field in its request. Where none applies, resource_type is stated explicitly and must agree with any reference annotation on the field. A parent field carries child_type rather than resource_type. A root-bound requirement with no type uses the reserved service type.
  6. Binding patterns. A requirement on a resource binds to that type's patterns. A requirement on a parent binds to each pattern with its final collection and ID removed (or its final literal removed for an AIP-156 singleton [6]); the parent of a top-level pattern is the service root. A key required by several methods binds to the union of their patterns.
  7. Permission key. The permission key is the resource type's plural, a dot, and the lower-camel-case operation: widgets.get. AIP-123 defines plural and AIP-156 requires it for singletons [3] [6]; this specification requires plural on every referenced resource type. The reserved service type has plural service (for example, service.exportAuditLog). An item_filter names a declared READ operation on the resource type of the method's first requirement.
  8. Access class and explicit grants. A standard method's class is fixed by its kind. Every custom requirement states its access_class; unspecified or unknown values are rejected. All requirements sharing a key must agree on resource type, class, and explicit_grant_only. For soft-delete recovery (AIP-164 [28]), Undelete is declared UPDATE class (so a delete forbid does not block recovery), while Expunge is declared DELETE class with explicit_grant_only = true.
  9. Conditional requirements and upserts. A requirement with condition applies only when the named bool request field is true. A standard Update (or BatchUpdate) whose request declares allow_missing automatically derives a conditional requirement: create on the bound resource's parent when allow_missing is true (read per item in BatchUpdate). A field hoisted to the top level of a batch request (AIP-233, AIP-234) counts as set on every item.
  10. Method effect. A declarative method is READ_ONLY if every requirement it declares or derives (conditional ones included) is READ, or if it declares idempotency_level = NO_SIDE_EFFECTS (or no_side_effects on an imported RPC) and none of its requirements is CREATE, UPDATE, DELETE, or EXECUTE. Otherwise it is DESTRUCTIVE if any requirement is DELETE, and MUTATING if none is. A handler_policy method is READ_ONLY when its descriptor sets NO_SIDE_EFFECTS or its imported_methods entry sets no_side_effects; otherwise its effect is UNKNOWN, and read-only credentials exclude it.
  11. Partial success. Synchronous methods are atomic (NEVER). An Operation-returning batch method whose request declares return_partial_success is REQUEST_SELECTED; one whose metadata declares failed_requests with no request flag is ALWAYS [9].
  12. Descriptor ETag. The server computes an opaque RFC 7232 ETag (descriptor_etag, AIP-154 [32]) over the active descriptors it interprets and stamps it on every QueryPermissionContextsResponse (and as the HTTP ETag header when serving a descriptor bundle). Any declaration change that alters requirements, keys, binding patterns, effects, or enabled extension options MUST produce a new descriptor_etag. Clients do not hash descriptors themselves: browser clients compare descriptor_etag against the HTTP ETag from their descriptor fetch, and gRPC reflection clients record the descriptor_etag from their initial context reply and re-fetch reflection descriptors when it changes (§3.7).

Order of Checks and the Error Status

A service checks authorization before validating a request (AIP-211, must) and before learning whether the resource or its parent exists (AIP-193, must) [8] [27]. It parses only enough of the request to bind the declared targets. A requirement whose target cannot be bound has no scope to authorize, and the request is denied.

A denial returns PERMISSION_DENIED. Following AIP-211, the message reads Permission '{permission}' denied on resource '{resource}' (or it might not exist). with the permission key and the name exactly as the caller supplied it. AIP-193 requires an ErrorInfo on every error and requires every dynamic part of the message to appear in its metadata. Disclosure rules therefore cover the whole status: code, message, reason, domain, metadata, and any other detail. Cases that must be indistinguishable (an absent row and a hidden row; a hidden duplicate and any other denial; an unknown alias and one whose target the caller may not see) MUST produce the same status in every field. Echo only values the caller supplied (never a resolved canonical name, an alias target, an owning parent, or a policy identifier), and bound and escape echoed values so a supplied name cannot forge log lines.

The same checks apply when validate_only is set: AIP-163 requires permission checks on dry runs [28]. A page token continues a query; AIP-158 forbids it from carrying authorization, so every page is authorized again. A permission change between pages therefore takes effect on subsequent pages, and a token never extends what the caller may see.

Missing Resources

Existence and authorization are determined in one consistent policy snapshot. For a resource that does not exist:

  • If the caller's grants already decide the request for that name, the decision stands: an allow yields NOT_FOUND, and a denial yields PERMISSION_DENIED.
  • If the decision cannot be made solely because the row is absent (for example, because a rule depends on the row's attributes), the service checks the list permission on the parent (AIP-211's "authorization to read children on the parent"). If allowed, the status is NOT_FOUND; otherwise PERMISSION_DENIED.

The list permission qualifies because a holder could list the collection and observe the child's absence. The check does not recurse: if the parent's decision is not determinable either, the status is PERMISSION_DENIED. For a top-level resource the parent is the service root. A resource type with no List method offers no such check, so a decision depending on its missing row returns PERMISSION_DENIED. A method with several requirements returns NOT_FOUND only if every requirement depending on the missing row passes the check. A resource is hidden from a caller holding neither get on it nor list on its parent; a forbid on get alone does not hide it from someone who can list the parent (below). A parent allow never overrides a denial on an existing resource, and an absent or unbindable request field is not an absent row.

List and Search

AIP-132 says a List should return the same results to any caller permitted to list the collection, and that Search methods are more relaxed [26]. This specification requires uniform List results. An existing API whose List filters by caller changes what those callers see when adopting this rule, so it ships a Search RPC first. A List is authorized by one check (the list key on the parent) and returns the full collection with the same total_size and page tokens for every permitted caller.

Before designing roles, account for what uniform List implies:

  • The List permission discloses every child. AIP-132 says List should return populated resources, so holding list on a parent is at least as revealing as holding get on each child. A forbid on get at one child does not hide that child from someone who can list its parent. Authoring tools SHOULD warn when such a forbid is written.
  • Existence cannot be hidden from siblings inside one List collection. A caller who must see only some children is granted a Search method instead of list, or confidential children are placed under a separate parent.

A Search method is a custom collection fetch method (AIP-136), such as GET /v1/{parent=companies/*/teams/*}/widgets:search. It declares its own operation and an item_filter, the operation every returned item must pass. The service applies the filter in the query or via an authoritative bulk check of candidates, and counts, page sizes, and tokens reveal nothing about rejected items. A Search with a wildcard parent applies its own key per parent as a filter; a caller holding it nowhere receives an empty result, indistinguishable from having no matching items. The same empty result is returned when the wildcard's fixed prefix names a missing parent unless the caller may see whether that parent exists: companies/UNKNOWN/teams/- never returns NOT_FOUND to someone who cannot see companies. A server MAY refuse a wildcard Search up front with PERMISSION_DENIED before validating its query when the caller's grants prove no matching parent can pass (for instance, a credential excluding reads or a forbid covering all matching parents); that reveals nothing an empty result would not and avoids a pointless scan.

Wildcards

AIP-159 lets a List accept - for a parent ID and says nothing about authorization [7]. A wildcard parent names a set of parents, not a single resource. Because uniform List returns identical results to every permitted caller, a wildcard List is authorized only if the list key holds for every potential parent the wildcard matches: in the grant model, a permit at or above the fixed prefix before the wildcard with no interrupting forbid below it. A caller holding list in only some parents lists them individually or uses Search.

That rule avoids inventing an extra wildcard-invocation permission (which would have nothing to bind when multiple segments are wildcards) and lets clients fold wildcard Lists locally: ALLOW when one ALLOW claim covers every matching parent, DENY when a DENY claim covers at least one. When the deployment allows private rules for the list key, the check is refused above their privacy boundary in every case, because passing only when no hidden rule exists would reveal the rule (§3.6).

- is accepted only as the whole ID segment of a declared wildcard variable; results carry canonical names with real parent IDs; and a batch item omitting its parent never inherits a wildcard top-level parent. AIP-217's unreachable field reports parents that are temporarily unavailable [29]. Holding list in every matching parent does not mean the caller may see the parents themselves: listing widgets across every team of company A is not listing teams. A server therefore names an unreachable parent only if the caller could see it (via get on it, list on its parent, or the deployment's declared visibility rule for unserved parents in §3.6), and otherwise fails the request with UNAVAILABLE rather than returning a partial answer.

AIP-159 permits a wildcard on Get only where IDs are unique across parents. The service resolves the resource first and then applies the Get rule to the resolved resource. No match, a hidden match, and a denied match all return the same PERMISSION_DENIED; NOT_FOUND is returned for no match only to a caller who holds list in every matching parent or get on every name the wildcard could match, and only when no private rules are permitted there for the proving key (§3.6). Multiple matches indicate a broken uniqueness invariant: log a server fault and answer with the same PERMISSION_DENIED.

Name Collisions

Any method that can collide with an existing name follows one rule: Create with a caller-chosen ID, Move or Rename to a destination, and each item of a BatchCreate. Update with allow_missing is not among them: on a taken name it updates that resource (AIP-134). Suppose Alice may create widgets in Team B and asks for ID w7, which already exists but is hidden from her. Answering ALREADY_EXISTS would tell her w7 exists. The service therefore authorizes the operation's own requirements first. If the name is taken, it checks in the same policy snapshot whether the caller can see the existing resource (get on it or list on its parent). It returns ALREADY_EXISTS only if that check allows, and otherwise returns PERMISSION_DENIED naming the method's own permission and caller-supplied target (such as widgets.create on the parent, never the visibility check), so a hidden collision is identical in every field to an ordinary denial.

Here AIP-133 and AIP-211 pull in opposite directions, and AIP-133 governs. AIP-211 (Authorization Checks) says a method should check only its own permission when selecting an error and not consult a related read permission. Followed alone, Create would return ALREADY_EXISTS and leak the hidden widget. AIP-133 (Create) states as a must that a duplicate ID returns ALREADY_EXISTS only if the caller has permission to see the duplicate, and PERMISSION_DENIED otherwise. Because a MUST overrides a SHOULD, Create consults visibility for this one error decision after its own permission passes.

One inference remains: a caller who can create widgets under a parent and is refused for one specific ID can infer that something hidden holds that name. The status reveals nothing further, and no permission snapshot predicts the refusal (§1.1). Services that cannot accept that inference assign IDs on the server.

Update, Upsert, and Delete

For an upsert, AIP-134 requires the caller to hold the update permission when allow_missing is set and suggests conditions to restrict creation. This specification adopts a stricter local rule: a request with allow_missing = true also requires create on the resource's parent, decided strictly from the request. A caller holding only update sends allow_missing = false and receives NOT_FOUND for a missing resource, as AIP-134 specifies.

AIP-135's allow_missing on Delete makes a missing resource a successful no-op. It adds no extra permission requirement, but its response on a missing row follows the missing-resource rule above: OK where the request would otherwise return NOT_FOUND, and PERMISSION_DENIED otherwise. Without that rule, an owner-only delete policy would answer OK for an absent widget and PERMISSION_DENIED for someone else's existing widget, disclosing existence. A cascading delete (force) requires at least delete on the named resource; a service that also checks delete on every child type declares the method as a handler_policy because standard cannot express subtree-wide child checks. FAILED_PRECONDITION (children present) and ABORTED (etag mismatch) are returned only to an authorized caller.

Batch Methods

A batch method applies its singular method's requirement to each item. AIP-231 notes that the top-level parent field exists "to permit a single permissions check" [9]. In this model, that check asks whether the item's key holds everywhere under the stated parent; if so, every item under it is authorized at once. Server execution follows these steps in order:

  1. Bind every item that can be bound and authorize it, even if another item is unbindable. Items under the top-level parent may be authorized by one universal check on that parent. When the top-level parent contains a wildcard (such as companies/A/teams/-), that check covers everything under every team the wildcard matches, so a forbid on one widget in one team fails the shortcut. Any item outside that parent, and every item when the universal check fails or is refused because private rules are permitted below the parent (§3.6), is authorized individually. An unauthorized item from another parent is therefore denied before step 4 could reveal a parent mismatch.
  2. If any bound item is unauthorized, a synchronous or atomic batch returns PERMISSION_DENIED without identifying the item: the message names the top-level parent if present, and otherwise only the permission. No validation result is revealed first.
  3. An unbindable item or an empty batch has no scope to authorize. Return INVALID_ARGUMENT only when the universal check on the top-level parent passes for every key its items would require (including optional field guards an unbindable item's write would trigger when §4.5 is enabled); with no top-level parent, or when the check fails, return PERMISSION_DENIED.
  4. Only then validate the request: an item whose own parent is not the top-level parent (direct parent match, as AIP-231 through AIP-235 require), duplicate items, and malformed fields return INVALID_ARGUMENT.
  5. Atomic mutations are fully authorized before any partial commit becomes visible.

Synchronous batch methods are atomic; an Operation-returning batch may report partial success, and an existing API adopts it through return_partial_success (AIP-233 through AIP-235). A requirement is item-level when evaluated once per item (targeting requests[] or names[], checking each item of a top-level batch on the service root, or triggered by one item's optional field guard); all other requirements are operation-level. In a partial batch, a failed operation-level requirement denies the whole request before any item runs. Otherwise each failed item is reported at its request index in failed_requests with the status its singular method would return, and if every item fails the operation's error is ABORTED.

Long-Running Operations

AIP-151 requires implementing google.longrunning.Operations whenever a service returns an Operation, without specifying who may inspect an operation. Declarations for served and unimplemented Operations RPCs live in ServiceAuthz.imported_methods (§4.2). On the server, the typical handler_policy binds each operation to its creator, rechecks the originating method's requirement on GetOperation and WaitOperation so revocations stop polling immediately, and filters ListOperations to operations the caller is permitted to get.

4.4 Server & Client Algorithms

The request handler and the context endpoint share one grant resolver. On the client, static descriptor screening (method_available) runs ahead of request-time folding (offer), cleanly separating static capability checks from snapshot evidence.

method_available(method, ceiling):
  m = interpretation[method]
  if m is listed as unimplemented:
    return UNAVAILABLE(UNIMPLEMENTED)           # server never serves this RPC
  if m is undeclared or cannot be interpreted:
    return UNAVAILABLE(EFFECT) if ceiling is read-only else AVAILABLE
  if m is a handler policy:
    return UNAVAILABLE(EFFECT) if ceiling is read-only and m.effect != READ_ONLY else AVAILABLE
  if ceiling is present:
    for each unconditional requirement r of m:
      if (r.resource_type, r.access_class) is outside ceiling:
        return UNAVAILABLE(CEILING)             # credential can never satisfy m
    if ceiling is read-only and m.effect != READ_ONLY:
      return UNAVAILABLE(EFFECT)                # e.g. mixed-effect method under read-only token
  return AVAILABLE                              # safe to register / evaluate per request
Client: folding accepted snapshots for one operation (pseudocode)
offer(method, request, ceiling):
  if method_available(method, ceiling) is UNAVAILABLE:
    return (method excluded statically; do not call offer)
  m = interpretation[method]
  if m is undeclared, uninterpretable, or a handler policy: return DEFER
  reqs = active requirements of m for request (per item in a batch)
       + optional field guards for fields request writes (only when §4.5 is enabled)
  if reqs is empty: return DEFER
  if m is a partial batch for request:
    op_reqs = operation-level requirements in reqs
    if any r in op_reqs exceeds ceiling: return DENY(CEILING)
    op_eval = fold_requirements(op_reqs, request)           # evaluated in newest accepted snapshot; expired -> UNLOADED
    if op_eval is DENY: return DENY(POLICY)
    if op_eval is DEFER: return DEFER
    for each item i of request:
      item_reqs = item-level requirements for item i
      if any r in item_reqs exceeds ceiling:
        item_result[i] = DENY(CEILING); continue
      item_result[i] = combine(op_eval, fold_requirements(item_reqs, item i))
    return item_result[]                                    # indexed by request item
  if any r in reqs has (r.resource_type, r.access_class) outside ceiling:
    return DENY(CEILING)                                    # checked before binding; no snapshot refresh
  results = []
  for r in reqs:
    targets = bind(r, request)                              # canonical names only (§3.4)
    if invalid or empty: return DEFER
    for t in targets:
      if t has a wildcard and (m declares item_filter or r targets a resource): return DEFER
      snap = newest accepted snapshot whose valid context covers t
      v = UNLOADED if snap is absent or expired (now >= snap.expire_time) else verdict(snap, r.key, t)
      results.add((v, snap))                                # universal verdict for a wildcard
  if any result is DENY: return DENY(POLICY)
  if every result is ALLOW and all share one snapshot_token: return ALLOW
  if any result is UNLOADED, or the allows span snapshot_tokens: return UNLOADED
  return CONDITIONAL

Accepting a snapshot

A client keeps isolated state per logical service: the current subject_context_id, the current snapshot_token, a list of accepted snapshots (retaining recently superseded or expired snapshots until a newer snapshot replaces their coverage, so an expired revocation never falls back to an older allow), and the last observed descriptor_etag. A response is accepted only if service matches the requested service (otherwise discard without touching state), descriptor_etag, subject_context_id, and snapshot_token are non-empty, expire_time is strictly later than the client's current time, and profile is known and not above max_profile.

The client tags each outbound request with its local sign-in session and a monotonically increasing local request sequence, and discards any reply arriving for an earlier session or dispatched before the most recent reset. A changed subject_context_id on a current-session reply resets cached snapshots and snapshot_token for that service and advances the reset sequence floor so earlier in-flight replies cannot trigger a second reset. Within the same subject context, concurrent in-flight requests obey a single monotonicity rule:

  • If the reply's snapshot_token equals the client's current snapshot_token, merge its valid contexts into that snapshot (a newer context for an anchor replaces an earlier context for the same anchor; each context retains its own expire_time).
  • If the reply's snapshot_token differs from the client's current snapshot_token, accept it and advance the client's current token only if the min_snapshot_token sent with that request still equals the client's current token (or the client held no token yet). Otherwise a newer reply already landed while this request was in flight, and this late reply is discarded.

A later snapshot in a lower profile is valid: it asserts less and is folded as received. If descriptor_etag differs from the ETag of the client's loaded descriptors (browser HTTP ETag or reflection client's last recorded value), the client keeps folding under §3.7's drift rules and schedules a background descriptor refresh without resetting the snapshot state.

Validating a context

Before matching, each context is validated as a whole, and any failing context is discarded completely (every claim for every key): an unknown or unspecified kind; a reference to a missing key set; an unset anchor or scope arm, or an anchor that is neither the root nor a resource name; a scope outside the anchor or outside the key's binding hierarchy; a hole that is malformed, not a strict descendant of its scope, or outside the key's binding hierarchy; a scope arm that disagrees with its string (such as a resource arm holding a collection); any hole or non-ALLOW claim in PROFILE_GRANT_SHAPED; or an overlap between claims of different kinds for one key. One missing hole shows the producer's remaining claims cannot be trusted, so nothing from that context is used. Overlap between claims of the same kind is redundant rather than corrupt, and a key absent from the client's descriptors is skipped (§3.7). Response-wide errors discard the entire response: a key set with id below 1, duplicate key-set ids, unsorted or duplicate keys within a key set, duplicate canonical anchors, or one requested anchor claimed by multiple contexts. Each entry in requested_anchors is validated like an anchor, and an invalid entry discards its context.

Evaluating a target

Each target is evaluated in one snapshot: the newest accepted snapshot containing a valid context whose anchor covers the target. If that newest covering snapshot has expired (now >= expire_time), evaluation returns UNLOADED rather than falling back to an older snapshot, so an expired revocation never resurrects an earlier allow. Within that snapshot, every valid unexpired covering context counts regardless of which response delivered it, so refreshing a broad anchor never hides what a narrower anchor proved under the same snapshot_token; for each anchor only its newest context counts (if that newest context has expired, it is omitted rather than falling back to an earlier context for the same anchor), and descendants_omitted in one context says nothing about another. Claims from different snapshot_tokens are never combined, and an older snapshot is never consulted once a newer one covers the target, so a revocation is never masked. Within the snapshot a claim applies when its key set contains the key, its scope is a segment prefix of the target, and no hole is a segment prefix of the target. If ALLOW and DENY both apply, the producer is in conflict: return UNLOADED without triggering a refetch loop. Otherwise ALLOW or DENY overrides CONDITIONAL regardless of scope depth. A wildcard target is evaluated against a context covering the resource name above its first wildcard (or the service root when the first ID segment is -): ALLOW requires a single ALLOW claim containing every name the wildcard matches, and DENY requires a DENY claim containing at least one.

Folding an operation

Clients screen every method with method_available(method, ceiling) before calling offer. Within offer, active requirements (including conditional requirements and any enabled §4.5 field guards) are checked against the credential ceiling before targets are bound; a ceiling failure returns DENY(CEILING) so the UI does not trigger a pointless snapshot refresh. For policy folding, a DENY on any required target returns DENY(POLICY) even when targets came from different snapshots, because withholding an action is the safer failure mode (§1.1). An ALLOW requires every active requirement to bind at least one target and every target to evaluate to ALLOW under one shared snapshot_token. Atomic batches fold as one unit; partial batches evaluate operation-level requirements once and return per-item verdicts indexed by request position.

Listing what is usable

A menu builder or MCP tool host asking which operations are usable first filters out every method where method_available(method, ceiling) returns UNAVAILABLE. Over the remaining declarative methods, a method is listed for a chosen scope when every unconditional requirement can bind at or below that scope and an ALLOW claim covers the entire scope with no hole intersecting it (handler-policy methods are left available for the server to decide). Queried at service_root with no scope chosen, the listing returns every statically available declarative method whose unconditional requirements appear in ALLOW claims, paired with the regions (scope minus holes) of those claims. That root listing is an upper bound: a listed method can still fail when multi-target requirements sit in disjoint scopes or conditional requirements trigger, and a method missing from the root listing is unproven rather than denied whenever forbids under Grant-Shaped, conditional permits, nonprojecting privacy boundaries, or descendants_omitted apply (§3.3). MCP hosts and UIs therefore keep unproven tools available to attempt or query narrower anchors once a scope is known.

4.5 Optional Extensions: Field Guards

Core authorization works at the method level. Most resource-oriented APIs keep privileged mutations explicit by moving sensitive changes (transferring ownership, changing billing tiers, or approving releases) into dedicated custom RPCs such as TransferWidget. Dedicated RPCs keep write surfaces obvious in audit logs and spare clients from parsing protobuf update masks. When an API already exposes sensitive fields inside standard Create or Update messages and cannot break callers by splitting them out, it can opt into the Field Guards extension defined below.

Core clients, servers, and MCP tool hosts that do not opt into Field Guards ignore (authz.v1.field) completely and never parse update masks or walk resource message fields.

authz/v1/field_guards.proto — Optional Field Guard Extension 
syntax = "proto3";

package authz.v1;

import "google/protobuf/descriptor.proto";

option java_multiple_files = true;
option java_outer_classname = "FieldGuardsProto";
option java_package = "com.example.authz.v1";

extend google.protobuf.FieldOptions {
  // Optional field guard on a resource field (§4.5). A standard Create
  // or Update, or its batch form, that writes this field also requires
  // this operation on the target of the write. A custom method that
  // can write the field lists the operation among its own requirements.
  FieldAuthz field = 51003;
}

// Extra operation required when a standard Create or Update writes one
// resource field. Names no target of its own; checked on the write target.
message FieldAuthz {
  // Access classes a field guard may carry.
  enum AccessClass {
    // Invalid. Every field guard states its class.
    ACCESS_CLASS_UNSPECIFIED = 0;

    // Changes an existing resource.
    UPDATE = 1;

    // Privileged administration, such as ownership.
    ADMIN = 2;
  }

  // The class of the operation.
  AccessClass access_class = 1;

  // Operation name in lower camel case, such as "setOwner". Together
  // with the resource type it identifies the permission key (§3.2).
  string operation = 2;

  // Never matched by a class selector in a permit (§3.7).
  bool explicit_grant_only = 3;
}

Extension Hook & Written-Field Rules

When a service enables Field Guards, descriptor interpretation records each resource's guarded field paths and OUTPUT_ONLY field paths, and adds each guard's derived permission key ({plural}.{operation}) to the service's key set. Guard keys bind to the patterns of the write targets (the parent for Create, the resource for Update, and the parent as well when Update declares allow_missing), so permission snapshots carry them like any other key. Any change to guarded or output-only paths changes the server's descriptor_etag.

At request time, both server enforcement (authorize) and opting-in clients (offer) call one pure hook, extract_field_guards(interpretation, method, request), and append its requirements to the method's active requirements before ceiling checks and folding. Because written fields are computed from the request alone, client and server always derive the exact same guard requirements:

  • Standard Update and BatchUpdate. An omitted update_mask means the populated fields of the resource, listed down to each leaf that is set. A wildcard mask (*) means every writable field. An explicit mask means its listed paths. A mask that is present with zero paths writes nothing (AIP-134 says should; this extension requires it). When allow_missing = true, populated fields are added to the mask set because creating a missing resource applies every populated field, and triggered guards are checked on both the resource and its parent.
  • Standard Create and BatchCreate. Written fields are the populated fields of the resource, checked on the parent (or service root for top-level resources).
  • Output-only fields. Fields marked google.api.field_behavior = OUTPUT_ONLY are stripped from the written set at every depth, including inside a whole message named in a mask [30].
  • Path matching. A guard triggers when a written path names the guarded field, a path inside it, or an enclosing message containing it. Guard paths inside maps or repeated fields use * for map keys or list elements (such as items.*.owner), matching either a specific entry path (items.foo.owner) or a * wildcard segment in the mask.
  • Batch hoisting and validation ordering. Each batch item is guarded from its own write on its own target. A field hoisted to the top level of a batch request (update_mask or allow_missing, per AIP-233 and AIP-234) counts for every item; if an item also sets the field, both values are evaluated prior to validation (even when checking the parent gate for an unbindable item under §4.3 step 3).
  • Custom methods and handler invariant. Field guards are derived automatically only for standard Create, Update, and their batch forms. Any custom RPC that can write a guarded field MUST list that guard's operation among its own requirements. Handlers MUST NOT write any field outside the computed written set.
AIP-161 Compatibility Caveat for Map Keys and Wildcards

As of October 2026, AIP-161 classifies backtick-quoted map keys (such as items.`a.b`.owner) and mid-path * wildcards over repeated fields or maps (items.*.owner) as non-standard extensions that standard protobuf FieldMask runtime libraries do not implement [30]. Services placing field guards inside maps or repeated fields MUST ship matching custom mask parsers on the server and every opting-in client, or restrict field guards to top-level and singular nested message fields, which standard protobuf libraries parse natively.

4.6 End-to-End Walkthrough and Executable Checks

Alice holds two grants: viewer at companies/A and widget-writer at companies/A/teams/B. Team C is confidential, so a forbid on reads is attached there. The reference model produces the following trace.

  1. Her client starts before anything is chosen and queries the service root in the grant-shaped profile. The snapshot contains two claims: ALLOW at companies/A for companies.get and teams.list, and ALLOW at companies/A/teams/B for widgets.create and widgets.update. The client now knows two scopes where Alice can act. teams.create appears in no claim, so the client has no proof for "New team" and does not offer it.
  2. The viewer's other read keys are omitted at A. The forbid at Team C makes "reads are allowed everywhere in A" false, and the grant-shaped profile cannot carry holes, so those keys are omitted. Nothing false is asserted.
  3. She opens Team B. The client queries that anchor and receives one claim carrying teams.get, settings.get, widgets.get, widgets.list, widgets.search, widgets.count, widgets.create, and widgets.update. "New widget" and "Edit" are offered; "Delete" is not, because widgets.delete is absent.
  4. With the scoped-claims profile, one query at A suffices. The same read keys arrive as ALLOW over companies/A with the hole companies/A/teams/C, plus DENY at C. The client folds ALLOW for Team B and DENY for Team C without a second round trip, and write keys arrive as DENY over A outside Team B.
  5. A wildcard List across the teams of A is not offered. widgets.list does not hold in every team the wildcard matches because of Team C, so the fold is not ALLOW, and the client offers SearchWidgets instead, which the server filters per parent and per item.
  6. The confidential team is still listed. The forbid at Team C does not reach teams.list, which binds to the company, so ListTeams on A returns C to Alice. If C's existence must be hidden from her, she is not granted teams.list on A (§4.3).
  7. An upsert needs create as well as update. UpdateWidget with allow_missing = true requires widgets.update on the widget and widgets.create on Team B. Alice holds both. A caller with only UPDATE is refused before any row is read.
  8. Her writer grant is revoked. The server denies the next update as soon as it observes the new policy state. Her client may display "Edit" until the snapshot's expire_time passes or the denial triggers a refresh; the stale snapshot confers nothing.

The executable checks exercise a finite reference model of this specification rather than a production enforcement point or a proof over arbitrary policies. They run in the HTML edition on load or on demand, and the same model drives the simulator (§3.9) and the explorer (§4.1). Each check is tagged with the area it covers. Checks marked "Pinned" record behavior that was questioned during review and confirmed correct so it does not regress. 5.1 Steel-Manned Objections & Architectural Boundaries

          
A specification should say clearly where it stops. These objections mark its boundaries.

          
    
            
  • Objection 1 — A scope with very many exceptions. A hole removes a positive proof; a DENY claim proves a refusal. If a server's budget cannot carry a claim together with every hole it needs, it omits that claim regardless of kind: an ALLOW sent without one of its holes would allow inside the exception, and a DENY sent without one would deny where the caller is allowed. Without other evidence the client folds UNLOADED, never a guess. The grant-shaped profile behaves this way by construction.
    • 
            
  • Objection 2 — Non-hierarchical sharing graphs. In collaboration products where access is attached to each document through sharing links instead of parent folders, almost nothing is uniform across a folder. Boundary: do not use scope-level contexts as the primary model there. Use relationship-based checks (SpiceDB, OpenFGA) with bulk checks and resource lookups [10] [20], and keep contexts for the surrounding workspace chrome.
    • 
            
  • Objection 3 — Client and server can drift. Both sides interpret the same protobuf descriptors directly, and every snapshot carries the server's opaque descriptor_etag so browser clients (via HTTP ETag) and gRPC reflection clients detect drift and refresh descriptors automatically (§3.7). While a client is briefly behind or ahead, additive releases stay sound; only changes to an existing method itself (or alternating replies during a rolling deploy across a reclassification) can transiently disagree until the rollout settles. What remains is drift between a declaration and the handler behind it: test declarations against handler behavior with allowed and denied requests, including wildcard Lists, upserts, and partial batches. Anything depending on stored resource state is decided by the handler and projects as CONDITIONAL because core contexts never read stored rows.
    • 
            
  • Objection 4 — Contexts go stale after a revocation. A client caches a snapshot until its expire_time, so a freshly revoked user may see an enabled action until the server refuses it. Mitigation: use snapshots strictly for presentation, and on PERMISSION_DENIED from any call evict and refresh the matching anchor. The server enforces revocation immediately; normal wall-clock skew on expire_time only shortens cache life (fast clock) or slightly widens an advisory UI window (slow clock) and never weakens enforcement.
    • 
            
  • Objection 5 — Class grants expand silently when an RPC is added. They would, without the capability diff. The build reports every key each role gains or loses, and operations that should never be picked up by a class selector are marked explicit_grant_only (§3.7).
    • 
            
  • Objection 6 — Derived identities tie permissions to the API surface. Renaming a resource's plural or an operation changes keys, and with them any role that names the operation. That is a policy change, and the capability diff reports it as one. Roles that select by class are unaffected. An organization that must keep a legacy vocabulary of permission names maps it to derived keys in server policy, where it is not a client's concern.
    • 
            
  • Objection 7 — Why not send roles to the frontend? A role name means nothing without its definition, exceptions are not part of any role, and exposing role structure couples every client to policy internals. Keys at scopes are what the policy amounts to for this caller, which is all a frontend or agent host needs and all it should rely on.
    •
